# 数据库连接池

前面 JDBC 篇你写的代码每次操作都 `DriverManager.getConnection`——建连接、用完、关连接。但建立数据库连接很慢（TCP 握手 + 认证，几十到几百毫秒），频繁建关连接会让数据库成为瓶颈。能不能**预先建好一批连接，用时借、用完还**？这就是**连接池**。本篇讲清连接池的原理、Druid 与 HikariCP 两大主流、配置与监控，以及为什么不用裸 JDBC 连接。这是 Spring Boot 默认内嵌 HikariCP 的底层。

> 💡 本篇建议用 HikariCP 写一个连接池，对比"每次 new Connection"和"从池借连接"的性能——你会直观看到连接池快一个数量级。理解了本篇，Spring Boot 自动配置 DataSource 对你就是透明的。

---

## 一、为什么需要连接池

### 1.1 裸 JDBC 的问题

```java
// 裸 JDBC：每次操作建连接、关连接
Connection conn = DriverManager.getConnection(url, user, pwd);  // 慢：TCP+认证
// 用连接查数据
conn.close();   // 关闭，下次又要重建
```

**痛点**：
- **建连接慢**：TCP 三次握手 + MySQL 认证 + 会话初始化，几十到几百毫秒
- **频繁建关耗资源**：每次都建关，CPU/网络/数据库负担重
- **无法控制并发**：突发流量可能瞬间建几百个连接，压垮数据库
- **连接泄漏**：忘记 `close()`，连接泄漏，数据库连接数耗尽

### 1.2 连接池的解法

**连接池**预先建一批连接放"池子"里，用时借、用完还（不是真关，是还回池）：

```
启动 → 建一批连接（如 10 个）放池子
请求1 → 从池借一个连接 → 用 → 还回池（不真关）
请求2 → 从池借一个连接 → 用 → 还回池
...
```

| 对比项 | 裸 JDBC | 连接池 |
| :--- | :--- | :--- |
| 建连接 | 每次新建（慢） | 预建复用（快） |
| 关连接 | 真关闭 | 还回池（复用） |
| 并发控制 | 无（可能压垮 DB） | 有（上限保护 DB） |
| 连接泄漏 | 易发生 | 池可回收超时连接 |

> 💡 **连接池的核心价值**：复用连接 + 控制并发。**复用**省去建连接的开销（快一个数量级），**控制**限制最大连接数保护数据库。这是生产环境必须用连接池的原因——裸 JDBC 只适合学习 demo。

> 💡 **`close()` 的真相**：从池借的连接，调 `close()` 不是真关闭，而是**还回池**（标记为可用）。这是连接池的关键设计——`Connection` 对象被池代理，`close` 被拦截改成归还。理解这点，就不会疑惑"关了连接怎么池里还有"。

## 二、连接池原理 ⭐

### 2.1 核心参数

| 参数 | 作用 | 典型值 |
| :--- | :--- | :--- |
| `initialSize` / `initialPoolSize` | 启动时建的初始连接数 | 5-10 |
| `minIdle` / `minimumIdle` | 最小空闲连接（保持的底线） | 5-10 |
| `maxActive` / `maximumPoolSize` | **最大连接数**（上限） | 20-50 |
| `maxWait` / `connectionTimeout` | 借连接最长等待时间 | 30 秒 |
| `idleTimeout` | 空闲连接超时（多久不用回收） | 10 分钟 |
| `maxLifetime` | 连接最大存活时间（防 DB 端超时） | 30 分钟 |
| `keepAlive` | 空闲连接保活（防被 DB 断） | true |

> ⚠️ **`maxActive` 是保护数据库的关键**：它限制最大连接数，防止突发流量建几百个连接压垮 DB。**设太小**→ 请求排队等连接；**设太大**→ 数据库扛不住。要根据 DB 配置（`max_connections`）和并发量调优。

> 💡 **`maxLifetime` 防的是 DB 端超时**：MySQL 有 `wait_timeout`（默认 8 小时），空闲连接超时会被 DB 单方面断开。池里的连接如果不知道被断了，借出来用会报错。`maxLifetime` 设小于 DB 的 `wait_timeout`，主动回收重建，避免借出"已断"的连接。

### 2.2 借还连接的流程

```
请求连接：
  池有空闲连接？ → 有：借出，标记为"使用中"
                → 无：当前连接数 < maxActive？建新连接
                              → 是：建新连接借出
                              → 否：等待 maxWait，超时抛异常

归还连接（close）：
  标记为"空闲"，还回池（不真关）
  如果连接已坏 → 真关闭，从池移除
```

> 💡 **借不到连接的两种情况**：池满（达到 `maxActive`）且都在用 → 等待 `maxWait`，超时抛异常。这是连接池的"限流"作用——保护数据库不被压垮，但代价是请求可能超时。

### 2.3 连接泄漏检测

如果借了连接不还（忘记 `close`），连接被占着不释放，池子耗尽。好的连接池有泄漏检测：

- **Druid**：`removeAbandoned` + `removeAbandonedTimeout`，超时未还的连接强制回收
- **HikariCP**：`leakDetectionThreshold`，超时未还记日志告警

> ⚠️ **连接泄漏是生产事故常见原因**：某个方法借了连接异常没 `close`，连接泄漏，池子慢慢耗尽，整个应用无法访问数据库。**try-with-resources 是防泄漏的标准写法**（JDBC 篇讲过）。

## 三、HikariCP ⭐

### 3.1 为什么是 HikariCP

**HikariCP** 是目前性能最高的 JDBC 连接池，Spring Boot 2.0+ 默认内嵌。特点：
- **极快**：用字节码优化、无锁设计、FastList 等技术，性能远超其他池
- **轻量**：代码量小（~130KB），配置简单
- **可靠**：严格的质量保证，连接泄漏检测

> 💡 **Spring Boot 默认 HikariCP**：引入 `spring-boot-starter-jdbc` 或 `spring-boot-starter-data-jpa`，HikariCP 自动加入依赖、自动配置。**不用手动引入，开箱即用**。

### 3.2 HikariCP 配置

```java
// 手动配置 HikariCP（理解原理）
HikariConfig config = new HikariConfig();
config.setJdbcUrl("jdbc:mysql://localhost:3306/test?useSSL=false&serverTimezone=Asia/Shanghai");
config.setUsername("root");
config.setPassword("123456");
config.setDriverClassName("com.mysql.cj.jdbc.Driver");   // MySQL 8

// 连接池参数
config.setMaximumPoolSize(20);        // 最大连接数
config.setMinimumIdle(5);              // 最小空闲
config.setConnectionTimeout(30000);     // 借连接超时 30 秒
config.setIdleTimeout(600000);          // 空闲超时 10 分钟
config.setMaxLifetime(1800000);         // 最大存活 30 分钟
config.setPoolName("MyHikariPool");

HikariDataSource ds = new HikariDataSource(config);

// 用法：从池借连接，用完还（close 是还回池）
try (Connection conn = ds.getConnection()) {
    // 查数据
}   // close() 自动还回池
```

### 3.3 HikariCP 的精简参数

HikariCP 刻意精简参数（作者认为很多参数有害无益）：

| 参数 | 作用 | 默认值 |
| :--- | :--- | :--- |
| `maximumPoolSize` | 最大连接数 | 10 |
| `minimumIdle` | 最小空闲 | 同 maximumPoolSize |
| `connectionTimeout` | 借连接超时 | 30 秒 |
| `idleTimeout` | 空闲超时 | 10 分钟 |
| `maxLifetime` | 最大存活 | 30 分钟 |
| `leakDetectionThreshold` | 泄漏检测 | 0（关闭） |

> 💡 **HikariCP 的 `minimumIdle` 默认等于 `maximumPoolSize`**：作者建议不设最小空闲，让池在空闲时缩到 0、忙时扩到 max——固定大小池性能最好。这是和其他池的设计差异。

## 四、Druid

### 4.1 Druid 的特点

**Druid**（阿里）是国内流行的连接池，特点：
- **监控强**：内置 Web 监控页面，看 SQL 执行情况、慢查询、连接状态
- **防火墙**：SQL 注入检测、慢 SQL 告警
- **功能全**：参数丰富，适合精细调优

> 💡 **Druid vs HikariCP**：
> - **HikariCP**：性能极致、轻量、Spring Boot 默认——大多数项目首选
> - **Druid**：监控强、SQL 防火墙、国内文档多——需要强监控/SQL 审计时选
>
> 性能 HikariCP 略胜，监控 Druid 略胜。**Spring Boot 默认 HikariCP，需要 Druid 手动切换**。

### 4.2 Druid 配置

```java
// 手动配置 Druid
DruidDataSource ds = new DruidDataSource();
ds.setUrl("jdbc:mysql://localhost:3306/test?useSSL=false&serverTimezone=Asia/Shanghai");
ds.setUsername("root");
ds.setPassword("123456");
ds.setDriverClassName("com.mysql.cj.jdbc.Driver");

// 连接池参数
ds.setInitialSize(5);          // 初始连接
ds.setMinIdle(5);               // 最小空闲
ds.setMaxActive(20);           // 最大连接
ds.setMaxWait(60000);          // 借连接超时 60 秒
ds.setTimeBetweenEvictionRunsMillis(60000);   // 检测间隔
ds.setMinEvictableIdleTimeMillis(300000);     // 最小空闲时间
ds.setMaxEvictableIdleTimeMillis(900000);     // 最大空闲时间

// Druid 特色：监控 + 防火墙
ds.setFilters("stat,wall");    // stat=监控统计, wall=SQL 防火墙
```

### 4.3 Druid 监控页面

Druid 内置 Web 监控，配置一个 Servlet 暴露：

```java
// 注册 Druid 监控 Servlet（原生）
@WebServlet("/druid/*")
public class DruidStatViewServlet extends StatViewServlet { }  // 继承 Druid 提供

// 或 web.xml 配置
```

访问 `http://localhost:8080/druid`，看 SQL 执行次数、慢 SQL、连接池状态。这是 Druid 的核心卖点。

> 💡 **Druid 监控的价值**：生产环境看哪个 SQL 慢、哪个表查得多、连接池有没有泄漏——一眼看清。HikariCP 要配 Actuator + 外部工具（如 Prometheus）才有类似能力。

## 五、连接池选型与对比 ⭐

| 对比项 | HikariCP | Druid | C3P0（已过时） |
| :--- | :--- | :--- | :--- |
| 性能 | ⭐ 最高 | 高 | 低 |
| 监控 | 弱（靠 Actuator） | ⭐ 内置 Web 页 | 弱 |
| SQL 防火墙 | 无 | ⭐ 有 | 无 |
| 配置复杂度 | 简单 | 中等 | 复杂 |
| Spring Boot 默认 | ✅ | 需手动 | ❌ |
| 适用场景 | 通用首选 | 强监控/审计 | 不推荐 |

> ⚠️ **C3P0 和 DBCP 已过时**：早期用的 C3P0、DBCP 性能差、配置复杂，已被 HikariCP/Druid 取代。**新项目不要用 C3P0/DBCP**，老项目看到可建议迁移。

> 💡 **选型建议**：
> - **通用项目**：HikariCP（Spring Boot 默认，不用配置）
> - **需要 SQL 监控/审计**：Druid（内置监控页面）
> - **微服务/高并发**：HikariCP（性能最优）
> - **国内传统项目**：Druid（文档多、监控强）

---

## ⚠️ 重点

1. **连接池核心价值**：复用连接（快）+ 控制并发（保护 DB）。
2. **`close()` 是还回池不是真关闭**：池代理了 Connection，close 被拦截成归还。
3. **`maxActive` 保护数据库**：限制最大连接，防突发流量压垮 DB。
4. **`maxLifetime` 防 DB 超时**：设小于 MySQL `wait_timeout`，主动回收重建。
5. **HikariCP 是 Spring Boot 默认**：性能最高，开箱即用。
6. **Druid 监控强**：内置 Web 页面，看 SQL/慢查询/连接状态。
7. **try-with-resources 防泄漏**：借了连接必须还，用 try-with-resources 保证。
8. **C3P0/DBCP 已过时**：新项目用 HikariCP 或 Druid。
9. **连接泄漏是生产事故**：忘记 close 连接泄漏，池耗尽，用泄漏检测兜底。

## 💻 实战案例：HikariCP 工具类

需求：封装 HikariCP 工具类，全局共享一个连接池。

```java
public class HikariUtil {
    private static final HikariDataSource dataSource;

    static {
        HikariConfig config = new HikariConfig();
        // 从配置文件读（实际项目用 properties/yaml）
        config.setJdbcUrl("jdbc:mysql://localhost:3306/test?useSSL=false&serverTimezone=Asia/Shanghai&characterEncoding=utf8");
        config.setUsername("root");
        config.setPassword("123456");
        config.setDriverClassName("com.mysql.cj.jdbc.Driver");
        config.setMaximumPoolSize(20);
        config.setMinimumIdle(5);
        config.setConnectionTimeout(30000);
        config.setMaxLifetime(1800000);
        dataSource = new HikariDataSource(config);
    }

    public static Connection getConnection() throws SQLException {
        return dataSource.getConnection();   // 从池借
    }

    public static DataSource getDataSource() {
        return dataSource;
    }
}
```

```java
// 使用：try-with-resources 保证归还
try (Connection conn = HikariUtil.getConnection()) {
    try (PreparedStatement ps = conn.prepareStatement("SELECT * FROM user WHERE id=?")) {
        ps.setInt(1, 1);
        try (ResultSet rs = ps.executeQuery()) {
            while (rs.next()) {
                System.out.println(rs.getString("name"));
            }
        }
    }
}   // conn.close() 自动还回池（不是真关）
```

> 💡 **这就是 Spring Boot 自动配置 DataSource 的前身**：本篇手动建 HikariDataSource 存进静态变量全局共享，Spring Boot 用 `DataSourceAutoConfiguration` 自动建 DataSource 存进 IoC 容器全局共享。**本篇手动做的事，Spring Boot 自动做了**——理解了本篇，Spring Boot 的 DataSource 自动配置对你就是透明的。

## 📌 在 Spring Boot 中

> 本篇讲的连接池原理、HikariCP/Druid 配置、连接泄漏，在 Spring Boot 中由自动配置 DataSource 接管。下面逐一对照，给出实际开发代码，以及"出问题怎么回到连接池原理排查"。实际开发你几乎不手动建连接池——Spring Boot 自动配 HikariCP，`spring.datasource.*` 一行配置，但理解了本篇，连接超时、池满、连接泄漏问题时才知道怎么查。

### 1. 自动配置：从"手动 HikariDataSource"到"spring.datasource"

**原生**：本篇实战手动 `new HikariConfig` + `new HikariDataSource`。
**Spring Boot**：`application.yml` 配置，自动建 DataSource。

```yaml
spring:
  datasource:
    url: jdbc:mysql://localhost:3306/test?useSSL=false&serverTimezone=Asia/Shanghai&characterEncoding=utf8
    username: root
    password: 123456
    driver-class-name: com.mysql.cj.jdbc.Driver
    # 不指定 type 默认 HikariCP
    type: com.zaxxer.hikari.HikariDataSource
    hikari:
      maximum-pool-size: 20          # 对应 setMaximumPoolSize
      minimum-idle: 5                # 对应 setMinimumIdle
      connection-timeout: 30000     # 对应 setConnectionTimeout
      idle-timeout: 600000           # 对应 setIdleTimeout
      max-lifetime: 1800000          # 对应 setMaxLifetime
      pool-name: MyHikariPool
```

```java
// Spring Boot 自动建好 DataSource，直接注入用
@Service
public class UserService {
    @Autowired
    private DataSource dataSource;   // Spring 自动注入 HikariDataSource

    public User findById(int id) throws SQLException {
        try (Connection conn = dataSource.getConnection()) {   // 从池借
            // ...
        }   // close 还回池
    }
}
```

> 💡 **原理对应**：`spring.datasource.*` 底层就是本篇的 `new HikariConfig` + `new HikariDataSource`——Spring Boot 的 `DataSourceAutoConfiguration` 读 yml 配置，自动建 HikariDataSource 存进 IoC 容器。**本篇手动建的连接池，Spring Boot 自动建好注入**，你只管用 `DataSource`。

> 💡 **原理排查**：启动报"Failed to obtain JDBC Connection"？检查 url/username/password、数据库是否启动、`maximum-pool-size` 是否够。运行中报 "Connection is not available, request after 30s"？池满了——检查 `maximum-pool-size`、是否有连接泄漏（慢 SQL 占着连接）、是否慢查询拖累。回到连接池原理：借不到连接要么池满要么配置错。

### 2. 切换 Druid：从"HikariCP 默认"到"手动换 Druid"

**原生**：本篇第四节手动配 Druid。
**Spring Boot**：引入依赖 + `type: druid`。

```xml
<dependency>
    <groupId>com.alibaba</groupId>
    <artifactId>druid-spring-boot-starter</artifactId>
    <version>1.2.20</version>
</dependency>
```

```yaml
spring:
  datasource:
    type: com.alibaba.druid.pool.DruidDataSource   # 切换 Druid
    url: jdbc:mysql://localhost:3306/test
    username: root
    password: 123456
    druid:
      initial-size: 5
      min-idle: 5
      max-active: 20
      max-wait: 60000
      filters: stat,wall          # 监控 + 防火墙
      stat-view-servlet:
        enabled: true             # 开启监控页面
        url-pattern: /druid/*
```

> 💡 **原理对应**：`spring.datasource.type` 指定连接池实现——改一行就换池。**本篇手动 new 不同池，Spring Boot 用 `type` 配置切换**，DataSource 接口不变（多态）。

### 3. 监控：从"Druid Web 页"到"Actuator + Prometheus"

**原生**：本篇 4.3 用 Druid 内置监控页。
**Spring Boot**：Actuator + Prometheus + Grafana（更通用），或 Druid 监控页。

```yaml
# Spring Boot Actuator 暴露指标
management:
  endpoints:
    web:
      exposure:
        include: health,info,metrics,prometheus
  metrics:
    export:
      prometheus:
        enabled: true
```

> 💡 **原理对应**：HikariCP 的指标通过 Actuator 暴露给 Prometheus，Grafana 展示——比 Druid 内置页更通用（不只看连接池，还看 JVM/HTTP）。**本篇 Druid 的监控，Spring Boot 用 Actuator 体系统一管理**。Druid 用户仍可用内置页（`druid-spring-boot-starter` 自动配）。

> 💡 **原理排查**：监控看不到连接池指标？检查 Actuator 是否暴露 `metrics`、`/actuator/metrics/hikaricp.*` 是否有数据。回到连接池原理：监控靠池暴露指标，要开启才能看。

### 4. 连接泄漏：从"leakDetectionThreshold"到"Spring 同样配置"

**原生**：本篇 2.3 讲 HikariCP 的 `leakDetectionThreshold`。
**Spring Boot**：同样配置，yml 一行。

```yaml
spring:
  datasource:
    hikari:
      leak-detection-threshold: 60000   # 借连接 60 秒未还记日志告警
```

> 💡 **原理对应**：`leak-detection-threshold` 底层就是 HikariCP 的泄漏检测——借出连接超时未还，记日志（含借出堆栈，方便定位哪个方法泄漏）。**本篇讲的泄漏检测，Spring Boot 用 yml 开启**，生产环境建议开启（设 60 秒）。

> 💡 **原理排查**：日志出现 "Apparent connection leak detected"？有连接借出超时未还——看日志里的堆栈，定位哪个方法没 close。回到连接池原理：泄漏是忘记归还，try-with-resources 是根治方案。

### 5. 事务管理：从"手动 conn.setAutoCommit"到"@Transactional"

**原生**：JDBC 篇讲的手动 `conn.setAutoCommit(false)` + `commit`/`rollback`。
**Spring Boot**：`@Transactional` 注解，Spring 用连接池的连接管事务。

```java
@Service
public class UserService {
    @Transactional   // Spring 自动从池借连接、关自动提交、提交/回滚
    public void transfer(int from, int to, double amount) {
        // Spring 从 DataSource 借连接，setAutoCommit(false)
        accountDao.debit(from, amount);
        accountDao.credit(to, amount);
        // 方法正常结束 commit，异常 rollback，连接还回池
    }
}
```

> 💡 **原理对应**：`@Transactional` 底层从 DataSource（连接池）借连接，设 `autoCommit=false`，方法结束 commit/rollback，连接还回池。**本篇连接池 + JDBC 篇事务，Spring 用 `@Transactional` 统一封装**——连接从池来，事务由 Spring 管，业务代码只写逻辑。理解了本篇和 JDBC 篇，`@Transactional` 对你就是透明的。

> 💡 **原理排查**：`@Transactional` 不生效？检查方法是否 public、是否同类调用（同类调用走不到代理）、异常是否被 catch 吞了（吞了 Spring 不知道该回滚）。回到事务原理：事务靠 AOP 代理拦截，同类调用/私有方法/异常被吞都会失效。

---

> 一句话：**连接池复用连接 + 控制并发，是生产环境必须**。Spring Boot 里你几乎不手动建连接池——`spring.datasource.*` 自动配 HikariCP，`@Autowired DataSource` 直接用，`@Transactional` 管事务。但底层还是本篇的 HikariCP/Druid + 借还连接 + maxActive/maxLifetime。理解了本篇，连接超时、池满、泄漏、事务不生效问题对你就是透明的。**出连接超时、池满、连接泄漏问题时，你仍要回到本篇原理排查**：`maximum-pool-size` 够吗、`max-lifetime` 小于 DB 超时吗、连接泄漏了吗、try-with-resources 用了吗。

## 本章小结

本篇讲清了数据库连接池：它预先建一批连接复用（省建连接开销）+ 控制最大连接数（保护 DB），`close()` 是还回池而非真关。重点掌握核心参数（`maxActive`/`maxLifetime`/`maxWait`/`idleTimeout`）、HikariCP（Spring Boot 默认，性能最高）、Druid（监控强，内置 Web 页）、连接泄漏检测、try-with-resources 防泄漏、C3P0/DBCP 已过时。核心认知：**Spring Boot 默认 HikariCP，`spring.datasource.*` 自动配置，本篇手动建的池被自动建好注入**。下一篇 [18-Apache DBUtils](18-Apache%20DBUtils.md) 讲如何简化 JDBC 的 CRUD 样板代码，为 MyBatis 做铺垫。
