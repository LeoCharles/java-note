# 00 - LangChain / LangGraph 学习路线图

> 这是一套**写给后端程序员的智能体（Agent）开发笔记**。
> 你不需要任何机器学习、算法或 Python AI 经验——只要会写业务代码（Java/Spring 更好，很多概念能直接类比），就能从零走到能独立交付一个生产级 AI 应用。
> 全系列 **13 篇**，按「基础概念 → 框架用法 → 编排内核 → 工程落地 → 实战项目」递进。

| 你是 | 你会得到什么 |

| 后端开发（Java / Spring / Go） | 用熟悉的分层、事务、会话、AOP 视角理解 Agent；知道它该放在架构的哪一层 |
| 前端 / 全栈 | 理解模型调用的成本、延迟和不确定性，能设计合理的交互 |

### 不写给谁

- 想训练/微调模型的人 —— 本系列**不涉及模型训练**，只讲如何**用模型做应用**
- 想学算法原理的人 —— 我们关心的是"怎么把模型接进系统"，不是"注意力机制怎么算"
- 只想复制一段 Demo 的人 —— 每篇都有可运行代码，但更强调"为什么这样写、线上会怎么坏"

### 一句话理解 Agent

> **Agent = 大模型 + 能调用的工具 + 一个自我循环的决策过程。**

普通程序：`if (条件) { 调接口 } else { 返回错误 }` —— 分支是你写死的。
Agent：**"下一步做什么"由模型自己决定**，它看到工具清单，选择调用哪个、传什么参数、要不要再调一次。

这既是它的威力，也是它的风险来源：**你不再能静态确定程序会走哪条路**，所以工程上必须补上状态管理、可观测性、权限边界和人工兜底——这正是 LangGraph 存在的理由。

## 🚀 五阶段学习路径

### 阶段一：建立正确的直觉（约 2–3 小时）

读 **01**。重点不是记名词，而是建立三个判断：

1. 模型**没有记忆**——它每次只能看到你塞进 Prompt 的内容（所以才有第 05 篇）
2. 模型**不知道你的私有数据**——所以才有 RAG（第 04 篇）
3. 模型**不能执行动作**——只能"说"要调用什么，真正执行的是你的代码（所以才有第 03、06 篇）

> 💡 这三句话能解释 80% 的初学者困惑。比如"为什么它记不住上一轮"、"为什么它编造了不存在的制度"、"为什么它说已经帮我下单了但其实没下单"。

### 阶段二：把模型当普通 API 用（约 1 周）

读 **02 → 03**。这一阶段最容易犯的错是**过早追求"智能"**。先把模型当作一个"输入文本、输出文本"的远程接口：

- 学会流式输出（用户等 10 秒看空白页会直接关掉）
- 学会结构化输出（后端要的是 JSON，不是一段散文）
- 学会处理超时、限流、报错（它就是个不稳定的第三方服务）

### 阶段三：给模型"喂知识"和"给记忆"（约 1 周）

读 **04 → 05**。RAG 是目前企业落地占比最高的场景，务必吃透：

- 切分策略决定了检索质量（比换模型更有效）
- 向量检索不是万能的，关键词检索 + 重排往往效果更好
- 记忆不是"聊得越久越好"，是要**有策略地裁剪和压缩**

### 阶段四：从"问答"到"办事"（约 1–2 周）

读 **06 → 07 → 08**。这是全系列的核心转折：

- 06 让你看到 Agent 的**神奇与失控**：它真的会自己决定调什么工具
- 07 用 LangGraph 把这种"失控"变成**显式状态机**：每个节点做什么、什么条件下走哪条边，全部可见、可测、可回放
- 08 补上生产必需品：**断点续跑、人工审批、状态回滚**

> ⚠️ 很多人卡在这里：会用 `create_agent` 写 Demo，一旦业务要求"退款前必须人工确认""失败要能重试""客户中途改需求要能回退"，就抓瞎了。第 07、08 篇就是解药。

### 阶段五：上线（约 1–2 周）

读 **09 → 10 → 11/12**。上线要回答的问题和 Demo 完全不同：

- 它刚才为什么这么回答？（可观测）
- 改了 Prompt 之后整体变好还是变坏？（评测）
- 用户能不能诱导它泄露数据 / 乱调工具？（安全）
- 一次对话花多少钱？P99 延迟多少？（成本与性能）
- 出问题能不能降级、能不能回滚？（稳定性）

## 🛠️ 环境准备

### 1. Python 环境

推荐 **Python 3.11+**（LangChain 1.x 最低 3.10）。

```bash
# 方案 A：官方推荐 uv（快，依赖解析稳）
pip install uv
uv venv
source .venv/bin/activate        # Windows: .venv\Scripts\activate
uv pip install -U langchain langgraph langchain-openai

# 方案 B：pip + venv
python -m venv .venv
source .venv/bin/activate
pip install -U langchain langgraph langchain-openai
```

> 💡 **给 Java 程序员的对照**：`venv` ≈ Maven 的 `target/` + 独立依赖树；`pyproject.toml` ≈ `pom.xml`；`uv` ≈ 一个更快的 Maven/Gradle；`pip freeze` ≈ 生成锁文件。

### 2. 一个可用的模型

你**不需要** OpenAI 账号也能学完本系列。任何**兼容 OpenAI 协议**的服务都能用：

```python
# .env
OPENAI_API_KEY=sk-xxx
OPENAI_BASE_URL=https://api.openai.com/v1      # 或换成国内的兼容端点
```

常见可选后端：

| 服务 | 配置要点 | 备注 |
| :--- | :--- | :--- |
| OpenAI | 默认 | 生态兼容性最好 |
| DeepSeek / 通义千问 / 豆包等 | `base_url` 指向其 OpenAI 兼容端点 | 国内网络友好、成本低 |
| Ollama（本地） | `base_url=http://localhost:11434/v1`，`api_key` 随便填 | 完全离线，适合调试 |
| 公司内网网关 | 通常也是 OpenAI 协议 | 注意是否需要额外鉴权头 |

```python
from langchain_openai import ChatOpenAI

model = ChatOpenAI(
    model="deepseek-chat",
    base_url="https://api.deepseek.com/v1",
    api_key="sk-xxx",
    temperature=0,
)
```

> ⚠️ **不同模型的能力差异很大**：工具调用（Tool Calling）、结构化输出、长上下文，老模型或小模型可能不支持或表现很差。本系列的部分示例需要**支持 Function Calling 的模型**，遇到不支持时先换模型，不要怀疑代码。

### 3. 可观测（强烈建议一开始就配）

```bash
# .env
LANGSMITH_TRACING=true
LANGSMITH_API_KEY=lsv2_xxx
LANGSMITH_PROJECT=agent-learning
```

配好后，你跑的每一次调用都会在 LangSmith 上有一条完整链路：输入、输出、token 数、耗时、工具调用参数。**调 Agent 不配追踪，等于闭着眼睛 debug。**

> 💡 不想用外部服务？后面第 10 篇会讲自建最小可观测方案的思路（结构化日志 + 调用耗时 + 工具命中率）。

## 📖 核心概念速查

先混个脸熟，看不懂没关系，后面每篇都会展开。

| 概念 | 一句话解释 | 类比（后端视角） | 详见 |
| :--- | :--- | :--- | :--- |
| **LLM** | 大语言模型，本质是"根据上文预测下一个 token" | 一个无状态、极慢、有时会编造数据的远端服务 | 01 |
| **Token** | 模型处理的最小文本单位 | 计费单位 + 长度限制单位 | 01 |
| **上下文窗口** | 一次请求能塞进去的最大 token 数 | 接口的 payload 上限 | 01 |
| **Prompt** | 你发给模型的全部文本（含系统指令、历史、资料） | 请求体 | 01、02 |
| **温度 temperature** | 输出的随机性（0 稳定，1 发散） | 类比"重试时的抖动幅度" | 01 |
| **Function Calling** | 模型以结构化格式"请求"调用某个函数 | 模型返回了一个 HTTP 调用意图，执行权在你 | 03 |
| **Embedding** | 把文本变成向量，语义相近则向量相近 | 给文本算一个"语义哈希"，可算距离 | 04 |
| **向量库** | 存向量、支持相似度检索的数据库 | 带 ANN 索引的 KV 库 | 04 |
| **RAG** | 先检索资料，再把资料塞进 Prompt 让模型回答 | 查询前先做一次数据组装 | 04 |
| **Agent** | 能自主决定"下一步做什么"的模型驱动循环 | 一个由模型驱动的状态机 | 06 |
| **ReAct** | Reason + Act：思考 → 调工具 → 看结果 → 再思考 | 带循环的决策流程 | 06 |
| **State** | 图在某一时刻的全部数据 | 一次请求的上下文对象（Context） | 07 |
| **Reducer** | 多个节点同时写同一个字段时的合并规则 | 并发写入的 merge 函数 | 07 |
| **Checkpoint** | 每个节点执行后的状态快照 | 数据库事务的 savepoint | 08 |
| **Thread** | 一条独立的对话会话 ID | 会话 sessionId | 08 |
| **Interrupt** | 图执行到某节点时暂停，等待外部输入 | 分布式事务里的"等待人工确认" | 08 |
| **Middleware** | 在模型/工具调用的前后插入逻辑 | Spring 的 `HandlerInterceptor` / AOP | 06 |
| **Tracing** | 记录一次调用的完整调用链 | 分布式链路追踪（SkyWalking） | 10 |
| **Eval** | 用数据集自动评估回答质量 | 集成测试 + 断言 | 10 |

## 🧩 生态全景：这些包到底谁是谁

初学者最容易乱的地方：**LangChain、LangGraph、LangSmith 是什么关系？**

```text
┌──────────────────────────────────────────────────────────────┐
│  你的应用                                                     │
└───────────────┬──────────────────────────────────────────────┘
                │
    ┌───────────▼────────────┐        ┌───────────────────────┐
    │  LangChain             │        │  LangSmith            │
    │  高层封装：模型、工具、    │───────▶│  可观测 / 评测 / 调试   │
    │  RAG、Agent、中间件       │  追踪   │  （SaaS 或自部署）      │
    └───────────┬────────────┘        └───────────────────────┘
                │ 构建于
    ┌───────────▼────────────┐
    │  LangGraph             │
    │  低层编排：状态图、持久化、  │
    │  人工介入、多 Agent        │
    └───────────┬────────────┘
                │ 依赖
    ┌───────────▼────────────┐
    │  langchain-core        │
    │  基础抽象：Runnable、消息、 │
    │  工具协议、回调、LCEL      │
    └────────────────────────┘
```

| 组件 | 定位 | 什么时候直接用 |
| :--- | :--- | :--- |
| **langchain-core** | 抽象与协议层 | 写自定义组件时 |
| **langchain** | 高层 API（`create_agent`、中间件、RAG 工具链） | 90% 的常规需求 |
| **langgraph** | 显式状态机、持久化、人工介入 | 流程复杂、要断点续跑、要多 Agent |
| **LangSmith** | 观测与评测平台 | 从第一天就该用 |
| **LangGraph Platform / Server** | 托管部署（API、队列、UI） | 需要对外提供服务时，也可自建 FastAPI |
| **LangChain4j / Spring AI** | Java 生态的同类框架 | **纯 Java 团队可评估**，见下 |

> 💡 **重要认知**：LangGraph 不是 LangChain 的"替代品"，而是**底座**。LangChain 1.x 的 `create_agent` 本身就是用 LangGraph 编译出来的。所以"学 LangChain 要不要学 LangGraph"的答案是：**做 Demo 不用，做生产必须。**

### 那 Java 团队该选哪个？

如果你是纯 Java 团队，完全有理由不引入 Python：

| 方案 | 优势 | 代价 |
| :--- | :--- | :--- |
| **LangChain4j** | Java 原生、与 Spring Boot 集成自然、API 风格贴近 LangChain | 生态与前沿特性的跟进略慢 |
| **Spring AI** | 官方（Spring 团队）维护、`ChatClient` 抽象干净、和 Spring 全家桶一致 | 相对年轻 |
| **Python LangChain/LangGraph** | 生态最全、新特性最先支持、社区示例最多 | 多一套技术栈、需要跨进程调用 |

> 💡 **本系列仍以 Python 为主**，原因不是"Java 不行"，而是：LangGraph 的图编排、中间件、评测工具在 Python 侧最完整，**先把模型和 Agent 的思维方式学会，换语言只是换写法**。第 10 篇会专门讲**Python Agent 服务如何被 Java 后端调用**（HTTP / 消息队列 / 网关鉴权 / 超时与降级）。

## 🔄 版本说明（重要）

AI 框架迭代极快，**"代码跑不起来"的第一原因通常是版本**。

### LangChain

| 版本 | 关键变化 |
| :--- | :--- |
| 0.1 / 0.2 | 早期版本，`LLMChain`、`AgentExecutor`、`initialize_agent` 为主 |
| 0.3 | `langchain-core` 拆分，LCEL（`|` 组合）成熟，`create_tool_calling_agent` |
| **1.0** | **`create_agent` 统一入口**；旧链式 API 迁到 `langchain-classic`；中间件（middleware）成为一等公民；消息类可直接从 `langchain.messages` 导入 |

**本系列以 1.x 为准**。如果你看到教程里用 `AgentExecutor` / `initialize_agent`，那是 0.x 的写法，**不是错，但已过时**。

### LangGraph

| 版本 | 关键变化 |
| :--- | :--- |
| 0.1 / 0.2 | `StateGraph` 基础形态，`MemorySaver`、`interrupt` 起步 |
| 0.3 / 0.4 | `Command`、`Send`（并行分发）、`InMemorySaver` 命名、Store 长期记忆 |
| **1.0** | API 趋于稳定；`create_react_agent` 在 `langgraph.prebuilt` 中保留；推荐用 LangChain 的 `create_agent` 作为上层封装 |

> - 尽量使用**跨版本稳定**的导入路径（如 `langchain_core.messages`）

## ⚠️ 初学者最常见的 8 个误解

| # | 误解 | 事实 |
| :--- | :--- | :--- |
| 1 | "模型记得我们上次聊的" | 模型**无状态**，记忆是你每次重新塞进去的 |
| 2 | "温度设 0 就完全确定了" | 大多数服务仍有微小抖动；且**不同批次/版本结果会变** |
| 3 | "换个更强的模型就能解决幻觉" | 幻觉主要靠**检索、约束、校验**解决，换模型只是缓解 |
| 4 | "Agent 越自主越好" | 自主性越高，**可预测性越低**。生产上要主动限制工具集和步数 |
| 5 | "RAG 就是接个向量库" | 检索质量取决于**切分、召回、重排、Prompt 组装**，向量库只是其中一环 |
| 6 | "先用 Prompt 糊一下再说" | Prompt 会随时间腐化，**必须配评测集**才能判断改动好坏 |
| 7 | "框架会帮我处理重试和成本" | 超出预期。**限流、缓存、预算、超时**都要自己设计 |
| 8 | "多 Agent 一定比单 Agent 强" | 大多数业务**单 Agent + 好工具**就够；拆多 Agent 会放大延迟与调试成本 |

## 🧭 怎么判断一个需求该用什么方案

这是实际工作中最高频的决策，先给你一张速查表，后面每篇会反复回到它：

```text
需求是什么？
│
├─ 只是改写/总结/翻译一段文本，且不依赖私有数据
│     └─▶ 直接调模型（Prompt Engineering）           → 02
│
├─ 需要模型基于"公司内部资料"回答
│     └─▶ RAG                                       → 04
│
├─ 需要模型"执行动作"（查库、下单、发消息）
│     └─▶ Tool Calling                              → 03
│
├─ 需要多步骤自主决策（先查再算再写）
│     └─▶ Agent + LangGraph                         → 06、07
│
├─ 需要人工审批 / 断点续跑 / 失败重试
│     └─▶ LangGraph + Checkpointer + Interrupt       → 08
│
└─ 需要多个角色分工（研究 / 写作 / 审核）
      └─▶ 多 Agent（先确认单 Agent 真的不行）          → 09
```

> ⚠️ **这个表要反着用**：先问"能不能用最简单的方式解决"。**用 Agent 解决一个分类问题，是新手最常见的过度设计。**

## ✅ 学习自检清单

学完一个阶段，用这几个问题检验自己（能答上来才算过关）：

**阶段一**
- [ ] 为什么模型"记不住"上一轮对话？记忆是怎么实现的？
- [ ] 上下文窗口超了会发生什么？有哪些应对手段？
- [ ] 模型说"我已帮你下单"但实际没下单，问题出在哪？

**阶段二**
- [ ] 流式输出解决了什么问题？服务端怎么实现？
- [ ] 结构化输出和"在 Prompt 里说请返回 JSON"有什么区别？
- [ ] RAG 里切分粒度、召回数量、重排，分别影响什么？

**阶段三**
- [ ] ReAct 循环什么时候停止？停止条件由谁决定？
- [ ] Agent 调用工具失败三次，应该怎么办？
- [ ] `create_agent` 和手写 `StateGraph` 各自适合什么场景？

**阶段四**
- [ ] 状态里的 `messages` 为什么要用 reducer 而不是直接赋值？
- [ ] 中断恢复时，模型会重新执行已经跑过的节点吗？
- [ ] 多 Agent 相比单 Agent，代价具体在哪里？

**阶段五**
- [ ] 线上回答变差了，你怎么定位是检索问题还是模型问题？
- [ ] 怎么防止用户通过 Prompt 注入让 Agent 调用越权工具？
- [ ] 一次对话的成本怎么核算？哪些手段最有效？
