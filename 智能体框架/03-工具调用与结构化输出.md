## 一、为什么需要工具调用

### 1.1 模型的能力边界

回顾 01 篇：模型只会"预测下一个 token"。它：

- 不知道**实时数据**（库存、订单状态、今天的汇率）
- 不会**精确计算**（金额、统计、日期差）
- 不能**修改任何东西**（下单、发消息、改状态）
- 不知道**你的业务规则**（谁能退款、退多少）

**工具调用就是给这些能力"外挂"接口。**

### 1.2 三个层次

```text
层次 1：纯问答
   "退货政策是什么？"           → 查知识库（RAG）

层次 2：查询类工具
   "我的订单 12345 到哪了？"     → 调订单查询 API

层次 3：执行类工具
   "帮我取消订单 12345"          → 调取消接口（有副作用！）
```

**层次 3 是风险的分水岭**：查询出错只是答错，执行出错是**真金白银的业务事故**。

> ⚠️ **本章的顺序很重要**：先把查询类工具做好，再碰执行类工具；执行类工具**必须有权限校验、确认机制和审计**。

### 1.3 工具调用的本质（再强调一次）

```text
模型输出：{"name": "get_order", "arguments": "{\"order_no\": \"12345\"}"}
                                    ↑ 注意：这只是"文本"，是一个 JSON 字符串
你的代码：解析 → 校验 → 执行 → 把结果作为 ToolMessage 塞回去
```

**模型从不执行任何代码。** 它只是"说"要调用什么。执行权永远在你的代码里——这也是你唯一能控制安全的地方。

## 二、工具调用的完整协议 ⭐

### 2.1 四步循环

```text
┌──────────────────────────────────────────────────────────┐
│ 1. 请求：messages + tools 定义                             │
│         ↓                                                 │
│ 2. 模型返回 AIMessage，其中 tool_calls 非空                 │
│         ↓                                                 │
│ 3. 你的代码：逐个执行工具，生成 ToolMessage                  │
│         ↓                                                 │
│ 4. 把 ToolMessage 追加进 messages，再次请求模型              │
│         ↓                                                 │
│    模型要么继续调工具（回到 2），要么给出最终回答（结束）      │
└──────────────────────────────────────────────────────────┘
```

### 2.2 原始的 REST 调用形态

```json
{
  "model": "gpt-4o-mini",
  "messages": [{"role": "user", "content": "订单 12345 到哪了？"}],
  "tools": [
    {
      "type": "function",
      "function": {
        "name": "get_order",
        "description": "根据订单号查询订单状态和物流信息。当用户询问订单进度、物流、发货情况时使用。",
        "parameters": {
          "type": "object",
          "properties": {
            "order_no": {
              "type": "string",
              "description": "订单号，纯数字，如 12345"
            }
          },
          "required": ["order_no"]
        }
      }
    }
  ]
}
```

返回：

```json
{
  "choices": [{
    "message": {
      "role": "assistant",
      "content": null,
      "tool_calls": [{
        "id": "call_abc123",
        "type": "function",
        "function": {
          "name": "get_order",
          "arguments": "{\"order_no\": \"12345\"}"
        }
      }]
    },
    "finish_reason": "tool_calls"
  }]
}
```

**你要做的三件事**：

1. 执行 `get_order(order_no="12345")`
2. 构造 `{"role": "tool", "tool_call_id": "call_abc123", "content": "<结果>"}`
3. 再次请求模型

> ⚠️ **`tool_call_id` 必须一一对应**。模型可能**一次返回多个 tool_calls**（并行调用），每个都要有对应的 `ToolMessage`，否则会报错。

### 2.3 并行工具调用

模型可以在一次回复里请求多个工具：

```json
"tool_calls": [
  {"id": "call_1", "function": {"name": "get_weather", "arguments": "{\"city\":\"北京\"}"}},
  {"id": "call_2", "function": {"name": "get_weather", "arguments": "{\"city\":\"上海\"}"}}
]
```

**你应该并发执行**，而不是串行：

```python
import asyncio

async def run_tools(tool_calls):
    tasks = [execute_one(tc) for tc in tool_calls]
    return await asyncio.gather(*tasks)
```

> 💡 并行执行能把 3 次 1 秒的调用从 3 秒降到 1 秒。**Agent 的延迟优化，很大一部分就来自这里。**

## 三、用 `@tool` 定义工具 ⭐

### 3.1 最小示例

```python
from langchain_core.tools import tool

@tool
def get_weather(city: str) -> str:
    """查询指定城市的当前天气。

    当用户询问天气、气温、是否下雨时使用此工具。
    """
    # 真实实现会调用天气 API
    return f"{city}：晴，12~20℃，西北风 3 级"
```

**`@tool` 做的事**：

1. 从**函数名**推断工具名（`get_weather`）
2. 从 **docstring** 推断描述（**这段文字会原样给模型看**）
3. 从**类型注解**生成 JSON Schema（`city: str` → `{"type": "string"}`）
4. 包装成 `BaseTool`，支持 `invoke`、`ainvoke`

```python
print(get_weather.name)          # get_weather
print(get_weather.description)   # 查询指定城市的当前天气。...
print(get_weather.args)          # {'city': {'title': 'City', 'type': 'string'}}
print(get_weather.invoke({"city": "北京"}))
```

> ⚠️ **docstring 不是注释，是给模型的 API 文档**。写得含糊，模型就会乱调或漏调。这是工具调用失败的第一大原因。

### 3.2 用 Pydantic 定义参数（推荐）

```python
from pydantic import BaseModel, Field
from typing import Literal
from langchain_core.tools import tool

class RefundInput(BaseModel):
    """退款申请的入参"""
    order_no: str = Field(description="订单号，纯数字，如 12345")
    amount: float = Field(gt=0, le=100000, description="退款金额（元），必须大于 0")
    reason: Literal["七天无理由", "质量问题", "发错货", "其他"] = Field(
        description="退款原因，只能从给定选项中选择"
    )
    remark: str | None = Field(default=None, description="补充说明，可为空")

@tool("refund_order", args_schema=RefundInput)
def refund_order(order_no: str, amount: float, reason: str, remark: str | None = None) -> dict:
    """为指定订单发起退款申请。

    只有在用户明确要求退款、且订单状态为「已完成」或「已发货」时使用。
    退款金额不得超过订单实付金额。提交后需要人工审批，不会立即到账。
    """
    return {"success": True, "refund_id": "R20261101001", "status": "待审批"}
```

**好处**：

- 参数约束（`gt`、`le`、`Literal`）会进入 schema，**模型能看到边界**
- 支持嵌套对象、列表
- 复杂工具可读性更好

> ⚠️ **`Literal` 特别有价值**：把"原因"限制成 4 个枚举，模型几乎不会输出别的值。**能枚举就枚举**，比事后校验有效得多。

### 3.3 异步工具

```python
@tool
async def search_orders(user_id: str, keyword: str) -> list[dict]:
    """按关键词搜索用户的订单列表。"""
    async with httpx.AsyncClient() as client:
        r = await client.get(f"{BASE}/orders", params={"user_id": user_id, "q": keyword})
        return r.json()
```

> 💡 **异步工具在 Agent 里价值极大**：多个工具可以真正并发执行。如果底层是 HTTP 调用，**一律写异步**。

### 3.4 工具返回什么

| 返回类型 | 效果 |
| :--- | :--- |
| `str` | 直接作为 `ToolMessage.content` |
| `dict` / `list` | 框架会序列化为 JSON 字符串 |
| `BaseModel` | 序列化为 JSON |
| `Command(...)`（LangGraph） | 高级用法：直接更新图状态（第 07 篇） |

**返回内容的原则**：

- **精简**：只返回模型需要的字段，别把整条 DB 记录塞进去（浪费 token）
- **结构化**：JSON 比一段自然语言更容易被模型理解
- **带状态码**：`{"success": false, "error": "订单不存在"}`
- **截断超长内容**：列表只返回前 20 条，并说明"共 N 条，已截断"

```python
@tool
def search_orders(keyword: str) -> str:
    """按关键词搜索订单。"""
    rows = db.query(keyword)
    if not rows:
        return "未找到相关订单"
    top = rows[:20]
    payload = [{"order_no": r.no, "status": r.status, "amount": float(r.amount)} for r in top]
    return json.dumps({
        "total": len(rows),
        "returned": len(payload),
        "truncated": len(rows) > 20,
        "items": payload,
    }, ensure_ascii=False)
```

## 四、让模型调用工具：`bind_tools`

### 4.1 绑定

```python
from langchain.chat_models import init_chat_model

model = init_chat_model("gpt-4o-mini", temperature=0)

tools = [get_weather, refund_order]
model_with_tools = model.bind_tools(tools)

resp = model_with_tools.invoke("北京今天天气怎么样？")
print(resp.tool_calls)
# [{'name': 'get_weather', 'args': {'city': '北京'}, 'id': 'call_xxx', 'type': 'tool_call'}]
```

**注意**：`resp.content` 这时候通常是空的，真正的意图在 `resp.tool_calls` 里。

### 4.2 `bind_tools` 做了什么

它把工具的定义（名称、描述、参数 schema）放进请求的 `tools` 字段，并告诉模型"你可以用这些工具"。

```python
# 等价于
model_with_tools = model.bind(
    tools=[t.tool_call_schema.model_json_schema() ... ]
)
```

> ⚠️ **`bind_tools` 返回的是新对象，不是修改原对象**：
> ```python
> mt = model.bind_tools(tools)
> model.invoke(...)      # 还是不带工具的
> mt.invoke(...)         # 带工具
> ```

### 4.3 `tool_choice`：强制/禁止调用

```python
model.bind_tools(tools, tool_choice="required")        # 必须调一个工具
model.bind_tools(tools, tool_choice="auto")            # 模型自己决定（默认）
model.bind_tools(tools, tool_choice="none")            # 禁止调用

# 强制调用指定工具
model.bind_tools(tools, tool_choice={"type": "function", "function": {"name": "get_weather"}})
```

**实际用途**：

- **意图路由**：定义一个 `classify_intent` 工具，`tool_choice="required"` 强制分类
- **第一步必须检索**：RAG 场景里强制先调检索工具

> ⚠️ **`tool_choice="required"` 不保证选的工具对**。它只保证"一定会调某一个"。要精确控制就指定工具名。

### 4.4 只绑定部分工具

**按场景动态收窄工具集**是降低误调用和成本的关键手段：

```python
ALL_TOOLS = [get_weather, search_orders, refund_order, send_email, ...]

def build_model(intent: str):
    if intent == "after_sale":
        return model.bind_tools([search_orders, refund_order])
    if intent == "general":
        return model.bind_tools([get_weather])
    return model
```

> 💡 **工具越少，模型选得越准，token 越省。** 10 个工具已是上限，30 个工具的 Agent 基本不可控。第 06 篇会讲"工具路由"。

## 五、执行循环：手写一遍才懂 ⭐⭐

框架会帮你封装，但**不手写一遍，你永远不知道出问题时该看哪里**。

### 5.1 完整实现

```python
from langchain_core.messages import HumanMessage, ToolMessage

def run_with_tools(model, tools, user_input, max_steps=6):
    """最小可用的工具调用循环"""
    tool_map = {t.name: t for t in tools}
    messages = [HumanMessage(user_input)]
    bound = model.bind_tools(tools)

    for step in range(max_steps):
        ai_msg = bound.invoke(messages)
        messages.append(ai_msg)

        # 没有工具调用 → 结束
        if not ai_msg.tool_calls:
            return ai_msg.content

        # 有工具调用 → 逐个执行
        for tc in ai_msg.tool_calls:
            tool = tool_map.get(tc["name"])
            if tool is None:
                result = f"错误：工具 {tc['name']} 不存在，可用工具：{list(tool_map)}"
            else:
                try:
                    result = tool.invoke(tc["args"])
                except Exception as e:
                    result = f"工具执行失败：{type(e).__name__}: {e}"

            messages.append(ToolMessage(
                content=str(result),
                tool_call_id=tc["id"],      # 必须对应
                name=tc["name"],
            ))

    # 超过步数上限 → 兜底
    return "抱歉，这个问题需要更多步骤处理，已转人工。"
```

### 5.2 这段代码里的每个细节都有原因

| 细节 | 为什么 |
| :--- | :--- |
| `messages.append(ai_msg)` | **必须**把带 `tool_calls` 的 AI 消息加进去，否则模型不知道自己在请求什么 |
| `tool_call_id` | 模型靠它把"我请求的"和"你返回的"对应起来 |
| `max_steps` | 防止死循环烧钱 |
| `tool is None` 分支 | 模型可能编造不存在的工具名 |
| `except` 分支 | **工具失败不能让整个流程崩**，要把错误告诉模型让它自己调整 |
| 兜底返回 | 超过步数要有明确的降级行为 |

### 5.3 把错误喂回模型，而不是直接抛异常

```python
try:
    result = tool.invoke(tc["args"])
except ValidationError as e:
    result = f"参数校验失败：{e}。请检查参数格式后重试。"
except PermissionError as e:
    result = f"权限不足：{e}。请提示用户联系管理员。"
except TimeoutError:
    result = "服务超时，请稍后重试或换一种方式查询。"
```

> 💡 **这是 Agent 比传统程序"聪明"的地方**：传统程序抛异常就挂了，Agent 能看到错误信息并**自己调整参数重试**。但前提是**你给了它清晰的错误描述**。

> ⚠️ **不要把所有异常都 `except Exception` 吞掉**。权限错误、参数错误应该抛给上层做审计；只有"模型可以自己修正"的错误才喂回去。

### 5.4 用框架的现成实现

LangChain 1.x 提供了 `create_agent`，把这个循环封装好了：

```python
from langchain.agents import create_agent

agent = create_agent(
    model=model,
    tools=[get_weather, search_orders],
    system_prompt="你是一个订单助手，回答简洁。",
)

result = agent.invoke({"messages": [("user", "北京天气怎么样？")]})
print(result["messages"][-1].content)
```

> 💡 **第 06 篇会详细讲 `create_agent`**。这里先手写循环，是为了让你能"拆开黑盒看"。

### 5.5 一个常见的 bug：忘记加 AIMessage

```python
# ❌ 错误
if ai_msg.tool_calls:
    for tc in ai_msg.tool_calls:
        messages.append(ToolMessage(...))
    # 忘了 append(ai_msg)

# 结果：模型报错 "tool_call_id not found" 或行为诡异
```

**正确的消息序列**：

```text
HumanMessage
AIMessage(tool_calls=[...])     ← 必须有
ToolMessage(tool_call_id=...)   ← 对应上一条
AIMessage(最终回答)
```

## 六、工具设计原则（决定成败）⭐⭐

**Agent 的效果，70% 取决于工具设计，30% 取决于模型和 Prompt。**

### 6.1 单一职责

```python
# ❌ 一个万能工具
@tool
def handle_order(action: str, order_no: str, reason: str = "", amount: float = 0):
    """处理订单相关操作。"""
    ...

# ✅ 拆成明确的工具
@tool
def get_order_detail(order_no: str) -> dict:
    """查询订单详情：状态、金额、商品、物流。当用户问"订单怎么样了"时使用。"""

@tool
def cancel_order(order_no: str, reason: str) -> dict:
    """取消订单。仅在订单状态为「待发货」时可用。"""
```

> ⚠️ **万能工具会让模型频繁传错参数**。`action` 字段是典型的反模式——模型不知道该传什么。

### 6.2 描述要写"什么时候用"，不只是"是什么"

```python
# ❌ 太简略
@tool
def search(query: str) -> str:
    """搜索。"""

# ✅ 完整
@tool
def search_knowledge_base(query: str) -> str:
    """在企业知识库中检索文档片段。

    适用于：产品使用说明、售后政策、常见问题、内部流程。
    不适用于：订单状态、物流信息（请用 get_order_detail）、
             实时价格（请用 get_price）。

    Args:
        query: 检索关键词，尽量使用用户原话中的名词短语，如「退货政策」「发票开具」。
    """
```

**描述里应该包含**：

1. **功能**：这个工具做什么
2. **触发条件**：什么情况下该用
3. **排除条件**：什么情况下**不该**用（防误调）
4. **参数说明**：格式、示例、边界
5. **副作用**：是否写数据、是否发通知

### 6.3 参数尽量少、尽量简单

| 反模式 | 问题 | 改进 |
| :--- | :--- | :--- |
| 20 个参数的巨型工具 | 模型漏填/填错 | 拆分工具，或把非必需参数设为可选 |
| 嵌套三层的对象 | 模型生成错误率飙升 | 扁平化 |
| 需要模型自己算的 ID | 容易编造 | 由上下文/代码提供，不让模型生成 |
| 自由文本枚举 | 值不可控 | 用 `Literal` |

> ⚠️ **不要让模型生成主键 ID、时间戳、用户 ID 这类"系统才知道"的参数**。它们应该由代码注入（从上下文、认证信息里取），而不是让模型猜。

### 6.4 幂等与副作用标注

```python
@tool
def create_ticket(title: str, content: str, idempotency_key: str) -> dict:
    """创建工单。

    注意：这是写操作，重复调用会创建多张工单。
    服务器会用 idempotency_key 去重，请使用「用户ID+问题摘要」作为 key。
    """
```

> 💡 **幂等键由谁生成？** 最好由**代码**生成并注入，而不是让模型生成。模型生成的 key 每次都不一样，幂等就失效了。

```python
# 更好的做法：在工具内部用上下文里的 key
@tool
def create_ticket(title: str, content: str, config: RunnableConfig) -> dict:
    """创建工单。"""
    user_id = config["configurable"]["user_id"]
    trace_id = config["configurable"]["trace_id"]
    key = f"{user_id}:{hashlib.md5(content.encode()).hexdigest()[:12]}"
    ...
```

### 6.5 返回结果要"模型友好"

```python
# ❌ 返回整条记录
return student_model.to_dict()   # 50 个字段，大部分模型用不上

# ✅ 只返回需要的
return {
    "name": s.name,
    "class": s.class_name,

    "rank": s.rank,

```

```python
# ❌ 返回 XML/HTML 或带大量空白

# ✅ JSON

```

> 💡 **中文一定要 `ensure_ascii=False`**。否则返回的是 `中文`，模型要额外解码，容易出错且更费 token。

### 6.6 工具数量控制

| 工具数 | 效果 |
| :--- | :--- |
| 1–5 | 准确率最高 |
| 5–10 | 可用，需要清晰描述 |
| 10–20 | 开始误调，需要按场景分组 |
| >20 | 基本不可控，必须做工具路由 |

```text

只绑定该意图下的 3–5 个工具

```

## 七、错误处理与安全边界 ⭐⭐

### 7.1 三层防护

```text
第 1 层：模型不该调（Prompt 约束 + 工具描述排除条件）
第 2 层：模型调了但参数不对（Pydantic 校验）
第 3 层：参数对但没权限（业务鉴权）  ← 唯一可靠的一层
```

> ⚠️ **永远不要只靠 Prompt 约束安全**。用户可以通过注入让模型调用任何工具。**权限判断必须在代码里，基于当前登录用户，而不是基于模型的输入。**

### 7.2 参数校验（第 2 层）

```python
@tool("refund_order", args_schema=RefundInput)
def refund_order(order_no: str, amount: float, reason: str, remark: str | None = None) -> dict:
    """发起退款。"""
    # Pydantic 已经校验过类型和范围；这里做业务校验
    ...
```

**Pydantic 能拦住**：类型错误、范围越界、枚举外值
**Pydantic 拦不住**：订单号不存在、金额超过实付、状态不允许退款

### 7.3 业务鉴权（第 3 层，最重要）

```python
from langchain_core.runnables import RunnableConfig

@tool
def get_order_detail(order_no: str, config: RunnableConfig) -> dict:
    """查询订单详情。"""
    user_id = config["configurable"]["user_id"]     # 来自认证，不来自模型

    order = order_repo.find_by_no(order_no)
    if order is None:
        return {"success": False, "error": "订单不存在"}

    if order.user_id != user_id:                    # 关键：越权检查
        logger.warning(f"越权查询: user={user_id} order={order_no}")
        return {"success": False, "error": "无权查看该订单"}

    return {"success": True, "order": to_vo(order)}
```

> ⚠️ **模型完全可能生成别人的订单号**（用户诱导："帮我查一下订单 99999"）。**如果这里不做校验，就是数据泄露事故。** 这是 AI 应用里最常见的线上安全问题。

## 八、参数校验与 Pydantic 模型

### 8.1 常用约束

```python
from pydantic import BaseModel, Field, field_validator
from typing import Literal
from datetime import date

class OrderQuery(BaseModel):
    order_no: str = Field(pattern=r"^\d{5,20}$", description="订单号，纯数字")
    user_id: str = Field(min_length=1, description="用户ID")
    start_date: date | None = Field(default=None, description="开始日期，格式 YYYY-MM-DD")
    end_date: date | None = Field(default=None, description="结束日期")
    status: Literal["待付款", "待发货", "已发货", "已完成", "已取消"] | None = None
    page: int = Field(default=1, ge=1, le=100, description="页码，从 1 开始")
    size: int = Field(default=20, ge=1, le=100, description="每页条数，最大 100")

    @field_validator("end_date")
    @classmethod
    def check_date_range(cls, v, info):
        start = info.data.get("start_date")
        if v and start and v < start:
            raise ValueError("结束日期不能早于开始日期")
        return v
```

> ⚠️ **`pattern` 里的正则要简单**。复杂的正则会出现在 schema 描述里，模型不一定能理解，反而可能被吓到不敢传参。

### 8.2 可选参数与默认值

```python
class SearchInput(BaseModel):
    keyword: str = Field(description="搜索关键词")
    limit: int = Field(default=10, description="返回条数，默认 10")
```

**给模型默认值的好处**：它可以只传必填项，减少出错。

### 8.3 模型的"参数幻觉"

模型会：

- 编造不存在的字段
- 把数字传成字符串（`"123"` vs `123`）
- 漏掉必填字段
- 传枚举之外的值

**Pydantic 会自动转换一部分**（`"123"` → `123` 在 `coerce` 模式下），但**不要依赖**。**用 `Strict` 模式更安全**：

```python
from pydantic import BaseModel, ConfigDict

class StrictInput(BaseModel):
    model_config = ConfigDict(strict=True)   # 不允许类型强转
```

> ⚠️ `strict=True` 会让模型偶尔的参数类型错误直接失败。**实战建议**：对**金额、ID** 这类关键字段用严格模式，其他字段允许宽松（配合校验重试）。

### 9.3 流式 + 结构化

前面说过流式 JSON 不完整。**两种实用方案**：

**方案 A：先自然语言流式，再结构化**

```python
# 第一段：流式给用户看
for chunk in model.stream(f"用通俗语言解释这段错误日志：\n{log}"):
    yield chunk.content

# 第二段：后台结构化（不流式）
data = model.with_structured_output(LogAnalysis).invoke(log)
```

**方案 B：把结构化拆成"字段级"**

让模型按行输出 `key: value`，前端边收边渲染。适合简单的表单填充。

### 9.4 结构化输出的失败处理

```python
def structured_invoke(schema, text, retries=2):
    for i in range(retries + 1):
        try:
            res = model.with_structured_output(schema, include_raw=True).invoke(text)
            if res["parsed"] is not None:
                return res["parsed"]
            # 解析失败：把错误反馈回去
            text = f"{text}\n\n上一次输出无法解析：{res['parsing_error']}\n请严格按 schema 输出。"
        except Exception as e:
            if i == retries:
                raise
    raise ValueError("结构化输出失败")
```

> ⚠️ **生产上一定要有兜底**：解析失败时返回一个"降级对象"（如 `{"status": "parse_failed"}`），而不是让整个接口 500。

## 十、实战：把现有 Spring 接口变成工具

### 10.1 场景

假设你有一个 Java 后端，已经提供了：

```http
GET  /api/orders/{orderNo}          查询订单
POST /api/orders/{orderNo}/refund   申请退款
GET  /api/tickets?keyword=xxx       查工单
```

现在要让 AI 助手能调用它们。

### 10.2 步骤一：定义返回契约

**先和后端约定"模型友好的返回格式"**。不要直接把内部 DTO 暴露给模型：

```json
{
  "success": true,
  "data": {
    "order_no": "12345",
    "status": "已发货",
    "amount": 299.00,
    "items": [{"name": "机械键盘", "qty": 1}],
    "can_refund": true
  }
}
```

### 10.3 步骤二：写工具

```python
import httpx, os
from langchain_core.tools import tool
from langchain_core.runnables import RunnableConfig

BASE = os.getenv("JAVA_API_BASE", "http://localhost:8080/api")
TIMEOUT = 10.0

@tool
async def get_order_detail(order_no: str, config: RunnableConfig) -> dict:
    """查询订单详情：状态、金额、商品清单、是否可以退款。

    当用户询问订单进度、物流、金额、能否退款时使用此工具。
    不适用于查询历史订单列表（请用 search_orders）。
    """
    user_id = config["configurable"]["user_id"]
    async with httpx.AsyncClient(timeout=TIMEOUT) as client:
        try:
            r = await client.get(
                f"{BASE}/orders/{order_no}",
                headers={"X-User-Id": user_id},       # 透传身份
            )
        except httpx.TimeoutException:
            return {"success": False, "error": "订单服务超时，请稍后重试"}

    if r.status_code == 404:
        return {"success": False, "error": f"订单 {order_no} 不存在"}
    if r.status_code == 403:
        return {"success": False, "error": "无权查看该订单"}
    if r.status_code != 200:
        return {"success": False, "error": f"订单服务异常（{r.status_code}）"}

    d = r.json()
    return {
        "success": True,
        "order_no": d["orderNo"],
        "status": d["status"],
        "amount": d["amount"],
        "can_refund": d["status"] in ("已发货", "已完成"),
        "items": [{"name": i["name"], "qty": i["qty"]} for i in d["items"]],
    }


@tool
async def apply_refund(order_no: str, amount: float, reason: str,
                       config: RunnableConfig) -> dict:
    """为订单申请退款（写操作，会创建退款单并进入审批流程）。

    仅当用户明确要求退款、且 get_order_detail 返回 can_refund=true 时调用。
    退款不会立即到账，需要人工审批。
    """
    user_id = config["configurable"]["user_id"]
    if amount <= 0:
        return {"success": False, "error": "退款金额必须大于 0"}

    async with httpx.AsyncClient(timeout=TIMEOUT) as client:
        r = await client.post(
            f"{BASE}/orders/{order_no}/refund",
            json={"amount": amount, "reason": reason},
            headers={
                "X-User-Id": user_id,
                "Idempotency-Key": f"{user_id}:{order_no}:{amount}",   # 幂等
            },
        )

    if r.status_code == 409:
        return {"success": False, "error": "该订单已有进行中的退款申请"}
    if r.status_code != 200:
        return {"success": False, "error": f"退款申请失败（{r.status_code}）"}

    d = r.json()
    return {"success": True, "refund_id": d["refundId"], "status": "待审批"}
```

### 10.4 步骤三：组装 Agent 并接入认证信息

```python
from langchain.agents import create_agent

agent = create_agent(
    model=model,
    tools=[get_order_detail, apply_refund],
    system_prompt=(
        "你是售后助手。\n"
        "1. 涉及退款时，必须先调用 get_order_detail 确认 can_refund=true。\n"
        "2. 退款金额由用户输入，不要自行计算或修改。\n"
        "3. 只能查询当前用户自己的订单。\n"
        "4. 不确定时请询问用户，不要猜测。"
    ),
)


def handle(user_id: str, session_id: str, message: str):
    return agent.invoke(
        {"messages": [("user", message)]},
        config={
            "configurable": {
                "user_id": user_id,          # 工具从这里读身份
                "thread_id": session_id,
            }
        },
    )
```

### 10.5 步骤四：Java 侧要配合的三件事

| 事项 | 说明 |
| :--- | :--- |
| **身份透传** | 用 `X-User-Id` 或 JWT 透传，**不要信任请求体里的 user_id** |
| **幂等键** | 写接口支持 `Idempotency-Key`，防止 Agent 重试导致重复退款 |
| **错误语义化** | 返回 `{"code": "ORDER_NOT_REFUNDABLE", "msg": "..."}`，便于模型理解并转述给用户 |

> 💡 **模型不擅长解析 HTTP 状态码**。把 4xx 转成明确的 `error` 字段，模型才能把"不能退款"友好地告诉用户。

## 十一、工具调用的成本与延迟

### 11.1 成本构成

```text
一次工具调用轮次 =
    输入 token（系统提示 + 历史 + 工具定义 + 上一轮工具结果）
  + 输出 token（tool_calls JSON）
  + 下一轮的输入（又多了工具结果）
```

**工具定义的开销容易被忽略**：

| 工具数 | 每次请求额外 token（约） |
| :--- | :--- |
| 3 | 300–600 |
| 10 | 1000–2000 |
| 30 | 3000–6000 |

**Agent 循环 5 轮 → 工具定义被重复计费 5 次。**

### 11.2 延迟构成

```text
总延迟 = Σ (模型思考时间 + 工具执行时间 + 网络往返)
```

| 优化点 | 手段 |
| :--- | :--- |
| 减少轮次 | 工具描述清楚、一次能查到的不要分两次 |
| 并行工具调用 | `asyncio.gather` |
| 工具本身快 | 加缓存、走内网、减少返回体积 |
| 流式反馈 | 让用户看到"正在查询…"，感知延迟下降 |

### 11.3 监控指标

```python
metrics = {
    "tool_call_count": 0,         # 每会话的工具调用次数
    "tool_error_rate": 0.0,       # 工具失败率
    "avg_steps": 0.0,             # 平均循环轮数
    "p99_latency_ms": 0,
    "token_per_session": 0,
}
```

> ⚠️ **`avg_steps` 突然上升**通常意味着：工具描述变差、模型换版本、或出现了新的问题类型。这是一个很好的**早期预警指标**。

## 十二、踩坑清单

| # | 坑 | 现象 | 解决 |
| :--- | :--- | :--- | :--- |
| 1 | docstring 写得太简略 | 模型不调或乱调工具 | 写清触发条件和排除条件 |
| 2 | 忘记 append AIMessage | `tool_call_id` 对不上 / 行为异常 | 按 5.1 的顺序构造消息 |
| 3 | `tool_call_id` 不匹配 | 400 错误 | 用 `tc["id"]` 原样传 |
| 4 | 工具异常直接抛出 | 整个请求 500 | `try/except` 转成错误字符串喂回模型 |
| 5 | 工具返回超长列表 | token 爆炸、模型抓不住重点 | 截断 + 说明总数 |
| 6 | 中文未 `ensure_ascii=False` | 返回 `\uXXXX`，模型理解变差 | 显式设置 |
| 7 | 模型编造工具名 | `Tool not found` | 显式检查并返回可用工具列表 |
| 8 | 忘记步数上限 | 死循环烧钱 | `max_steps` |
| 9 | 信任模型传的 user_id | 越权访问 | 从 `config` 取认证身份 |
| 10 | 写操作无幂等键 | 重试导致重复下单 | `Idempotency-Key` |
| 11 | 工具数过多 | 误调用、token 高 | 按意图分组绑定 |
| 12 | 用自由文本做枚举 | 值不可控 | `Literal` |
| 13 | 工具名与业务术语不一致 | 模型理解偏差 | 用业务语言命名 |
| 14 | 同步工具在异步 Agent 中 | 并发失效 | 用 `async def` |
| 15 | 并行 tool_calls 串行执行 | 延迟翻倍 | `asyncio.gather` |
| 16 | 工具返回内部异常栈 | 泄露实现细节、模型困惑 | 返回语义化错误 |
| 17 | 没有审计日志 | 出问题无法溯源 | 记录完整调用 |
| 18 | `bind_tools` 结果被丢弃 | 工具没生效 | 使用返回的新对象 |

## 十三、本章小结与练习

### 核心结论

1. **工具调用的本质是"模型输出调用意图，代码负责执行"**，执行权和安全边界都在你这边。
2. **完整协议四步**：请求带 tools → 模型返回 `tool_calls` → 执行并构造 `ToolMessage` → 再次请求。
3. **`@tool` 的 docstring 就是给模型的 API 文档**，写清"何时用、何时不用"。
4. **手写一遍循环**，你才知道出问题时该查消息序列、参数、还是工具实现。
5. **工具设计决定 Agent 效果**：单一职责、描述完整、参数简单、返回精简、数量可控。
6. **三层防护**：Prompt 约束 → Pydantic 校验 → 业务鉴权。**只有第三层可靠**。
7. **写操作必须有幂等、确认和审计**。
8. **成本和延迟随轮次线性增长**，工具定义会重复计费。

### 动手练习

1. 写一个 `get_weather` 工具，用 `@tool` 和 Pydantic 两种方式各实现一次，对比生成的 schema。
2. 手写一个完整的工具调用循环（不看 5.1），支持最多 5 轮、工具异常捕获、步数超限兜底。
3. 设计三个工具：`search_orders`（查列表）、`get_order_detail`（查详情）、`apply_refund`（退款）。给每个写完整的 docstring（含触发/排除条件）。
