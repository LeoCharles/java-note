## 一、把大模型当成一个"奇怪的远端服务"

### 1.1 它就是一个 HTTP 接口

抛开所有玄学，你调用大模型的方式就是发一个 HTTP 请求：

```http
POST https://api.openai.com/v1/chat/completions
Authorization: Bearer sk-xxx
Content-Type: application/json

{
  "model": "gpt-4o-mini",
  "messages": [
    {"role": "system", "content": "你是一个专业的 Java 技术顾问"},
    {"role": "user", "content": "解释一下 Spring 的 IoC"}
  ],
  "temperature": 0.7
}
```

返回：

```json
{
  "id": "chatcmpl-xxx",
  "choices": [
    {
      "index": 0,
      "message": {
        "role": "assistant",
        "content": "Spring 的 IoC（控制反转）是一种设计原则……"
      },
      "finish_reason": "stop"
    }
  ],
  "usage": {
    "prompt_tokens": 35,
    "completion_tokens": 420,
    "total_tokens": 455
  }
}
```

**就这么简单。** 你可以用 `OkHttp`、`Retrofit`、`WebClient` 在任何语言里调用它。LangChain 做的事情，本质上就是把这层 HTTP 调用**封装得更好用**（多模型统一、重试、流式解析、工具调用协议、链式组合）。

> 💡 **第一个认知转变**：不要把它想成"AI"，先把它想成**一个返回文本的第三方 API**——慢、贵、不确定、偶尔胡说，但很强大。这个视角能帮你避开绝大多数工程上的坑。

### 1.2 与普通 API 的六个关键区别

| 维度 | 普通 REST API | 大模型 API |
| :--- | :--- | :--- |
| **确定性** | 同样输入 → 同样输出 | 同样输入 → **可能不同输出** |
| **正确性** | 正确或报错 | 总会返回一段"看起来对"的话，**可能完全是编的** |
| **延迟** | 几十毫秒 | **秒级**，长回答可能 10–60 秒 |
| **计费** | 按调用次数 | 按 **token 数**，且输入输出单价不同 |
| **状态** | 你可能依赖 session | **完全无状态**，服务端不记得你上次说了什么 |
| **可测试性** | 断言返回码和字段 | **无法精确断言文本内容** |

这六条直接推导出后面所有工程手段：

- 不确定 → 要设 `temperature=0` + 结构化输出 + 校验重试
- 会编造 → 要 RAG + 引用溯源 + 兜底话术
- 慢 → 要流式输出 + 超时 + 异步
- 按 token 计费 → 要压缩上下文 + 缓存 + 预算控制
- 无状态 → 要自己管理会话（第 05 篇）
- 难测试 → 要评测集而不是单元测试（第 10 篇）

### 1.3 一个最小的 Python 调用

```python
import os
from openai import OpenAI

client = OpenAI(
    api_key=os.getenv("OPENAI_API_KEY"),
    base_url=os.getenv("OPENAI_BASE_URL"),   # 兼容 OpenAI 协议的服务都能用
)

resp = client.chat.completions.create(
    model="gpt-4o-mini",
    messages=[
        {"role": "system", "content": "你是一个简洁的技术顾问，回答不超过 100 字。"},
        {"role": "user", "content": "什么是 IoC？"},
    ],
    temperature=0,
)

print(resp.choices[0].message.content)
print(resp.usage)          # 计费依据
```

> ⚠️ **`base_url` 是兼容性的关键**。国内绝大多数模型服务（DeepSeek、通义、豆包、Kimi、公司网关）都提供 OpenAI 兼容端点，改一个 URL 就能切换，这也是后面 LangChain "统一入口"能成立的原因。

## 二、Token：模型世界的计量单位

### 2.1 什么是 Token

模型不直接处理"字"或"单词"，而是先把文本切成 **token**（词元）。一个 token 大致是：

- 英文：约 **0.75 个单词**（`"hello world"` → 2 个 token）
- 中文：约 **1 个汉字 ≈ 1–2 个 token**（取决于模型的分词器）
- 代码：通常比自然语言更"费" token

```python
# 用 tiktoken 估算（OpenAI 模型）
import tiktoken

enc = tiktoken.get_encoding("cl100k_base")
text = "Spring 的 IoC 容器负责管理 Bean 的生命周期"
print(len(enc.encode(text)))        # 约 18 个 token
```

不同模型的分词器不同，**不要用 A 模型的 token 数去算 B 模型的成本**。

### 2.2 为什么必须懂 Token

| 场景 | 为什么和 token 有关 |
| :--- | :--- |
| **成本** | 输入输出都按 token 计费，长 Prompt 直接等于钱 |
| **长度限制** | 上下文窗口按 token 算，超了直接报错 |
| **延迟** | 输出 token 越多越慢（自回归逐个生成） |
| **截断** | 塞太多历史，最早的对话会被挤掉 |

**一个量级感**：

| 内容 | 约多少 token |
| :--- | :--- |
| 一句普通中文 | 20–40 |
| 一篇公众号文章（2000 字） | 2000–3000 |
| 一个 Java 类（200 行） | 1500–2500 |
| 一本 20 万字的技术书 | 30 万+ |

> ⚠️ **实战中最容易忽略的**：**工具定义本身也占 token**。你给 Agent 注册 30 个工具的完整 schema，可能一次就吃掉 3000–5000 token，而且**每次调用都要重新传**。工具过多是 Agent 成本和延迟飙升的隐性原因（第 06 篇会讲怎么控制）。

### 2.3 成本估算的简单方法

```text
单次成本 = prompt_tokens × 输入单价 + completion_tokens × 输出单价
```

以某模型为例（价格仅示意，以官方为准）：

| 项目 | 单价（每百万 token） | 一次典型请求 |
| :--- | :--- | :--- |
| 输入 | $0.15 | 3000 token → $0.00045 |
| 输出 | $0.60 | 500 token → $0.0003 |

单次不到 0.1 美分，看起来便宜。但**乘以日活和轮次**：

```text
日均 1 万用户 × 每人 5 轮 × 每轮 0.0008 美元 ≈ 每天 40 美元 ≈ 每月 1200 美元
```

如果对话变长、带了 10 篇 RAG 文档、又接了 Agent 反复调用工具，**成本可能翻 10 倍**。

> 💡 **工程上的三个抓手**：① 缩短系统提示（别写 3000 字人设）；② 控制历史长度（滑动窗口/摘要）；③ **缓存命中**（很多服务商对相同前缀的输入有折扣）。

## 三、上下文窗口：一次请求的上限

### 3.1 概念

**上下文窗口（context window）** = 模型单次能"看到"的最大 token 总数，包含：

```text
系统提示 + 历史对话 + 本轮用户输入 + 检索到的资料 + 工具定义 + 模型输出
```

常见量级：8K、32K、128K、200K，部分模型到 1M+。

> ⚠️ **"支持 128K"不等于"128K 都好用"**。模型对超长上下文的**中间部分**关注度会下降（业界称 "lost in the middle"）。**把关键信息放在开头或结尾，比堆长度有效得多。**

### 3.2 超了会怎样

| 情况 | 结果 |
| :--- | :--- |
| 请求 token > 模型上限 | 直接返回 400 错误（不同厂商文案不同） |
| 输出超过 `max_tokens` | 被截断，`finish_reason` 为 `length` |

```python
resp = client.chat.completions.create(
    model="gpt-4o-mini",
    messages=messages,
    max_tokens=500,          # 限制输出长度（也要花钱）
)
if resp.choices[0].finish_reason == "length":
    print("输出被截断了，可能需要更大 max_tokens 或让模型分段回答")
```

### 3.3 超出时怎么办（四种策略）

| 策略 | 做法 | 适用 | 代价 |
| :--- | :--- | :--- | :--- |
| **滑动窗口** | 只保留最近 N 轮 | 闲聊、客服 | 丢失早期信息 |
| **摘要压缩** | 把旧对话总结成一段 | 长会话 | 有信息损失、多一次调用 |
| **检索式记忆** | 历史存库，按相关性召回 | 长期助教、个人助理 | 架构复杂 |
| **分块处理** | 长文档切块分别处理再汇总（Map-Reduce） | 长文总结、批量分析 | 调用次数多 |

> 💡 **给后端程序员的类比**：上下文窗口就像**一次请求的 payload 大小限制**。你不会把所有数据都塞进一个请求，而是分页/筛选——**对待上下文要同样克制**。

第 05 篇会把"记忆管理"完整展开。

### 3.4 一个实用的 token 预算表

设计一个功能时，先算预算：

```text
模型上限 128000
 ├─ 系统提示               1500
 ├─ 工具定义（10 个工具）   3000
 ├─ 检索资料（5 段）        6000
 ├─ 历史对话（10 轮）       4000
 ├─ 本轮用户输入            500
 ├─ 预留输出                4000
 └─ 余量                    ~115000  ← 看起来很充裕？实际很快就用光
```

> ⚠️ **真实项目里，RAG 的检索片段和工具定义是最容易失控的两块**。一个"贴心的"检索策略把 top_k 设成 20，每段 800 token，一次就是 16000 token，还没算历史。

## 四、模型是怎么"说话"的：下一个 token 预测

### 4.1 一个极其重要的简化模型

抛开神经网络细节，大模型做的事情就一件：

> **给定前面所有的 token，预测下一个 token 的概率分布，选一个出来，然后重复。**

```text
输入: "Spring 的 IoC 是"
预测: {"一种": 0.42, "一个": 0.21, "指": 0.15, ...}
选中: "一种"
输入: "Spring 的 IoC 是一种"
预测: {"设计": 0.55, "思想": 0.18, ...}
...
```

这解释了几乎所有的"怪异行为"：

| 现象 | 原因 |
| :--- | :--- |
| 为什么它会"编造"？ | 它只是在生成"**看起来最像**接下来该说的话"，不负责验证真假 |
| 为什么数字算不对？ | 逐 token 生成，不是真的在做算术；大数乘法尤其容易错 |
| 为什么同样的输入结果不同？ | 每次都在概率分布里**采样**，除非把温度设为 0 |
| 为什么它会"顺着你说"？ | 上下文里你表达了倾向，它就接着往那个方向生成 |
| 为什么它不知道昨天的事？ | 训练数据有截止日期，模型本身不联网 |

> 💡 **一句话**：**它是个极其强大的"文本接龙器"，不是"知识库"，更不是"计算器"。** 你的工程任务，就是**给它接上知识库和计算器**。

### 4.2 由此推导出的四条工程原则

| 原则 | 原因 | 落地手段 |
| :--- | :--- | :--- |
| **别让它"算"，让它"调"** | 算术不可靠 | 金额/统计交给代码或工具（第 03 篇） |
| **别让它"记"，给它"看"** | 模型无记忆 | RAG（第 04 篇）、显式拼接历史（第 05 篇） |
| **别让它"猜"，给它"约束"** | 会自由发挥 | 结构化输出、枚举、校验重试（第 03 篇） |
| **别信它"说"，验证它"做"** | 会说谎 | 工具执行结果以系统为准，不让模型编造执行结果（第 06 篇） |

## 五、Prompt：你以为的指令 vs 它的实际输入

### 5.1 三种角色

OpenAI 协议里，`messages` 有三种 `role`：

| role | 作用 | 谁写 |
| :--- | :--- | :--- |
| `system` | 设定身份、规则、输出格式 | 开发者 |
| `user` | 用户输入 | 用户 |
| `assistant` | 模型之前的回复（也用来"教"它格式） | 模型 / 开发者预设 |

```python
messages = [
    {"role": "system", "content": "你是一个 Java 面试官，每次只问一个问题。"},
    {"role": "user", "content": "开始吧"},
    {"role": "assistant", "content": "请解释一下 HashMap 的扩容机制。"},
    {"role": "user", "content": "当元素数量超过阈值时扩容为原来的两倍……"},
]
```

> 💡 **`assistant` 消息可以用来"预填"**：在最后放一条 `assistant` 消息，模型会**接着它往下写**。这在强制输出格式时非常好用（第 03 篇会详细讲）。

### 5.2 模型看到的"全部内容"远不止你的问题

一次实际请求里，模型看到的是：

```text
[system] 你是一个客服助手，只能回答订单相关问题……
[user]   我要退货
[assistant] 好的，请提供订单号。
[user]   12345
[system/tool] 工具返回：{"status":"已发货","canRefund":true}
[user]   那就退了吧
```

**你写的"Prompt"只是其中一小部分。** 很多"模型怎么突然不听话了"的问题，是因为：

- 工具返回了超长/无关的内容，把指令冲淡了
- 历史对话里有互相矛盾的要求
- 检索到的文档内容里含有"忽略以上指令"这类恶意文本（**Prompt 注入**，第 10 篇）

### 5.3 Prompt 的基本结构

一个比较稳的结构（不是唯一真理，但好用）：

```text
# 角色
你是 XX 公司的售后客服助手。

# 任务
根据用户问题和检索到的知识库内容给出答复。

# 约束
1. 只回答与售后相关的问题，其他问题礼貌拒绝并转人工。
2. 必须基于提供的资料回答，资料中没有的内容说"我不确定"。
3. 涉及退款金额时，必须调用 refund_calculator 工具，不得自己计算。
4. 输出使用简体中文，不超过 200 字。

# 输出格式
{"answer": "...", "need_human": true/false, "citations": ["文档ID"]}

# 参考资料
{retrieved_docs}
```

**四个要点**：

1. **角色 + 任务**要具体，别写"你是一个有用的助手"
2. **约束**要可执行、可判定（"回答要专业"无法判定，"不超过 200 字"可以）
3. **输出格式**能结构化就结构化
4. **动态内容**（资料、历史）放在最后，且用明确分隔符包起来

### 5.4 几个高性价比的 Prompt 技巧

| 技巧 | 说明 | 例子 |
| :--- | :--- | :--- |
| **给例子（Few-shot）** | 比描述规则有效得多 | 给 2–3 个"输入→期望输出" |
| **指定思考步骤** | 让模型先列要点再回答 | "先列出涉及的条款，再给出结论" |
| **明确拒答条件** | 减少幻觉 | "如果资料中没有，直接回答'未找到相关信息'" |
| **分隔符隔离数据** | 防注入、防混淆 | `<docs>...</docs>` |
| **角色 + 反向约束** | 同时说"要做什么"和"不要做什么" | "不要使用 Markdown；不要编造链接" |

> ⚠️ **Prompt 不是越"礼貌"越好**。"请你尽量、麻烦你最好能……"这种模糊措辞会让约束失效。**写成明确的规则和判定条件。**

### 5.5 Prompt 会腐化，必须配评测

同一个 Prompt：

- 今天在 GPT-4o-mini 上效果好
- 换成另一个模型可能变差
- 服务商升级模型版本后可能变化
- 你"优化"了一句，别处又坏了

> 💡 **所以第 10 篇一定要做评测集**：一组带标准答案的问题，每次改 Prompt 跑一遍打分。**没有评测的 Prompt 调优 = 赌博。**

## 六、温度、Top-P 与"不确定性"

### 6.1 温度（temperature）

温度控制**采样时的随机性**：

| 温度 | 行为 | 适用 |
| :--- | :--- | :--- |
| `0` | 几乎总是选概率最高的 token | 抽取、分类、代码、结构化输出 |
| `0.3–0.7` | 有一定变化 | 一般对话 |
| `0.9–1.2` | 更发散 | 创意写作、头脑风暴 |

```python
# 要稳定、可复现 → 低温
extractor = ChatOpenAI(model="gpt-4o-mini", temperature=0)

# 要创意 → 高温
writer = ChatOpenAI(model="gpt-4o-mini", temperature=0.9)
```

> ⚠️ **`temperature=0` 也不保证 100% 一致**。原因包括：浮点计算、服务端批处理、模型版本更新、混合专家路由等。**不要把"输出完全一致"写进测试断言**，应该断言"结构合法""包含关键字段""语义等价"。

### 6.2 Top-P（核采样）

只在累计概率达到 P 的候选里采样。一般**只调一个**：要么调温度，要么调 top_p，不要同时乱调。

```python
ChatOpenAI(model="gpt-4o-mini", top_p=0.9, temperature=0.7)
```

### 6.3 其他常用参数

| 参数 | 作用 | 建议 |
| :--- | :--- | :--- |
| `max_tokens` | 限制输出长度 | **必须设置**，防止异常长输出烧钱 |
| `timeout` | 请求超时 | 30–60s，配合流式使用 |
| `max_retries` | 自动重试次数 | 2–3 次，注意幂等 |
| `stop` | 遇到指定字符串停止 | 少用，容易误截断 |
| `seed` | 请求可复现（部分模型支持） | 调试时有用，不保证跨版本 |

## 七、模型不会执行动作：Function Calling 的真面目

### 7.1 一个必须澄清的误解

很多人以为：**"模型能调用工具，所以它能执行代码。"** —— 错。

**模型能做的只有一件：输出一段结构化的"我想调用这个函数，参数是这些"的 JSON。真正执行的是你的代码。**

```text
用户: "北京今天天气怎么样？"

模型输出:
{
  "name": "get_weather",
  "arguments": {"city": "北京"}
}

你的代码:
  → 解析这个 JSON
  → 检查 city 参数
  → 调用真实的天气 API
  → 把结果作为一条 tool 消息塞回给模型

模型输出:
  "北京今天晴，气温 12-20 度。"
```

### 7.2 为什么这个设计很重要

| 含义 | 说明 |
| :--- | :--- |
| **权限在你手里** | 你可以拒绝、可以二次校验、可以要求审批 |
| **执行结果由你提供** | 模型编造"已下单"时，你可以用真实工具结果纠正它 |
| **可以做审计** | 每次工具调用都能记录：谁、什么时候、参数是什么 |
| **可以 Mock** | 测试时把工具换成假的，模型逻辑仍可验证 |

> ⚠️ **反过来，这也是最大的安全风险点**：如果模型被 Prompt 注入诱导去调用 `delete_user`，而你的代码无脑执行——**出事的是你的系统，不是模型。** 第 10 篇会讲权限边界。

### 7.3 一个最小示例

```python
tools = [{
    "type": "function",
    "function": {
        "name": "get_weather",
        "description": "查询指定城市的当前天气",
        "parameters": {
            "type": "object",
            "properties": {
                "city": {"type": "string", "description": "城市名，如 北京"}
            },
            "required": ["city"],
        },
    },
}]

resp = client.chat.completions.create(
    model="gpt-4o-mini",
    messages=[{"role": "user", "content": "北京天气怎么样"}],
    tools=tools,
)

msg = resp.choices[0].message
print(msg.tool_calls)   # [ChatCompletionMessageToolCall(...)]

# 注意：模型只是"请求"调用，下面这行是你自己执行的
result = get_weather(**json.loads(msg.tool_calls[0].function.arguments))
```

第 03 篇会把这一整套（工具定义、参数校验、多轮循环、错误处理）完整落地成 LangChain 写法。

### 7.4 结构化输出 vs Function Calling

两者常被混淆：

| 方式 | 用途 | 本质 |
| :--- | :--- | :--- |
| **Function Calling** | 让模型"请求执行动作" | 输出 `tool_calls` |
| **Structured Output / JSON Mode** | 让模型"返回固定结构的数据" | 输出合法 JSON |

两者底层都是"约束输出格式"，**很多框架会用工具调用来实现结构化输出**。第 03 篇会对比适用场景。

## 八、模型不知道你的数据：Embedding 与 RAG 的动机

### 8.1 幻觉的根源

问模型"我们公司的年假有几天"，它不知道。但它不会说"不知道"——它会**基于训练数据里"一般公司年假 5–15 天"的统计规律，编一个听起来合理的答案**。

这就是幻觉：**不是模型坏了，是你问了它不可能知道的事。**

**解决思路有三条**：

| 思路 | 做法 | 代价 |
| :--- | :--- | :--- |
| 微调（Fine-tuning） | 用你的数据继续训练模型 | 贵、慢、更新困难、容易过时 |
| 塞进 Prompt | 把相关资料直接放进上下文 | 上下文有限，文档多了放不下 |
| **RAG** | 先检索"最相关"的几段，再放进 Prompt | **主流方案** |

### 8.2 RAG 的核心思想

```text
用户问题
   ↓
在知识库里检索最相关的 N 段
   ↓
把 "问题 + 这 N 段资料" 一起交给模型
   ↓
模型基于资料回答，并给出引用
```

**为什么需要 Embedding（向量化）**：

关键词搜索"如何请假"匹配不到文档里的"休假申请流程"——**字面不同，语义相同**。Embedding 把文本映射成一个向量，语义相近的文本向量距离近，于是可以"按意思找"。

```python
from openai import OpenAI
client = OpenAI()

vec = client.embeddings.create(
    model="text-embedding-3-small",
    input="休假申请流程",
).data[0].embedding
print(len(vec))    # 1536 维
```

然后计算两个向量的余弦相似度，越大越相近。

> 💡 **给后端程序员的类比**：向量检索 ≈ **给每条记录算一个"语义指纹"，建一个 ANN（近似最近邻）索引，查询时找指纹最接近的**。它和平时的 B+ 树索引解决的是同一类问题：**高效找到"相关"的数据**。

第 04 篇会从切分、Embedding、向量库、检索、重排一路做到完整可用的知识库问答。

### 8.3 RAG 不是银弹

| 问题 | 说明 |
| :--- | :--- |
| 检索不到 | 切分不当、同义词、问题表述差异 |
| 检索到无关内容 | 噪声把模型带偏 |
| 资料过期 | 知识库需要更新机制 |
| 多跳问题 | "A 的负责人所在部门的预算"需要多次检索 |
| 表格/图片 | 纯文本切分会丢失结构 |

> ⚠️ **真实项目里，RAG 效果差通常有 70% 是"检索"问题，30% 是"Prompt 组装"问题，模型问题占比很小。** 所以第 04 篇会把重点放在检索而非换模型。

## 九、从"问答"到"Agent"：为什么需要自主决策

### 9.1 一个问答系统不够用的例子

用户说：**"帮我看看上个月的报销到哪一步了，如果还没审批就催一下，顺便把发票明细发我邮箱。"**

这不是一次问答能解决的：

1. 查用户身份 → 2. 查报销单 → 3. 判断状态 → 4. 若未审批则调用催办（可能需要权限/审批） → 5. 拉取发票明细 → 6. 发邮件

而且第 3 步的"判断"依赖查询结果，第 4 步可能失败需要重试，第 5 步可能需要用户再确认。

**这正是 Agent 的适用场景：多步骤、依赖中间结果、需要调用多个系统。**

### 9.2 Agent 的最小定义

```text
Agent = 模型 + 可用工具集 + 一个循环

循环:
  1. 模型看当前上下文，决定下一步
  2. 如果决定调用工具 → 执行工具，把结果放回上下文
  3. 如果认为可以回答 → 结束，输出结果
```

**关键区别**：

| | 普通调用 | Agent |
| :--- | :--- | :--- |
| 调用次数 | 1 次 | 多次（不确定） |
| 控制流 | 你写死 | 模型决定 |
| 失败处理 | 你写 | 需要设计（重试、换工具、放弃、转人工） |
| 成本 | 可预估 | **不可预估**（可能循环 10 次） |
| 可测试性 | 高 | 低 |
| 风险 | 低 | **高**（可能调用危险工具） |

### 9.3 为什么后面要学 LangGraph

`create_agent` 能让你 10 行代码跑起来一个 Agent，但它有个本质问题：**流程是隐式的**。你不知道它下一步会干什么，出了事只能看日志猜。

LangGraph 的价值在于：**把隐式循环变成显式状态图**。

```python
# create_agent：隐式
agent = create_agent(model, tools=[...])

# LangGraph：显式（每个节点、每条边你都能看见）
graph.add_node("查报销单", query_expense)
graph.add_node("判断状态", check_status)
graph.add_node("催办", urge_approval)
graph.add_conditional_edges("判断状态", route_after_check, {
    "need_urge": "催办",
    "done": END,
})
```

**什么时候必须上 LangGraph**：

- 需要人工审批（暂停、等外部输入、恢复）
- 需要断点续跑（服务重启后从上次中断处继续）
- 需要流程可视化、可回放、可测试
- 多 Agent 分工协作
- 需要严格控制"哪些步骤允许模型自主，哪些必须固定"

第 06 篇先用 `create_agent` 建立直觉，第 07 篇再拆开它的黑盒。

### 9.4 别过早用 Agent

这是本篇最重要的一条实践建议：

```text
能用一次调用解决      → 不要用 Agent
能用固定流程 + 少量判断 → 不要用 Agent
能用 3 个工具 + 明确步数上限 → 可以用 Agent
需要动态决定调哪些工具、调几次 → 才用 Agent
```

> ⚠️ **Agent 的每一次自主决策，都是一次不可预测的调用、一次延迟和一次成本。** 很多团队用 Agent 做了本该用 `if-else + 3 次 API 调用` 解决的事，结果系统又慢又贵又难测。

## 十、成本、延迟与失败模式

### 10.1 延迟的构成

```text
总耗时 = 网络往返 + 排队 + 首 token 延迟（TTFT） + 生成耗时
                              ↑                    ↑
                         主要取决于服务商        与输出 token 数成正比
```

**典型量级**：

| 场景 | 耗时 |
| :--- | :--- |
| 短回答（100 token） | 1–3 秒 |
| 长回答（1000 token） | 10–30 秒 |
| Agent 3 轮工具调用 | 15–60 秒 |
| RAG（检索 + 生成） | 2–6 秒 |

**应对**：

- **流式输出**（streaming）：用户 0.5 秒就能看到第一个字，体感完全不同
- **异步 + 任务 ID**：长任务后台跑，前端轮询/推送
- **超时 + 降级**：超时返回缓存答案或转人工
- **并行**：多个独立检索/工具调用并发执行

### 10.2 常见失败模式

| 失败 | 表现 | 原因 | 对策 |
| :--- | :--- | :--- | :--- |
| **幻觉** | 编造事实、链接、数据 | 模型不知道 | RAG + 要求引用 + 不确定就说不知道 |
| **格式崩坏** | 该返回 JSON 却返回一段话 | 约束不够 | 结构化输出 + 校验重试 |
| **指令漂移** | 多轮后忘了最初规则 | 上下文太长 | 关键约束重复注入 / 每轮重设系统提示 |
| **工具乱调** | 频繁调用不需要的工具 | 工具描述不清 | 精简工具、写清楚什么时候用/不用 |
| **死循环** | Agent 反复调同一个工具 | 缺少终止条件 | 步数上限、重复调用检测 |
| **越权** | 调用了不该调的接口 | Prompt 注入 | 权限校验放在代码层，不信任模型 |
| **成本爆炸** | 单次请求几十万 token | 无长度控制 | 上下文预算、max_tokens、缓存 |
| **延迟抖动** | P99 突然 60 秒 | 服务商限流 | 重试 + 超时 + 备用模型 |

> 💡 **这八条几乎覆盖了生产事故的 90%**。后面每一篇都会回到这张表。

### 10.3 一个"最小可用"的健壮调用封装

```python
import time
from openai import OpenAI, APITimeoutError, RateLimitError

client = OpenAI()


def safe_chat(messages, model="gpt-4o-mini", max_tokens=800, retries=3):
    for attempt in range(retries):
        try:
            resp = client.chat.completions.create(
                model=model,
                messages=messages,
                temperature=0,
                max_tokens=max_tokens,
                timeout=30,
            )
            text = resp.choices[0].message.content or ""
            if resp.choices[0].finish_reason == "length":
                text += "\n[回答被截断]"
            return text
        except RateLimitError:
            time.sleep(2 ** attempt)          # 指数退避
        except APITimeoutError:
            if attempt == retries - 1:
                raise
            time.sleep(1)
    raise RuntimeError("模型调用失败，请稍后重试")
```

> ⚠️ **生产上还要加**：熔断、并发限流、按用户配额、降级到备用模型、记录 token 用量。这些在第 10 篇展开。

## 十一、技术选型：什么时候用哪种方案

### 11.1 决策树

```text
你的需求？
│
├─ 文本改写/分类/抽取/总结，输入可放进上下文
│    └─▶【直接调用 + Prompt】  最简单、最快、最便宜
│
├─ 需要基于公司内部文档回答
│    └─▶【RAG】  文档多、需要更新、需要溯源
│
├─ 需要操作业务系统（查/改数据）
│    └─▶【工具调用】  模型决定调什么，你负责执行
│
├─ 多步骤、依赖上一步结果
│    └─▶【Agent（create_agent）】
│
├─ 需要审批 / 断点续跑 / 严格流程
│    └─▶【LangGraph 状态图】
│
└─ 多个角色分工（研究/写作/审核）
     └─▶【多 Agent】——先确认单 Agent 真的不行
```

### 11.2 各方案的成本对比（相对值）

| 方案 | 开发成本 | 单次调用成本 | 延迟 | 可控性 | 适合阶段 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| 直接调用 | 低 | 1× | 低 | **高** | 快速验证 |
| RAG | 中 | 1.5–3× | 中 | 高 | 知识问答 |
| 工具调用 | 中 | 2–3× | 中 | 中 | 业务操作 |
| 单 Agent | 中高 | 3–10× | 高 | 中低 | 动态流程 |
| LangGraph | 高 | 3–10× | 高 | **高** | 核心业务 |
| 多 Agent | 很高 | 10–30× | 很高 | 低 | 复杂任务 |

> 💡 **这张表要"从左往右"选，而不是从右往左**。先证明左边的方案不行，再往右走。

### 11.3 一个真实项目的演进路径

```text
第 1 周：直接用 Prompt + 1 次调用，验证"这事能不能成"
第 2 周：加结构化输出，接入业务系统做工具调用
第 3 周：发现需要私有知识 → 上 RAG
第 4 周：发现流程有分支需要判断 → 用 create_agent
第 6 周：发现要审批、要断点续跑 → 迁移到 LangGraph
第 8 周：加可观测、评测集、限流、降级 → 上线
```

**没有项目是第一天就用多 Agent 的。** 如果有，通常是过度设计。

## 十二、本章小结与自检

### 核心结论

1. **大模型是一个无状态、按 token 计费、有延迟、会编造的远端文本服务**。所有工程手段都由此推导。
2. **Token 既是计费单位也是长度单位**。上下文窗口是所有设计的天花板，必须做预算。
3. **模型只会"预测下一个 token"**，所以它不擅长精确计算、不掌握私有知识、不保证事实正确。
4. **Function Calling 的本质是"模型输出调用意图，代码负责执行"**。权限、校验、审计都在你这一侧。
5. **RAG 解决"不知道你的数据"**，核心难点在检索质量，不在模型。
6. **Agent = 模型 + 工具 + 循环**，灵活性和不可控性同源。
7. **选型要"从简到繁"**，能一次调用解决就不要上 Agent。
