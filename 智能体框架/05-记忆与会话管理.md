## 一、记忆到底解决什么问题

### 1.1 四个典型场景

```text
场景 1（上下文延续）
用户：帮我查订单 12345
用户：它到哪了？
     ↑ "它"指什么？没有历史就答不上来

场景 2（偏好记忆）
用户（上周）：以后回答简洁点，别写那么多
用户（本周）：这个接口怎么设计？
     ↑ 跨会话的偏好，短期历史帮不上忙

场景 3（任务状态）
Agent：请提供收货地址
用户：北京朝阳区xxx
Agent：（中断了）……
用户：继续
     ↑ 上一步做到哪了？

场景 4（长文档对话）
用户上传了 200 页 PDF，连续问了 20 个问题
     ↑ 全文放不进上下文，需要"压缩 + 按需召回"
```

### 1.2 记忆的本质

```text
记忆 = 存储（存在哪） + 检索（怎么取） + 裁剪（取多少） + 注入（怎么拼进 Prompt）
```

**这四步每一步都是工程决策**，和模型无关。

> ⚠️ **最大的误区**：以为"把模型换成支持更长上下文的"就解决了记忆问题。
> 32K → 128K → 200K，**成本线性增长，效果却不一定提升**（lost in the middle），**延迟也在涨**。长上下文是"能用"，不是"好用"。

## 二、三种记忆，别混为一谈 ⭐

| 类型 | 内容 | 生命周期 | 存储 | 典型实现 |
| :--- | :--- | :--- | :--- | :--- |
| **短期记忆** | 当前会话的消息列表 | 一次会话 | 内存 / Redis | Checkpointer、消息列表 |
| **长期记忆** | 用户偏好、事实、历史结论 | 跨会话、长期 | 数据库 / 向量库 | Store、用户画像表 |
| **业务状态** | 订单号、流程节点、表单数据 | 业务决定 | **业务数据库** | 不要放模型侧 |

### 2.1 为什么必须分开

```text
❌ 全塞进消息历史
   问题：token 爆炸、跨会话丢失、无法结构化查询

❌ 全部让模型"记住"
   问题：模型不保证记住、也无法审计

✅ 分层
   短期 → 消息窗口
   长期 → 结构化存储 + 按需检索
   业务 → 数据库（模型只负责"读"和"写"的工具调用）
```

> 💡 **一个判断标准**：**如果这个信息丢失会导致业务错误，它就不该只存在"记忆"里**。订单号、金额、审批状态必须在业务库里，Agent 通过工具去查。

### 2.2 记忆的三个关键问题

设计任何记忆方案前，先回答：

1. **存什么**：全量消息？摘要？提取的事实？结构化字段？
2. **存多久**：一次会话？7 天？永久？
3. **怎么用**：全量注入？相关性召回？按规则拼装？

> ⚠️ **不回答这三个问题就动手，最后一定变成"把所有东西都塞进去"**，然后成本失控、效果下降。

## 三、短期记忆：上下文窗口管理 ⭐⭐

### 3.1 最朴素的做法

```python
history = [SystemMessage("你是技术助手")]

def chat(text):
    history.append(HumanMessage(text))
    ai = model.invoke(history)
    history.append(ai)
    return ai.content
```

**问题**：

```python
# 20 轮之后
sum(model.get_num_tokens_from_messages(history))   # 15000+ token
# 成本 ×20，延迟 ×3，且最早的约束被稀释
```

### 3.2 五种裁剪策略

#### 策略 1：保留最近 N 轮（最简单）

```python
def keep_last_n(messages, n=10):
    system = [m for m in messages if isinstance(m, SystemMessage)]
    rest = [m for m in messages if not isinstance(m, SystemMessage)]
    return system + rest[-n * 2:]        # 每轮 user + assistant
```

**优点**：简单、可预测
**缺点**：硬截断，可能丢失关键信息（"我前面说了我住在上海"）

#### 策略 2：按 token 预算裁剪（更准确）

```python
def trim_to_budget(messages, max_tokens=3000):
    system = [m for m in messages if isinstance(m, SystemMessage)]
    rest = [m for m in messages if not isinstance(m, SystemMessage)]

    used = model.get_num_tokens_from_messages(system)
    kept = []
    for m in reversed(rest):                       # 从最新往前
        n = model.get_num_tokens_from_messages([m])
        if used + n > max_tokens:
            break
        kept.insert(0, m)
        used += n
    return system + kept
```

> 💡 **比"最近 N 轮"好**：短消息可以多留几条，长消息少留几条。

#### 策略 3：始终保留关键消息（推荐）

**有些消息不能丢**：最初的系统提示、用户的关键约束、工具调用的结果。

```python
PINNED_ROLES = ("system",)

def trim_keep_pinned(messages, max_tokens=3000):
    pinned = [m for m in messages if m.type in PINNED_ROLES]
    rest = [m for m in messages if m.type not in PINNED_ROLES]

    # 从最新往前保留，但保证 tool 消息和它的 ai 消息成对
    kept = []
    used = sum(model.get_num_tokens_from_messages([m]) for m in pinned)
    for m in reversed(rest):
        n = model.get_num_tokens_from_messages([m])
        if used + n > max_tokens:
            break
        kept.insert(0, m)
        used += n
    return pinned + kept
```

> ⚠️ **裁剪时要保证消息对完整**：`AIMessage(tool_calls)` 和对应的 `ToolMessage` 不能被拆开，否则 API 报错。

#### 策略 4：摘要压缩（见下一节）

#### 策略 5：检索式记忆（见第五节）

### 3.3 各策略对比

| 策略 | 实现复杂度 | 信息保留 | 成本 | 适用 |
| :--- | :--- | :--- | :--- | :--- |
| 最近 N 轮 | ⭐ | 低 | 最低 | 闲聊、短会话 |
| token 预算 | ⭐ | 中 | 低 | 通用 |
| 保留关键消息 | ⭐⭐ | 中高 | 低 | 有硬约束的场景 |
| 摘要压缩 | ⭐⭐⭐ | 中 | 中（多一次调用） | 长会话 |
| 检索式记忆 | ⭐⭐⭐⭐ | 高 | 中高 | 长期助教、客服 |

## 四、摘要记忆：把历史压成一段话

### 4.1 基本思路

```text
旧对话（20 轮，8000 token）
        ↓ 摘要模型
摘要（300 token）："用户是 Java 后端，正在做订单系统…
                  已确认需求：…；未解决问题：…"
        ↓
[系统提示] + [摘要] + [最近 5 轮原文]
```

### 4.2 实现

```python
SUMMARY_PROMPT = """请把下面的对话压缩成一段摘要，供后续对话参考。

保留：
- 用户的身份、偏好、明确提出的要求
- 已确认的结论、数字、ID
- 尚未解决的问题

删除：
- 客套话、重复内容、已经解决的细节

对话：
{history}

输出一段不超过 300 字的摘要："""


class SummaryMemory:
    def __init__(self, model, keep_recent=6, max_summary_tokens=400):
        self.model = model
        self.keep_recent = keep_recent
        self.max_summary_tokens = max_summary_tokens
        self.summary = ""
        self.messages = []

    def add(self, msg):
        self.messages.append(msg)

    def build_prompt(self, system_prompt: str):
        msgs = []
        if self.summary:
            msgs.append(SystemMessage(f"【历史对话摘要】\n{self.summary}"))
        msgs.append(SystemMessage(system_prompt))
        msgs.extend(self.messages[-self.keep_recent * 2:])
        return msgs

    def maybe_compress(self):
        if len(self.messages) <= self.keep_recent * 2 + 4:
            return

        old = self.messages[: -self.keep_recent * 2]
        text = "\n".join(f"{m.type}: {m.content}" for m in old)
        combined = (self.summary + "\n" + text).strip()

        self.summary = self.model.invoke(
            SUMMARY_PROMPT.format(history=combined),
            config={"max_tokens": self.max_summary_tokens},
        ).content

        self.messages = self.messages[-self.keep_recent * 2:]
```

### 4.3 摘要的坑

| 坑 | 说明 | 应对 |
| :--- | :--- | :--- |
| 摘要丢失关键数字 | 模型概括时把"金额 299 元"写没了 | Prompt 里明确"保留所有数字和 ID" |
| 摘要出错并累积 | 摘要的摘要会越来越失真 | **只摘要原文，不要摘要摘要**；或定期从原文重建 |
| 成本没省多少 | 每次压缩要一次额外调用 | 按 token 阈值触发，不要每条都压 |
| 摘要破坏指令 | 系统提示被揉进摘要 | 系统提示**永远不参与摘要** |

> ⚠️ **不要把 system prompt 放进摘要**。摘要后模型会"忘记"自己的角色设定。

### 4.4 混合策略（推荐）

```text
[系统提示]（固定，永不裁剪）
[长期记忆]（用户画像，按需注入）
[历史摘要]（压缩的旧对话）
[最近 N 轮原文]（完整保留）
[本轮用户输入]
```

> 💡 这个结构兼顾了**完整性和成本**，是工业界最常见的形态。

## 五、长期记忆：跨会话记住用户 ⭐⭐

### 5.1 长期记忆存什么

| 类型 | 例子 | 存储方式 |
| :--- | :--- | :--- |
| **用户偏好** | "回答简洁点"、"用中文"、"我是 Java 后端" | 结构化 KV |
| **事实** | "我住在上海"、"我的订单号是 12345" | 结构化 KV / 图 |
| **历史结论** | "上次讨论过这个方案，结论是不采用" | 向量库 |
| **交互历史** | 所有历史对话 | 向量库（按需召回） |

### 5.2 方案 A：结构化用户画像（最实用）

```python
class UserProfile(BaseModel):
    user_id: str
    preferences: dict[str, str] = {}       # {"language": "zh", "style": "concise"}
    facts: dict[str, str] = {}             # {"city": "上海", "role": "Java 后端"}
    updated_at: datetime
```

```sql
CREATE TABLE user_profile (
    user_id     VARCHAR(64) PRIMARY KEY,
    preferences JSONB NOT NULL DEFAULT '{}',
    facts       JSONB NOT NULL DEFAULT '{}',
    updated_at  TIMESTAMPTZ DEFAULT now()
);
```

**注入方式**：

```python
def build_system_prompt(user_id: str) -> str:
    p = load_profile(user_id)
    prefs = "\n".join(f"- {k}: {v}" for k, v in p["preferences"].items())
    facts = "\n".join(f"- {k}: {v}" for k, v in p["facts"].items())
    return f"""你是 {COMPANY} 的技术助手。

【用户偏好】
{prefs or "- 无"}

【已知信息】
{facts or "- 无"}
"""

# 结果：
# 【用户偏好】
# - language: zh
# - style: concise
# 【已知信息】
# - role: Java 后端
# - city: 上海
```

**怎么更新画像**：

```python
EXTRACT_PROMPT = """从下面的对话中提取用户的长期偏好和事实信息。

只提取"以后还会用到"的稳定信息，不要提取一次性内容（如"今天问了一个问题"）。
如果没有新信息，输出空 JSON。

对话：
{conversation}

输出 JSON：
{{"preferences": {{...}}, "facts": {{...}}}}
"""

def update_profile(user_id, conversation):
    extracted = model.with_structured_output(ProfileDelta).invoke(
        EXTRACT_PROMPT.format(conversation=conversation)
    )
    merge_into_db(user_id, extracted)
```

> ⚠️ **抽取要异步做**，不要阻塞用户请求。而且要注意：**模型抽取可能出错**（把"我不要简洁"抽成"偏好简洁"），最好在 UI 上让用户能查看/编辑自己的画像。

> 💡 **这是"AI 记住我"最靠谱的实现方式**：**结构化 + 可解释 + 可编辑**。比"把所有历史塞进向量库然后相似度召回"可靠得多。

### 5.3 方案 B：对话历史向量化（语义召回）

把每条历史消息向量化，需要时按相似度召回：

```python
from langchain_core.documents import Document

def save_memory(user_id: str, text: str, kind: str = "conversation"):
    vectorstore.add_documents([Document(
        page_content=text,
        metadata={"user_id": user_id, "kind": kind, "ts": time.time()},
    )])


def recall_memory(user_id: str, query: str, k: int = 3):
    docs = vectorstore.similarity_search(
        query, k=k, filter={"user_id": user_id},
    )
    return "\n".join(d.page_content for d in docs)
```

**优点**：能召回很久以前说过的相关内容
**缺点**：

- 召回可能不准（"我喜欢简洁"和"这个回答太长了"语义相近，但一个是偏好一个是抱怨）
- 难以去重、更新、删除
- 容易把无关的旧对话塞进 Prompt

> ⚠️ **不要把所有历史都塞进向量库**。只存**总结过的、有价值的**信息，否则召回质量会随着数据量增长而下降。

### 5.4 方案 C：LangGraph Store（1.x 推荐）

LangGraph 提供了 `Store` 抽象，跨会话持久化：

```python

# 读取

```

## 六、LangGraph Checkpointer：会话状态的标准解法 ⭐

### 6.1 是什么

**Checkpointer** 在**每个节点执行后**保存一份状态快照，附上 `thread_id`。下次用同一个 `thread_id` 调用，就能接着上次继续。

```python
from langgraph.checkpoint.memory import InMemorySaver

checkpointer = InMemorySaver()

agent = create_agent(model=model, tools=[], checkpointer=checkpointer)

config = {"configurable": {"thread_id": "user_u1001_chat_01"}}

# 第一轮
agent.invoke({"messages": [("user", "我叫张三，在杭州工作")]}, config)

# 第二轮（同一个 thread_id，自动带上历史）
resp = agent.invoke({"messages": [("user", "我在哪工作？")]}, config)
print(resp["messages"][-1].content)     # "您在杭州工作"
```

### 6.2 生产用持久化 Checkpointer

```python
from langgraph.checkpoint.postgres import PostgresSaver
from langgraph.checkpoint.redis import RedisSaver

# PostgreSQL
with PostgresSaver.from_conn_string(PG_DSN) as saver:
    saver.setup()                     # 建表（首次）
    agent = create_agent(model, tools, checkpointer=saver)

# Redis（注意：RedisSaver 属于 langgraph-checkpoint-redis 包）
saver = RedisSaver.from_conn_string(REDIS_URL)
```

> ⚠️ **`InMemorySaver` 只能用于开发**。进程重启就全没了，多实例也不共享。

### 6.3 Checkpointer 解决了什么

| 问题 | 解法 |
| :--- | :--- |
| 服务重启后对话丢失 | 状态在数据库里 |
| 多实例负载均衡 | 任意实例都能读到同一 thread |
| 历史无限增长 | 需要配合裁剪（见 6.4） |
| 人工审批中断 | 状态可恢复（第 08 篇） |

### 6.4 历史裁剪中间件

LangGraph 1.x 提供 `SummarizationMiddleware` / `trim_messages` 处理历史过长：

```python
from langchain_core.messages import trim_messages

trimmed = trim_messages(
    messages,
    max_tokens=4000,
    strategy="last",              # 保留最新的
    token_counter=model,
    include_system=True,          # 保留 system
    allow_partial=False,
    start_on="human",             # 从 human 消息开始，避免拆散工具调用
)
```

```python
from langchain.agents.middleware import SummarizationMiddleware

agent = create_agent(
    model=model,
    tools=[],
    checkpointer=checkpointer,
    middleware=[
        SummarizationMiddleware(
            model=model,                    # 用便宜的模型做摘要
            max_tokens_before_summary=4000,
            messages_to_keep=10,
        )
    ],
)
```

> 💡 **`start_on="human"` 很重要**：确保裁剪后消息序列以用户消息开始，避免 `tool_call_id` 对不上导致的 400 错误。

### 6.5 Thread 的设计

```text
thread_id = "{tenant}:{user_id}:{channel}:{conversation_id}"
```

| 设计方式 | 说明 | 适用 |
| :--- | :--- | :--- |
| `user_id` 单值 | 一个用户一条线 | 个人助手 |
| `user_id:session_id` | 一个会话一条线 | 客服工单（每次咨询独立） |
| `tenant:user:session` | 多租户隔离 | SaaS |
| `order_id` | 以业务实体为线 | 订单处理 Agent |

> ⚠️ **`thread_id` 决定了"什么算同一次对话"**。设计错了，要么用户看到别人的历史（安全事故），要么该记住的没记住。

> ⚠️ **多租户场景一定要把 `tenant_id` 放进 thread_id**，并在查询时校验归属，**不能信任客户端传的 thread_id**。

### 6.6 状态大小的问题

Checkpointer 保存的是**完整状态**（含全部消息），长期运行会：

- 表膨胀（每条消息都存）
- 每次读取变慢
- 恢复时 token 爆炸

**治理手段**：

1. **定期归档**旧 thread（超过 N 天的转冷存储）
2. **裁剪中间件**控制单个 thread 的消息数
3. **只存必要字段**（不要把大文档内容放进状态）
4. 用 `checkpoint_ns` / 独立表分区

## 七、业务状态：别让模型管业务数据

### 7.1 一个真实的翻车案例

```text
用户：我要退款
Agent：好的，请提供订单号
用户：12345
Agent：退款已提交，金额 299 元
```

**问题**：Agent 从"记忆"里认为金额是 299（可能是用户上一轮随便说的），**实际订单金额是 599**。

> ⚠️ **模型不应该成为业务数据的"存储"。** 金额、订单号、状态必须以**工具查询结果**为准。

### 7.2 正确做法

```python
@tool
async def apply_refund(order_no: str, config: RunnableConfig) -> dict:
    """为订单申请退款。退款金额由系统根据订单自动计算。"""
    # ✅ 金额从订单服务读取，不让模型传
    order = await order_api.get(order_no)
    if order["status"] not in ("已发货", "已完成"):
        return {"success": False, "error": f"订单状态为「{order['status']}」，不可退款"}

    refund = await refund_api.create(order_no, amount=order["amount"])
    return {"success": True, "refund_id": refund["id"], "amount": order["amount"]}
```

**关键差异**：

| 错误做法 | 正确做法 |
| :--- | :--- |
| 工具参数含 `amount`，由模型填 | **金额由服务端计算** |
| 模型记住"用户说要退 299" | 每次以订单服务为准 |
| 状态在对话里 | 状态在数据库里 |

### 7.3 状态内的数据要"最小化"

LangGraph 的 State 里应该放：

- ✅ 消息
- ✅ 流程节点、重试次数
- ✅ 工具调用摘要
- ❌ 完整订单对象（放 ID 即可）
- ❌ 大文档全文（放引用）
- ❌ 敏感信息（token、身份证）

> 💡 **State 会被持久化、被日志记录、被追踪系统采集**。往里面放敏感数据的成本很高。

## 八、完整的会话管理实现

```python
# memory.py
import time, json
from dataclasses import dataclass, field
from langchain_core.messages import BaseMessage, SystemMessage, HumanMessage, AIMessage

SYSTEM_PROMPT = """你是 {company} 的技术助手。

【用户偏好】
{preferences}

【已知信息】
{facts}

规则：
1. 回答简洁，除非用户要求详细。
2. 不确定时明确说不确定，不要编造。
"""


@dataclass
class Session:
    thread_id: str
    user_id: str
    messages: list[BaseMessage] = field(default_factory=list)
    summary: str = ""
    profile: dict = field(default_factory=dict)
    created_at: float = field(default_factory=time.time)


class SessionManager:
    def __init__(self, model, store, max_tokens=3500, keep_recent=8):
        self.model = model
        self.store = store                 # Redis / PG 客户端
        self.max_tokens = max_tokens
        self.keep_recent = keep_recent

    # ---------- 读写 ----------
    def load(self, thread_id: str, user_id: str) -> Session:
        raw = self.store.get(f"session:{thread_id}")
        profile = self.store.get(f"profile:{user_id}") or {"preferences": {}, "facts": {}}
        if not raw:
            return Session(thread_id=thread_id, user_id=user_id, profile=profile)

        data = json.loads(raw)
        msgs = [deserialize(m) for m in data["messages"]]
        return Session(
            thread_id=thread_id, user_id=user_id,
            messages=msgs, summary=data.get("summary", ""),
            profile=profile, created_at=data["created_at"],
        )

    def save(self, session: Session, ttl_days: int = 30):
        self.store.setex(
            f"session:{session.thread_id}",
            ttl_days * 86400,
            json.dumps({
                "messages": [serialize(m) for m in session.messages],
                "summary": session.summary,
                "created_at": session.created_at,
            }, ensure_ascii=False),
        )

    # ---------- 组装 Prompt ----------
    def build_messages(self, session: Session) -> list[BaseMessage]:
        system = SYSTEM_PROMPT.format(
            company="XX 公司",
            preferences="\n".join(f"- {k}: {v}" for k, v in session.profile["preferences"].items()) or "- 无",
            facts="\n".join(f"- {k}: {v}" for k, v in session.profile["facts"].items()) or "- 无",
        )
        msgs = [SystemMessage(system)]
        if session.summary:
            msgs.append(SystemMessage(f"【历史对话摘要】\n{session.summary}"))
        msgs.extend(self._trim(session.messages))
        return msgs

    def _trim(self, messages):
        recent = messages[-self.keep_recent * 2:]
        used = self.model.get_num_tokens_from_messages(recent)
        while used > self.max_tokens and len(recent) > 2:
            recent = recent[1:]                    # 从最旧开始丢
            used = self.model.get_num_tokens_from_messages(recent)
        return recent

    # ---------- 主流程 ----------
    def chat(self, thread_id: str, user_id: str, text: str) -> str:
        session = self.load(thread_id, user_id)
        session.messages.append(HumanMessage(text))

        msgs = self.build_messages(session)
        ai = self.model.invoke(msgs)
        session.messages.append(ai)

        # 超过阈值就压缩
        if len(session.messages) > self.keep_recent * 2 + 6:
            self._compress(session)

        self.save(session)
        return ai.content

    def _compress(self, session: Session):
        old = session.messages[:-self.keep_recent * 2]
        text = "\n".join(f"{m.type}: {m.content}" for m in old)
        merged = (session.summary + "\n" + text).strip()
        session.summary = self.model.invoke(
            f"把以下对话压缩为 300 字以内的摘要，保留用户偏好、关键数字和未解决问题：\n{merged}",
            config={"max_tokens": 400},
        ).content
        session.messages = session.messages[-self.keep_recent * 2:]


def serialize(m: BaseMessage) -> dict:
    return {"type": m.type, "content": m.content}


def deserialize(d: dict) -> BaseMessage:
    cls = {"human": HumanMessage, "ai": AIMessage, "system": SystemMessage}[d["type"]]
    return cls(d["content"])
```

### 8.1 使用

```python
mgr = SessionManager(model=model, store=redis_client)

print(mgr.chat("u1001:chat1", "u1001", "我叫张三，在杭州做 Java 开发"))
print(mgr.chat("u1001:chat1", "u1001", "我在哪个城市？"))    # 杭州

# 换一个会话（thread_id 不同）
print(mgr.chat("u1001:chat2", "u1001", "我是做什么的？"))    # 从 profile 里读到"Java 开发"
```

### 8.2 加一个"记忆抽取"的异步任务

```python
from concurrent.futures import ThreadPoolExecutor

executor = ThreadPoolExecutor(max_workers=2)

def chat_with_memory(thread_id, user_id, text):
    answer = mgr.chat(thread_id, user_id, text)
    executor.submit(extract_and_update_profile, user_id, text, answer)
    return answer


def extract_and_update_profile(user_id, question, answer):
    profile = store.get(f"profile:{user_id}") or {"preferences": {}, "facts": {}}
    delta = model.with_structured_output(ProfileDelta).invoke(
        f"从对话中提取用户长期信息：\n用户：{question}\n助手：{answer}"
    )
    profile["preferences"].update(delta.preferences or {})
    profile["facts"].update(delta.facts or {})
    store.set(f"profile:{user_id}", json.dumps(profile, ensure_ascii=False))
```

> ⚠️ **异步任务要考虑失败**：抽取出错不能影响主流程，加日志和重试。

## 九、成本控制实战

### 9.1 成本结构

```text
单轮成本 = (系统提示 + 长期记忆 + 历史摘要 + 最近 N 轮 + 本轮问题 + 工具定义) × 输入单价
         + 输出 token × 输出单价
```

**随轮次增长的部分**：最近 N 轮（有上限）+ 历史摘要（有上限）——**如果做了裁剪，就是 O(1)；不做就是 O(n)**。

### 9.2 五个立竿见影的手段

| 手段 | 效果 | 代价 |
| :--- | :--- | :--- |
| **限制最近 N 轮** | 直接砍掉线性增长 | 可能丢信息 |
| **摘要压缩** | 历史大小恒定 | 一次额外调用 + 有损 |
| **精简系统提示** | 每轮都省 | 无 |
| **工具按需绑定** | 每轮省 1000–5000 token | 需要意图路由 |
| **Prompt 缓存** | 固定前缀打折 | 需要把固定内容放前面 |

### 9.3 一个实际的预算表

```text
场景：企业知识助手，平均 8 轮对话

 系统提示            400
 用户画像            200
 历史摘要            300
 最近 6 轮原文       1800
 检索资料（4 段）     2000
 工具定义（5 个）     800
 ─────────────────────────
 输入合计            5500
 输出                500
 ─────────────────────────
 单轮 ≈ 6000 token

 8 轮会话 ≈ 单轮 × 8（越往后输入越长）
 实际约 50000–60000 token
```

> 💡 **对比不裁剪**：第 8 轮时输入约 15000 token，8 轮累计约 **90000+ token**。**裁剪能省 30–40%**。

## 十、隐私与合规

### 10.1 必须做的四件事

| 事项 | 说明 |
| :--- | :--- |
| **告知** | 明确告诉用户"对话会被保存用于改进/记忆" |
| **可查** | 用户能查看自己的记忆内容 |
| **可删** | 支持"忘记我"（GDPR 删除权） |
| **可关** | 允许关闭长期记忆 |

### 10.2 技术实现

```python
# 删除某个用户的所有记忆
def forget_user(user_id: str):
    store.delete(f"profile:{user_id}")
    for key in store.scan(f"session:*"):
        data = json.loads(store.get(key))
        if data.get("user_id") == user_id:
            store.delete(key)
    vectorstore.delete(where={"user_id": user_id})      # 向量库也要删
    audit_log("user_forgotten", user_id=user_id)
```

> ⚠️ **向量库的删除经常被遗漏**。RAG 记忆里存着用户的历史，删了主表但向量还在，就是合规事故。

### 10.3 敏感信息脱敏

```python
PATTERNS = [
    (r"\d{17}[\dXx]", "[身份证]"),
    (r"1[3-9]\d{9}", "[手机号]"),
    (r"\d{16,19}", "[银行卡]"),
]

def scrub(text: str) -> str:
    for pat, repl in PATTERNS:
        text = re.sub(pat, repl, text)
    return text

# 存记忆前脱敏
session.messages.append(HumanMessage(scrub(text)))
```

> ⚠️ **脱敏要在"写入持久化存储之前"做**。写完再脱敏，原文已经在库里了。

## 十一、常见方案对比

| 方案 | 实现 | 跨会话 | 成本 | 可控性 | 推荐场景 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| 内存消息列表 | ⭐ | ❌ | 最低 | 高 | Demo |
| 最近 N 轮 | ⭐ | ❌ | 低 | 高 | 通用 |
| 滑动窗口 + 摘要 | ⭐⭐ | ❌ | 中 | 高 | 长会话 |
| 结构化用户画像 | ⭐⭐⭐ | ✅ | 低 | **最高** | **推荐** |
| 历史向量召回 | ⭐⭐⭐⭐ | ✅ | 中高 | 中 | 长期助教 |
| LangGraph Checkpointer | ⭐⭐ | ✅ | 低 | 高 | **Agent 场景标配** |
| Checkpointer + Store | ⭐⭐⭐ | ✅ | 中 | 高 | **生产推荐** |

**推荐组合**：

```text
短期：Checkpointer（thread_id）+ 裁剪/摘要中间件
长期：结构化用户画像（Profile）+ 少量向量召回
业务：业务数据库 + 工具调用（不进记忆）
```

## 十二、踩坑清单

| # | 坑 | 现象 | 解决 |
| :--- | :--- | :--- | :--- |
| 1 | 历史无限增长 | 成本、延迟飙升 | 裁剪或摘要 |
| 2 | 裁剪拆散 tool 消息对 | 400 错误 | `start_on="human"` |
| 3 | `InMemorySaver` 用于生产 | 重启丢数据 | 用 PG/Redis |
| 4 | `thread_id` 未隔离租户 | **数据串号** | `tenant:user:session` |
| 5 | 信任客户端传的 `thread_id` | 越权读历史 | 服务端校验归属 |
| 6 | 系统提示被摘要吞掉 | 人格漂移 | 系统提示永不参与摘要 |
| 7 | 摘要摘摘要 | 逐渐失真 | 只从原文重建 |
| 8 | 金额/状态放在记忆里 | 业务错误 | 以工具查询为准 |
| 9 | 敏感信息写进 State | 泄露 | State 最小化 + 脱敏 |
| 10 | 向量库未同步删除 | 合规风险 | 删除联动 |
| 11 | 摘要模型太贵 | 省的钱不够花的 | 用小模型做摘要 |
| 12 | 每条消息都调摘要 | 成本反增 | 按 token 阈值触发 |
| 13 | 不记录 `usage_metadata` | 无法核算成本 | 每次累加 |
| 14 | 记忆抽取阻塞主流程 | 响应变慢 | 异步执行 |
| 15 | 抽取结果直接覆盖 | 偏好被搞错 | 合并 + 可编辑 |

## 十三、本章小结与练习

### 核心结论

1. **模型无记忆**，记忆 = 存储 + 检索 + 裁剪 + 注入，全是工程决策。
2. **三种记忆要分开**：短期（会话）、长期（用户）、业务（数据库）。
3. **短期记忆的核心是裁剪**：最近 N 轮 / token 预算 / 保留关键消息 / 摘要 / 检索召回。
4. **摘要要小心**：保留数字和 ID、不摘要系统提示、不要摘要摘要。
5. **长期记忆首选结构化画像**：可解释、可编辑、成本低。
6. **LangGraph Checkpointer 是 Agent 场景的标准解法**，但 `thread_id` 设计决定安全。
7. **业务数据不要放记忆里**，金额、状态以服务端查询为准。
8. **成本随轮次增长**，裁剪能省 30–40%；要监控 `usage_metadata`。
9. **隐私合规**：可查、可删、可关、脱敏。
