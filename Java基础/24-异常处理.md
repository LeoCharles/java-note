# 异常处理

Java 通过「异常机制」把程序运行时的错误（除零、空指针、文件找不到）从正常业务逻辑中分离出来，让错误处理代码更集中、更清晰。掌握异常体系与处理方式，是写出健壮 Java 代码的必修课——线上 OOM、空指针、资源泄漏，多半都根源于异常处理不当。

> 💡 本篇涉及 JVM 如何在方法调用栈上传播异常，建议结合 [02-JVM内存模型](02-JVM内存模型.md) 理解方法栈，会更容易吃透 finally 执行时机与异常传播。

---

## 一、异常体系总览

Java 所有异常和错误的顶层父类是 `java.lang.Throwable`。它有两个直接子类：`Error` 和 `Exception`。

```
Throwable（顶层）
├── Error（JVM 错误，程序不该 try）
│   ├── OutOfMemoryError        // 内存溢出
│   ├── StackOverflowError      // 栈溢出
│   └── VirtualMachineError     // 虚拟机错误
└── Exception
    ├── RuntimeException（运行时异常，非受检）
    │   ├── NullPointerException
    │   ├── ArrayIndexOutOfBoundsException
    │   ├── ClassCastException
    │   ├── ArithmeticException
    │   └── NumberFormatException
    └── 其他 Exception 子类（编译时异常，受检）
        ├── IOException
        ├── SQLException
        └── ParseException
```

> 💡 **记忆要点**：`Error` 和 `RuntimeException` 及其子类是**非受检异常**（unchecked），编译器不强制处理；`Exception` 的其他子类是**受检异常**（checked），编译器强制要求处理（try-catch 或 throws），否则编译不通过。

## 二、Error：不该 try 的 JVM 错误

`Error` 表示 JVM 自身出了问题，程序通常无法恢复，**不该也不必 try-catch**。

```java
public class ErrorDemo {
    // 栈溢出：无限递归
    public static void recursive() {
        recursive();  // ❌ 会抛 StackOverflowError
    }

    // 堆溢出：不断分配大对象
    public static void oom() {
        java.util.List<int[]> list = new java.util.ArrayList<>();
        while (true) {
            list.add(new int[1000000]);  // ❌ 会抛 OutOfMemoryError
        }
    }
}
```

> ⚠️ **不要 try Error**：`OutOfMemoryError`、`StackOverflowError` 是 JVM 级别的严重故障，try 住也救不回来——堆已经满了或栈已经爆了，后续任何对象分配都会失败。正确做法是排查根因（内存泄漏、递归过深、JVM 参数太小）。

## 三、编译时异常 vs 运行时异常

### 3.1 编译时异常（受检异常 Checked）

编译器在编译期就检查：必须 try-catch 或 throws，否则**编译不通过**。常见代表：`IOException`、`SQLException`、`ParseException`、`ClassNotFoundException`。

```java
import java.io.FileInputStream;
import java.io.IOException;

public class CheckedDemo {
    public static void main(String[] args) {
        // ❌ 编译错误：Unhandled exception: java.io.IOException
        // FileInputStream fis = new FileInputStream("a.txt");

        // ✅ 方式一：try-catch
        try (FileInputStream fis = new FileInputStream("a.txt")) {
            System.out.println("打开成功");
        } catch (IOException e) {
            e.printStackTrace();
        }

        // ✅ 方式二：调用声明了 throws 的方法，自己处理
        try {
            readFile();
        } catch (IOException e) {
            e.printStackTrace();
        }
    }

    public static void readFile() throws IOException {  // 声明抛出
        // 编译器要求：要么 try，要么继续 throws
    }
}
```

> 📌 **设计意图**：受检异常表示「合理可恢复」的错误（文件不存在、网络断开），编译器强制你思考如何处理，避免遗漏。

### 3.2 运行时异常（非受检 RuntimeException）

编译器不强制处理，通常是程序逻辑错误。常见代表：`NullPointerException`、`ArrayIndexOutOfBoundsException`、`ClassCastException`、`ArithmeticException`、`NumberFormatException`。

```java
public class RuntimeDemo {
    public static void main(String[] args) {
        String s = null;
        System.out.println(s.length());   // ❌ NullPointerException

        int[] arr = {1, 2, 3};
        System.out.println(arr[5]);        // ❌ ArrayIndexOutOfBoundsException

        Object o = "hello";
        Integer i = (Integer) o;           // ❌ ClassCastException

        System.out.println(10 / 0);       // ❌ ArithmeticException

        int n = Integer.parseInt("abc");  // ❌ NumberFormatException
    }
}
```

> ⚠️ 这些异常**编译器不报错**，但一运行就崩。预防靠写代码时的判空、边界检查，而不是 try-catch 兜底。

## 四、异常处理五个关键字

Java 异常处理围绕五个关键字：`try`、`catch`、`finally`、`throw`、`throws`。

| 关键字 | 作用 | 位置 |
| :--- | :--- | :--- |
| `try` | 尝试执行可能出错的代码块 | 方法体内 |
| `catch` | 捕获并处理异常 | 紧跟 try |
| `finally` | 无论是否异常都执行的清理代码 | try/catch 之后 |
| `throw` | 手动抛出一个异常对象 | 方法体内 |
| `throws` | 声明方法可能抛出的异常 | 方法签名上 |

### 4.1 throw：手动抛出异常

`throw` 用于方法体内主动抛出一个异常实例，常用于参数校验、业务规则违反。

```java
public class ThrowDemo {
    public static double divide(int a, int b) {
        if (b == 0) {
            // 手动抛出，注意是 new 出来的对象
            throw new ArithmeticException("除数不能为 0");
        }
        return (double) a / b;
    }

    public static void setAge(int age) {
        if (age < 0 || age > 150) {
            throw new IllegalArgumentException("年龄非法：" + age);  // ✅ 带上下文
        }
    }

    public static void main(String[] args) {
        System.out.println(divide(10, 0));  // 抛出 ArithmeticException: 除数不能为 0
    }
}
```

> 💡 `throw` 抛的是**对象实例**（`new XxxException()`），不是类名。一个 throw 只能抛一个异常。

### 4.2 throws：声明异常

`throws` 写在方法签名上，声明该方法可能抛出哪些异常，把处理责任交给调用方。可声明多个，逗号分隔。

```java
import java.io.FileInputStream;
import java.io.IOException;
import java.text.ParseException;
import java.text.SimpleDateFormat;

public class ThrowsDemo {
    // 声明一个受检异常
    public static void readFile(String path) throws IOException {
        FileInputStream fis = new FileInputStream(path);  // 可能抛 IOException
        fis.close();
    }

    // 声明多个异常
    public static void parse(String dateStr) throws ParseException, IOException {
        new SimpleDateFormat("yyyy-MM-dd").parse(dateStr);
        new FileInputStream("a.txt");
    }

    public static void main(String[] args) {
        try {
            readFile("a.txt");   // 调用方必须处理
            parse("2024-01-01");
        } catch (IOException | ParseException e) {  // 多异常合并 catch（见下文）
            e.printStackTrace();
        }
    }
}
```

> ⚠️ **throws 的滥用陷阱**：新手图省事，主方法直接 `throws Exception`，把异常一路抛到 JVM，最终程序崩溃、栈轨迹打印到控制台。这等于没处理。受检异常要么在调用链合适层级 catch，要么转译为业务异常再抛。

### 4.3 try-catch-finally：捕获处理

```java
public class TryCatchDemo {
    public static int demo() {
        try {
            System.out.println("try 执行");
            int n = 10 / 0;              // 抛出异常
            return 1;                    // 不会执行到
        } catch (ArithmeticException e) {
            System.out.println("catch 执行：" + e.getMessage());
            return 2;
        } finally {
            System.out.println("finally 一定执行");
        }
    }

    public static void main(String[] args) {
        System.out.println("结果：" + demo());
    }
}
// 输出：
// try 执行
// catch 执行：/ by zero
// finally 一定执行
// 结果：2
```

#### 多个 catch：从小到大，父类放最后

```java
public class MultiCatchOrderDemo {
    public static void main(String[] args) {
        try {
            int[] arr = {1, 2, 3};
            System.out.println(arr[5]);
        } catch (ArrayIndexOutOfBoundsException e) {
            System.out.println("数组越界：" + e.getMessage());
        } catch (RuntimeException e) {  // ✅ 父类放后面
            System.out.println("运行时异常");
        } catch (Exception e) {         // ✅ 最顶层父类放最后
            System.out.println("其他异常");
        }

        // ❌ 错误顺序：父类在前，后面子类永远不可达
        // catch (Exception e) { }
        // catch (ArrayIndexOutOfBoundsException e) { }  // 编译错误：exception already caught
    }
}
```

> ⚠️ **规则**：多个 catch 必须按「子类 → 父类」顺序排列，否则编译器报错 `exception already caught`。因为父类在前，子类异常早就被父类 catch 走了，后面的子类 catch 永远不可达。

#### finally 一定执行

```java
public class FinallyDemo {
    public static int test() {
        try {
            return 1;
        } finally {
            System.out.println("finally 在 return 之前执行");  // ✅ 会打印
        }
    }

    public static int test2() {
        try {
            System.exit(0);   // 唯一不执行 finally 的情况：JVM 直接退出
            return 1;
        } finally {
            System.out.println("不会执行");  // ❌ 不会打印
        }
    }

    public static void main(String[] args) {
        System.out.println(test());
    }
}
```

> 💡 **finally 的执行时机**：try/catch 中的 return 先算出返回值压栈，然后执行 finally，最后才真正 return。所以 finally 总在 return 前执行，除非 `System.exit()` 或 JVM 崩溃、线程被杀死。

### 4.4 finally 中 return 的坑 ⭐

```java
public class FinallyReturnTrap {
    public static int test() {
        try {
            return 1;       // try 的返回值
        } finally {
            return 2;       // ❌ finally 的 return 会覆盖 try 的 return！
        }
    }

    public static void main(String[] args) {
        System.out.println(test());  // 2，不是 1
    }
}
```

> ⚠️ **这是面试高频坑、也是开发大坑**：`finally` 里写 `return` 会**吞掉** try/catch 的返回值，甚至吞掉 try 块里未捕获的异常。**永远不要在 finally 里 return**。IDE 通常会警告，务必遵守。

## 五、Throwable 常用方法

每个异常对象都继承自 `Throwable`，常用方法如下：

| 方法 | 返回 | 用途 |
| :--- | :--- | :--- |
| `getMessage()` | String | 异常的简短描述信息 |
| `toString()` | String | 异常类全名 + message |
| `printStackTrace()` | void | 打印完整栈轨迹到 stderr |
| `getStackTrace()` | StackTraceElement[] | 获取栈帧数组，可程序化分析 |
| `getCause()` | Throwable | 获取包装的根因异常 |

```java
public class ThrowableDemo {
    public static void main(String[] args) {
        try {
            int n = 10 / 0;
        } catch (ArithmeticException e) {
            System.out.println("getMessage: " + e.getMessage());    // / by zero
            System.out.println("toString: " + e.toString());        // java.lang.ArithmeticException: / by zero
            System.out.println("printStackTrace:");
            e.printStackTrace();   // 完整栈轨迹
        }
    }
}
```

> 📌 **生产规范**：日志框架（SLF4J）的 `log.error("xxx", e)` 会自动打印栈轨迹，**不要**再手动 `e.printStackTrace()`——它输出到 stderr，不受日志框架控制，无法归档、无法过滤级别、无法统一格式。

## 六、Objects.requireNonNull：参数校验

`java.util.Objects` 提供了静态校验方法，是 JDK 内置的参数校验利器。

```java
import java.util.Objects;

public class RequireNonNullDemo {
    public static void process(String name, Integer age) {
        // ✅ 不传消息
        Objects.requireNonNull(name);
        // ✅ 带消息，抛出时带上下文
        Objects.requireNonNull(age, "age 不能为 null");
        // ✅ 带消息 supplier（延迟构造，性能更好）
        Objects.requireNonNull(name, () -> "参数 " + name + " 不能为空");

        System.out.println("处理：" + name + ", " + age);
    }

    public static void main(String[] args) {
        process(null, 18);   // 抛 NullPointerException: name 不能为 null
    }
}
```

> 💡 相比手写 `if (x == null) throw new NullPointerException()`，`requireNonNull` 更简洁、语义更明确，JDK 源码、Spring 源码大量使用。

## 七、try-with-resources（Java 7+，重点⭐⭐）

凡是实现了 `AutoCloseable` 接口的资源（文件流、数据库连接、网络连接），都可用 try-with-resources **自动关闭**，替代 finally 手动 `close()`。Java 8 完全支持，是资源管理的标准写法。

```java
import java.io.FileInputStream;
import java.io.FileOutputStream;
import java.io.IOException;

public class TryWithResourcesDemo {
    // ❌ 旧写法：finally 手动关，又臭又长，还容易漏关
    public static void oldStyle() {
        FileInputStream fis = null;
        try {
            fis = new FileInputStream("a.txt");
            int data = fis.read();
        } catch (IOException e) {
            e.printStackTrace();
        } finally {
            if (fis != null) {
                try {
                    fis.close();   // close 本身也可能抛异常
                } catch (IOException e) {
                    e.printStackTrace();
                }
            }
        }
    }

    // ✅ try-with-resources：自动关闭，资源在 try 结束时自动 close
    public static void newStyle() {
        try (FileInputStream fis = new FileInputStream("a.txt");
             FileOutputStream fos = new FileOutputStream("b.txt")) {
            int data = fis.read();
            fos.write(data);
        } catch (IOException e) {
            e.printStackTrace();
        }
        // fis、fos 在这里已自动 close，即使中途抛异常也会关
    }

    // ✅ 自定义资源：实现 AutoCloseable
    static class MyResource implements AutoCloseable {
        @Override
        public void close() {
            System.out.println("MyResource 自动关闭");
        }
    }

    public static void main(String[] args) {
        try (MyResource r = new MyResource()) {
            System.out.println("使用资源");
        }  // 输出：使用资源 / MyResource 自动关闭
    }
}
```

> ⚠️ **资源关闭顺序**：多个资源按**声明逆序**关闭（后声明的先关）。try-with-resources 还会自动处理「被抑制异常」——try 块抛异常、close 也抛异常时，close 的异常会被 `addSuppressed` 附加到主异常，可通过 `getSuppressed()` 获取。

> 📌 **开发铁律**：所有 `AutoCloseable` 资源（InputStream、Connection、ResultSet、Statement）一律用 try-with-resources，杜绝资源泄漏。这是 Java 7+ 的标准写法，Java 8 完全支持。

## 八、多异常合并 catch（Java 7+）

多个异常处理逻辑相同时，可用 `|` 合并到一个 catch，避免重复代码。Java 8 完全支持。

```java
import java.io.IOException;
import java.sql.SQLException;

public class MultiCatchMergeDemo {
    public static void process() {
        try {
            doWork();
        } catch (IOException | SQLException e) {   // ✅ 合并捕获
            log(e);
            throw new RuntimeException("处理失败", e);  // 异常转译
        }
    }

    static void doWork() throws IOException, SQLException {}

    static void log(Exception e) {
        System.out.println("记录：" + e.getMessage());
    }
}
```

> 💡 合并 catch 中，变量 `e` 的编译类型是这些异常的**最近公共父类**，且是**隐式 final**，不能在 catch 块内重新赋值。

## 九、异常链 / 异常转译

底层异常（如 SQLException）不应直接抛给上层业务，应**包装转译**为业务异常，保留原始异常作为 cause，便于排查。

```java
public class ExceptionChainDemo {
    // 自定义业务异常
    static class BusinessException extends Exception {
        public BusinessException(String message, Throwable cause) {
            super(message, cause);   // ✅ 保留原始异常链
        }
    }

    // DAO 层：抛底层 SQLException
    static class UserDao {
        public void save() throws java.sql.SQLException {
            throw new java.sql.SQLException("主键冲突");
        }
    }

    // Service 层：捕获 SQLException，转译为 BusinessException
    static class UserService {
        public void register() throws BusinessException {
            try {
                new UserDao().save();
            } catch (java.sql.SQLException e) {
                // 异常转译：底层是 SQLException，对外暴露 BusinessException
                throw new BusinessException("用户注册失败", e);
            }
        }
    }

    public static void main(String[] args) {
        try {
            new UserService().register();
        } catch (BusinessException e) {
            e.printStackTrace();
            System.out.println("根因：" + e.getCause());  // SQLException: 主键冲突
        }
    }
}
```

> 💡 也可用 `Throwable.initCause(Throwable)` 或构造 `new Exception(msg, cause)` 建立异常链。`getCause()` 可逐层追溯根因。Spring 等框架大量用异常转译把 `SQLException` 转成 `DataAccessException`。

## 十、自定义异常

业务异常应自定义，继承 `Exception`（受检）或 `RuntimeException`（非受检），构造方法调用 `super(message)`。

```java
// 自定义受检业务异常
class BusinessException extends Exception {
    private int code;  // 业务错误码

    public BusinessException(int code, String message) {
        super(message);
        this.code = code;
    }

    public BusinessException(int code, String message, Throwable cause) {
        super(message, cause);
        this.code = code;
    }

    public int getCode() {
        return code;
    }
}

// 自定义非受检异常
class OrderNotFoundException extends RuntimeException {
    public OrderNotFoundException(String orderId) {
        super("订单不存在：" + orderId);
    }
}

// 使用
public class CustomExceptionDemo {
    public static void findOrder(String orderId) {
        if (!"ORD001".equals(orderId)) {
            throw new OrderNotFoundException(orderId);   // ✅ 抛自定义异常
        }
    }

    public static void main(String[] args) {
        findOrder("ORD999");   // 抛 OrderNotFoundException: 订单不存在：ORD999
    }
}
```

> 📌 **规范**：自定义异常通常继承 `RuntimeException`（非受检），避免调用方被迫到处 try-catch；提供错误码字段，便于前端/接口统一处理；构造方法务必调用 `super(message)` 或 `super(message, cause)`。

## ⚠️ 重点

### 重点 1：Error 不该 try ⭐

```java
try {
    // ❌ 没意义：OOM 后堆已满，catch 里的代码也分配不了对象
    doHugeMemoryWork();
} catch (OutOfMemoryError e) {
    e.printStackTrace();   // 救不回来
}
```

> ⚠️ `Error` 是 JVM 级故障，程序已无法正常工作，try 住也无意义。应通过排查内存泄漏、调整 JVM 参数、限制递归深度来预防。

### 重点 2：finally 一定执行（除 System.exit）⭐

```java
public static int test() {
    try {
        return 1;
    } finally {
        System.out.println("必执行");  // ✅ return 前执行
    }
}
```

> 💡 唯一不执行的情况：`System.exit(int)`、JVM 崩溃、当前线程被杀死、守护线程非正常退出。

### 重点 3：finally 中 return 会覆盖 try 的 return ⭐⭐

```java
public static int test() {
    try {
        return 1;
    } finally {
        return 2;   // ❌ 返回 2，吞掉 try 的 1
    }
}
```

> ⚠️ 这是开发大坑：finally 的 return 不仅覆盖返回值，还会**吞掉 try 块里未捕获的异常**。**永远别在 finally 里 return**。

### 重点 4：多个 catch 必须从小到大 ⭐

```java
try { ... }
catch (NullPointerException e) { }      // ✅ 子类在前
catch (RuntimeException e) { }         // ✅ 父类在后
catch (Exception e) { }                 // ✅ 顶层最后
// catch (RuntimeException e) { }       // ❌ 顺序反了，编译错误
```

### 重点 5：try-with-resources 必须用 ⭐⭐

```java
// ❌ 旧：手动 close，易漏
FileInputStream fis = new FileInputStream("a.txt");
try { ... } finally { fis.close(); }

// ✅ 新：自动 close
try (FileInputStream fis = new FileInputStream("a.txt")) { ... }
```

> 📌 所有 `AutoCloseable` 资源一律用 try-with-resources，这是 Java 8 的标准实践。

### 重点 6：不要 catch (Exception e) 一把梭 ⭐⭐

```java
try {
    doWork();
} catch (Exception e) {        // ❌ 太宽泛，吞掉所有异常
    e.printStackTrace();
}

// ✅ 捕获具体异常
try {
    doWork();
} catch (IOException e) {
    log.error("IO 失败", e);
    throw new BusinessException("文件读取失败", e);
} catch (SQLException e) {
    log.error("DB 失败", e);
    throw new BusinessException("数据库操作失败", e);
}
```

> ⚠️ `catch (Exception e)` 会把 `NullPointerException`、`ClassCastException` 等运行时异常也吞掉，掩盖真正的 bug。只捕获你预期并知道如何处理的异常。

### 重点 7：异常信息要有上下文 ⭐

```java
// ❌ 没上下文，出问题不知道是哪个订单
throw new RuntimeException("失败");

// ✅ 带业务上下文
throw new RuntimeException("订单 " + orderId + " 支付失败，金额=" + amount);
```

> 📌 异常信息要包含：**做什么、操作什么、关键参数值**，便于线上排查。日志同理。

### 重点 8：不要用异常做流程控制 ⭐⭐

```java
// ❌ 用异常判断字符串是否是数字
public static boolean isNumber(String s) {
    try {
        Integer.parseInt(s);
        return true;
    } catch (NumberFormatException e) {
        return false;
    }
}

// ✅ 用正则或工具方法
public static boolean isNumber(String s) {
    return s != null && s.matches("-?\\d+");
}
```

> ⚠️ 异常实例化、栈轨迹生成代价高（要 `fillInStackTrace`），用异常控制流程性能差且语义混乱。能用 if 判断就别用异常。

## 💻 实战案例

### 案例 1：电商自定义业务异常体系 ⭐⭐

真实电商后端通常有一套业务异常体系，配合错误码统一返回。

```java
// 业务异常基类
class BusinessException extends RuntimeException {
    private final int code;
    public BusinessException(int code, String message) {
        super(message);
        this.code = code;
    }
    public int getCode() { return code; }
}

// 订单不存在
class OrderNotFoundException extends BusinessException {
    public OrderNotFoundException(String orderId) {
        super(40001, "订单不存在：" + orderId);
    }
}

// 库存不足
class StockNotEnoughException extends BusinessException {
    public StockNotEnoughException(String sku, int need, int have) {
        super(40002, "库存不足：" + sku + " 需要" + need + " 实有" + have);
    }
}

// 金额异常
class InvalidAmountException extends BusinessException {
    public InvalidAmountException(double amount) {
        super(40003, "金额非法：" + amount);
    }
}

// 使用：下单流程
public class OrderService {
    public void placeOrder(String orderId, String sku, int qty, double amount) {
        // 参数校验：金额必须为正
        if (amount <= 0) {
            throw new InvalidAmountException(amount);
        }
        // 查订单
        if (!"ORD001".equals(orderId)) {
            throw new OrderNotFoundException(orderId);
        }
        // 查库存
        int stock = 10;
        if (qty > stock) {
            throw new StockNotEnoughException(sku, qty, stock);
        }
        System.out.println("下单成功");
    }

    public static void main(String[] args) {
        OrderService service = new OrderService();
        try {
            service.placeOrder("ORD999", "SKU001", 100, -50);
        } catch (BusinessException e) {
            // 统一返回前端：{code: 40003, message: "金额非法：-50.0"}
            System.out.println("code=" + e.getCode() + ", msg=" + e.getMessage());
        }
    }
}
```

> 💡 这套体系配合 Spring 的 `@ControllerAdvice` + `@ExceptionHandler`，就能实现「异常 → 统一 JSON 响应」，是后端统一异常处理的标准铺垫。

### 案例 2：DAO 层 SQLException → Service 层 BusinessException 异常转译 ⭐

```java
import java.sql.SQLException;

// DAO 层：抛底层异常
class UserDao {
    public void save(String name) throws SQLException {
        // 模拟主键冲突
        throw new SQLException("Duplicate entry '" + name + "' for key 'uk_name'");
    }
}

// Service 层：转译为业务异常
class UserService {
    public void register(String name) {
        try {
            new UserDao().save(name);
        } catch (SQLException e) {
            // ✅ 异常转译：底层 SQLException 包装成业务异常，保留 cause
            throw new BusinessException(50001, "用户注册失败：" + name, e);
        }
    }
}

// 业务异常带 cause
class BusinessException extends RuntimeException {
    private final int code;
    public BusinessException(int code, String message, Throwable cause) {
        super(message, cause);
        this.code = code;
    }
    public int getCode() { return code; }
}

public class ExceptionTranslateDemo {
    public static void main(String[] args) {
        try {
            new UserService().register("leo");
        } catch (BusinessException e) {
            System.out.println("业务异常：" + e.getMessage());
            System.out.println("根因：" + e.getCause());  // 追溯到 SQLException
        }
    }
}
```

> 📌 **分层异常转译**是 Java 后端的标准做法：DAO 层抛技术异常（SQLException、IOException），Service 层转译为业务异常，Controller 层统一处理。这样上层只关心业务，不耦合 JDBC 细节。

### 案例 3：try-with-resources 读写文件 ⭐

```java
import java.io.*;
import java.nio.charset.StandardCharsets;

public class FileCopyDemo {
    // ✅ 同时管理多个资源，自动逆序关闭
    public static void copy(String src, String dst) {
        try (FileInputStream fis = new FileInputStream(src);
             FileOutputStream fos = new FileOutputStream(dst);
             BufferedReader reader = new BufferedReader(
                 new InputStreamReader(fis, StandardCharsets.UTF_8));
             BufferedWriter writer = new BufferedWriter(
                 new OutputStreamWriter(fos, StandardCharsets.UTF_8))) {
            String line;
            while ((line = reader.readLine()) != null) {
                writer.write(line);
                writer.newLine();
            }
        } catch (IOException e) {
            throw new RuntimeException("文件拷贝失败：" + src + " -> " + dst, e);
        }
        // 四个资源全部自动关闭，无需 finally
    }

    public static void main(String[] args) {
        copy("input.txt", "output.txt");
    }
}
```

> ⚠️ 注意：嵌套装饰流（`new BufferedReader(new InputStreamReader(fis))`）时，只要把最外层放进 try-with-resources 即可，外层 close 会级联关闭内层。但更稳妥的做法是把每个独立资源都声明在 try 里。

### 案例 4：参数校验抛异常

```java
import java.util.Objects;

class UserDTO {
    private String username;
    private String email;
    private Integer age;

    public UserDTO(String username, String email, Integer age) {
        this.username = username;
        this.email = email;
        this.age = age;
    }

    // 校验方法：失败抛 IllegalArgumentException（运行时异常）
    public void validate() {
        Objects.requireNonNull(username, "用户名不能为空");
        Objects.requireNonNull(email, "邮箱不能为空");
        Objects.requireNonNull(age, "年龄不能为空");

        if (!email.matches("^[\\w.-]+@[\\w.-]+\\.\\w+$")) {
            throw new IllegalArgumentException("邮箱格式非法：" + email);
        }
        if (age < 0 || age > 150) {
            throw new IllegalArgumentException("年龄非法：" + age);
        }
    }
}

public class ValidateDemo {
    public static void main(String[] args) {
        UserDTO user = new UserDTO("leo", "leo@bad", -1);
        try {
            user.validate();
        } catch (IllegalArgumentException e) {
            System.out.println("校验失败：" + e.getMessage());
        }
    }
}
```

> 💡 实际项目中参数校验多用 Bean Validation（`@NotNull`、`@Size`、`@Email`），底层也是抛 `ConstraintViolationException`。理解手动校验是掌握框架校验的基础。

### 案例 5：金融计算异常处理

```java
import java.math.BigDecimal;

// 金融场景：金额计算必须处理溢出和非法输入
class FinanceService {
    // 转账
    public void transfer(String from, String to, BigDecimal amount) {
        // 参数校验
        if (from == null || to == null) {
            throw new IllegalArgumentException("账户不能为空");
        }
        if (amount == null || amount.compareTo(BigDecimal.ZERO) <= 0) {
            throw new InvalidAmountException(amount == null ? null : amount.doubleValue());
        }
        if (from.equals(to)) {
            throw new IllegalArgumentException("转入转出账户不能相同");
        }
        try {
            doTransfer(from, to, amount);
        } catch (ArithmeticException e) {
            // BigDecimal 除不尽时抛 ArithmeticException
            throw new BusinessException(50010, "金额计算精度异常", e);
        }
    }

    private void doTransfer(String from, String to, BigDecimal amount) {
        // 模拟除法未指定精度
        BigDecimal result = amount.divide(new BigDecimal("3"));
        System.out.println(from + " -> " + to + " : " + result);
    }
}

class BusinessException extends RuntimeException {
    private final int code;
    public BusinessException(int code, String message, Throwable cause) {
        super(message, cause);
        this.code = code;
    }
    public int getCode() { return code; }
}

class InvalidAmountException extends BusinessException {
    public InvalidAmountException(Double amount) {
        super(40003, "金额非法：" + amount);
    }
}

public class FinanceDemo {
    public static void main(String[] args) {
        try {
            new FinanceService().transfer("A001", "B002", new BigDecimal("100"));
        } catch (BusinessException e) {
            System.out.println("code=" + e.getCode() + ", msg=" + e.getMessage());
            if (e.getCause() != null) {
                System.out.println("根因：" + e.getCause());
            }
        }
    }
}
```

### 案例 6：统一异常处理铺垫（Spring @ExceptionHandler 思路）

```java
// 模拟 Spring 统一异常处理的核心思路
class GlobalExceptionHandler {
    // 处理业务异常
    public String handleBusiness(BusinessException e) {
        return "{\"code\":" + e.getCode() + ",\"message\":\"" + e.getMessage() + "\"}";
    }

    // 处理参数异常
    public String handleIllegalArg(IllegalArgumentException e) {
        return "{\"code\":400,\"message\":\"" + e.getMessage() + "\"}";
    }

    // 兜底：处理未知异常
    public String handleUnknown(Exception e) {
        return "{\"code\":500,\"message\":\"系统繁忙\"}";
    }
}

// 模拟 Controller
class OrderController {
    public String createOrder(String orderId) {
        try {
            // 业务逻辑
            if (!"ORD001".equals(orderId)) {
                throw new OrderNotFoundException(orderId);
            }
            return "{\"code\":200,\"message\":\"ok\"}";
        } catch (BusinessException e) {
            return new GlobalExceptionHandler().handleBusiness(e);
        } catch (IllegalArgumentException e) {
            return new GlobalExceptionHandler().handleIllegalArg(e);
        } catch (Exception e) {
            return new GlobalExceptionHandler().handleUnknown(e);
        }
    }
}

class BusinessException extends RuntimeException {
    private final int code;
    public BusinessException(int code, String message) { super(message); this.code = code; }
    public int getCode() { return code; }
}

class OrderNotFoundException extends BusinessException {
    public OrderNotFoundException(String orderId) { super(40001, "订单不存在：" + orderId); }
}

public class GlobalExceptionDemo {
    public static void main(String[] args) {
        System.out.println(new OrderController().createOrder("ORD999"));
        // {"code":40001,"message":"订单不存在：ORD999"}
    }
}
```

> 💡 Spring 的 `@ControllerAdvice` + `@ExceptionHandler` 就是把这套 try-catch 集中到一处，Controller 方法只抛异常、不写 catch，由全局处理器统一转 JSON。理解本例就能平滑过渡到 Spring 的统一异常处理。

## 🚀 新版本补充

### Java 9：try-with-resources 增强

Java 9 允许 try-with-resources 使用**已存在的 effectively final 变量**，不必在 try 里重新声明。

```java
// Java 9+ ✅
FileInputStream fis = new FileInputStream("a.txt");
try (fis) {   // 直接用已存在的变量（fis 不可再赋值）
    int data = fis.read();
} catch (IOException e) {
    e.printStackTrace();
}

// Java 8 ❌ 必须在 try 里声明新变量
try (FileInputStream fis2 = new FileInputStream("a.txt")) { ... }
```

> ⚠️ Java 8 不支持这种写法，了解即可。Java 9+ 中要求该变量是 effectively final（未重新赋值）。

### Java 9：StackWalker API

更高效的栈遍历 API，替代 `Throwable.getStackTrace()` 的高开销反射：

```java
// Java 9+
StackWalker walker = StackWalker.getInstance();
walker.forEach(frame -> System.out.println(frame.getClassName() + "#" + frame.getMethodName()));
```

> 💡 `try-with-resources`、多异常合并 catch、`Throwable.addSuppressed` 都是 Java 7 引入，Java 8 完全支持，属于基准内容，不在本节展开。

## 本章小结

| 知识点 | 要点 |
| :--- | :--- |
| 异常顶层 | Throwable，分 Error / Exception |
| Error | JVM 错误（OOM、StackOverflow），不该 try |
| 受检异常 | Exception 的非 RuntimeException 子类，必须处理 |
| 非受检异常 | RuntimeException 及其子类，可不处理 |
| 五个关键字 | try、catch、finally、throw、throws |
| throw vs throws | throw 抛对象（方法内），throws 声明（签名上） |
| 多个 catch | 子类 → 父类，父类放最后 |
| finally | 一定执行（除 System.exit），别在里面 return |
| Throwable 方法 | getMessage / toString / printStackTrace / getCause |
| try-with-resources | 自动关闭 AutoCloseable，Java 7+ 标准写法 |
| 多异常合并 catch | catch (A \| B e)，e 隐式 final |
| 异常链 | new Exception(msg, cause)，getCause 追溯 |
| 自定义异常 | 继承 Exception/RuntimeException，调 super(message) |
| 最佳实践 | 别用异常做流程、捕获具体异常、带上下文、资源用 TWR |

---

## 学习建议

1. **画一遍异常树**：拿纸画出 Throwable → Error / Exception → RuntimeException / 受检异常的继承关系，标出每类的代表异常。这张图是理解整个异常体系的地基，面试必考。
2. **敲一遍 try-catch-finally 的 return 坑**：把「finally 覆盖 return」「finally 吞异常」两个例子运行一遍，亲眼看到输出，比看十遍文字都深刻——这是开发高频踩坑点。
3. **用 try-with-resources 重写旧代码**：找一个用 finally 手动 close 的文件读写示例，改成 try-with-resources，体会「自动关闭 + 被抑制异常」的便利，养成肌肉记忆。
4. **写一套自定义业务异常**：照着电商案例，写 `BusinessException` + `OrderNotFoundException` + `StockNotEnoughException`，带错误码和 cause 构造，为后续学 Spring 统一异常处理打基础。
5. **理解「异常转译」的分层思想**：DAO 抛技术异常、Service 转业务异常、Controller 统一处理——这是 Java 后端的标准分层异常策略，务必吃透，后续 Spring 项目会反复用到。
