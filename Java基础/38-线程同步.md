# 线程同步

多线程并发执行能提升程序性能，但也带来了**线程安全问题**：当多个线程同时读写同一份共享数据时，如果不加控制，就会出现数据错乱、超卖、超支等诡异 bug。线程同步的核心目标，就是保证「共享数据在同一时刻只被一个线程操作」。

> 💡 在阅读本篇前，建议先看 [37-线程基础与线程创建](37-线程基础与线程创建.md)，理解线程的生命周期与基本用法，再来看同步机制会顺理成章。

---

## 一、线程安全问题

### 1.1 问题演示：多窗口卖票

经典的卖票案例：3 个窗口卖 100 张票，理想情况下票卖完正好剩 0 张，但多线程下会出现负数票。

```java
public class Ticket implements Runnable {
    private int tickets = 100;

    @Override
    public void run() {
        while (true) {
            if (tickets > 0) {
                try {
                    Thread.sleep(10);  // 模拟出票耗时，放大问题
                } catch (InterruptedException e) {
                    e.printStackTrace();
                }
                System.out.println(Thread.currentThread().getName()
                        + " 卖出第 " + tickets-- + " 张票");  // ❌ tickets-- 不是原子操作
            } else {
                break;
            }
        }
    }

    public static void main(String[] args) {
        Ticket t = new Ticket();
        new Thread(t, "窗口1").start();
        new Thread(t, "窗口2").start();
        new Thread(t, "窗口3").start();
    }
}
```

运行结果可能出现：

```
窗口2 卖出第 2 张票
窗口1 卖出第 1 张票
窗口3 卖出第 0 张票     ❌ 已经是 0 还在卖
窗口1 卖出第 -1 张票    ❌ 出现负数！
```

> ⚠️ `tickets--` 看似一行代码，实际包含三步：**读 → 减 → 写**。线程 A 读到 `tickets=1`，还没减，线程 B 也读到 `tickets=1`，两人都减一次，结果变成了 `-1`。这就是典型的**原子性问题**。

### 1.2 问题演示：银行取款超支

```java
public class Account {
    private double balance;  // 余额

    public void withdraw(double amount) {
        if (balance >= amount) {           // ① 判断余额
            try { Thread.sleep(10); }       // 模拟取款耗时
            catch (InterruptedException e) {}
            balance -= amount;             // ② 扣款
            System.out.println(Thread.currentThread().getName()
                    + " 取款 " + amount + "，剩余 " + balance);
        } else {
            System.out.println(Thread.currentThread().getName()
                    + " 余额不足");
        }
    }
}

// 余额 1000，两人同时各取 1000，结果都取成功，余额变 -1000  ❌
```

### 1.3 三大根源：原子性、可见性、有序性

| 特性 | 含义 | 破坏原因 |
| :--- | :--- | :--- |
| **原子性** | 一个或多个操作要么全执行要么全不执行，中间不能被打断 | `i++` 是读-改-写三步，多线程交错执行会丢更新 |
| **可见性** | 一个线程修改了共享变量，其他线程能立即看到 | 每个线程有自己的**工作内存（CPU 缓存）**，看不到主内存的最新值 |
| **有序性** | 程序执行的顺序与代码顺序一致 | 编译器和 CPU 为了优化会**指令重排**，单线程下不影响结果，多线程下会出问题 |

```java
// 可见性问题演示
public class VisibilityDemo {
    private static boolean running = true;  // 普通变量，无可见性保证

    public static void main(String[] args) throws InterruptedException {
        new Thread(() -> {
            while (running) {
                // 空循环：线程可能一直读工作内存中的旧值 running=true
            }
            System.out.println("子线程结束");
        }).start();

        Thread.sleep(1000);
        running = false;  // 主线程改了，子线程未必能看到  ❌
        System.out.println("主线程已修改 running=false");
    }
}
```

> 💡 **JMM（Java 内存 Model）** 规定：每个线程有自己的工作内存，共享变量存在主内存。线程对变量的操作：先从主内存读到工作内存 → 修改 → 再写回主内存。这个机制是可见性问题的根源。

## 二、synchronized 三种用法

`synchronized` 是 Java 内置的锁机制，是解决线程安全问题最常用的手段。

### 2.1 同步代码块

```java
synchronized (锁对象) {
    // 需要同步的代码
}
```

```java
public class TicketSyncBlock implements Runnable {
    private int tickets = 100;
    private Object lock = new Object();  // 专用锁对象

    @Override
    public void run() {
        while (true) {
            synchronized (lock) {  // ✅ 同步代码块，锁是 lock 对象
                if (tickets > 0) {
                    System.out.println(Thread.currentThread().getName()
                            + " 卖出第 " + tickets-- + " 张票");
                } else {
                    break;
                }
            }
        }
    }
}
```

> ⚠️ **锁对象必须是同一个**！如果每个线程用不同的锁对象，synchronized 就形同虚设。下面是常见错误：

```java
@Override
public void run() {
    while (true) {
        synchronized (new Object()) {  // ❌ 每次都是新对象，锁不住！
            // ...
        }
    }
}
```

### 2.2 同步方法

```java
public synchronized void method() {  // 锁是 this
    // 需要同步的代码
}
```

```java
public class TicketSyncMethod implements Runnable {
    private int tickets = 100;

    @Override
    public void run() {
        while (sell()) { }  // 循环调用同步方法
    }

    // ✅ 同步方法，锁是 this
    private synchronized boolean sell() {
        if (tickets > 0) {
            System.out.println(Thread.currentThread().getName()
                    + " 卖出第 " + tickets-- + " 张票");
            return true;
        }
        return false;
    }
}
```

> 💡 同步方法的锁是 `this`，即当前对象。所以**多个线程调用同一个对象的同步方法**才会互斥；如果每个线程用不同的对象实例，则不会互斥。

### 2.3 静态同步方法

```java
public static synchronized void method() {  // 锁是 Class 对象
    // 需要同步的代码
}
```

```java
public class TicketSyncStatic implements Runnable {
    private static int tickets = 100;  // 静态变量

    @Override
    public void run() {
        while (sell()) { }
    }

    // ✅ 静态同步方法，锁是 TicketSyncStatic.class
    private static synchronized boolean sell() {
        if (tickets > 0) {
            System.out.println(Thread.currentThread().getName()
                    + " 危出第 " + tickets-- + " 张票");
            return true;
        }
        return false;
    }
}
```

> 💡 静态方法没有 `this`，所以锁是**类的 Class 对象**（`XXClass.class`，全局唯一）。无论 new 多少个实例，静态同步方法都互斥。

### 2.4 三种用法对比与锁对象选择

| 用法 | 锁对象 | 适用场景 |
| :--- | :--- | :--- |
| 同步代码块 | 自己指定（任意对象 / this / Class / 专用锁） | 精确控制同步范围，性能最好 |
| 同步方法 | `this` | 整个方法体都需要同步 |
| 静态同步方法 | `XXClass.class` | 静态变量的同步 |

```java
public class LockChoiceDemo {
    private Object lock = new Object();  // ✅ 专用锁，职责单一

    public void method1() {
        synchronized (lock) { /* 临界区 A */ }  // 用专用锁
    }

    public void method2() {
        synchronized (this) { /* 临界区 B */ }  // 用 this
        // 注意：method1 和 method2 用的锁不同，不会互斥！
    }
}
```

> 📌 **锁对象选择规范**：
> - 优先用**专用锁对象**（`private final Object lock = new Object();`），职责清晰、避免误用。
> - 不要用 `String` 常量、`Integer` 缓存对象等做锁——它们可能被其他代码引用，造成意外互斥。

### 2.5 synchronized 底层原理

`synchronized` 的底层依赖**对象头中的 Mark Word** 和 **monitor（管程/监视器）**：

```
对象在堆中的内存布局：
┌─────────────────────────────┐
│  对象头（Header）            │
│  ├── Mark Word（锁状态、hash、GC 年龄等）│
│  └── 类型指针（指向 Class 元数据）       │
├─────────────────────────────┤
│  实例数据（字段值）          │
├─────────────────────────────┤
│  对齐填充（Padding）         │
└─────────────────────────────┘
```

同步代码块的字节码中，会看到 `monitorenter` 和 `monitorexit` 指令：

```
monitorenter      // 进入 monitor，count+1
// 临界区代码
monitorexit       // 退出 monitor，count-1，为 0 时释放锁
```

同步方法则是在方法的 `flags` 中加 `ACC_SYNCHRONIZED` 标志位，JVM 调用时自动加锁/释放。

**锁升级过程**（JDK 1.6 优化后）：

```
无锁 → 偏向锁 → 轻量级锁 → 重量级锁
        ↓         ↓           ↓
     单线程     CAS 自旋     操作系统互斥量
     重入      优化         （挂起线程，开销大）
```

| 锁状态 | 触发条件 | 性能 | 说明 |
| :--- | :--- | :--- | :--- |
| 偏向锁 | 首个线程进入 | 最高 | 在 Mark Word 记录线程 ID，下次同线程直接进入 |
| 轻量级锁 | 两个线程交替竞争 | 较高 | 用 CAS 自旋尝试获取，不阻塞线程 |
| 重量级锁 | 激烈竞争 | 较低 | 依赖 OS 的 mutex，未获取的线程挂起阻塞 |

> 💡 锁升级是**不可逆**的（偏向 → 轻量 → 重量，不能降级）。JVM 在运行期根据竞争情况自动升级，开发者无需手动干预。

## 三、volatile 关键字

`volatile` 是比 `synchronized` 更轻量的同步机制，主要解决**可见性**和**有序性**，但**不保证原子性**。

### 3.1 保证可见性

```java
public class VisibilityFixed {
    private static volatile boolean running = true;  // ✅ 加 volatile

    public static void main(String[] args) throws InterruptedException {
        new Thread(() -> {
            while (running) {  // ✅ 能及时读到主线程的修改
            }
            System.out.println("子线程结束");
        }).start();

        Thread.sleep(1000);
        running = false;  // 主线程修改后，子线程立刻可见
    }
}
```

> 💡 `volatile` 的可见性原理：写操作会**立刻刷回主内存**，并使其他线程工作内存中的副本**失效**，迫使他们重新从主内存读取。

### 3.2 禁止指令重排

编译器和 CPU 为了优化性能，会对指令进行重排（在不改变单线程语义的前提下）。但多线程下重排会出问题：

```java
public class Singleton {
    private static Singleton instance;  // ❌ 没 volatile，可能拿到未初始化的对象

    public static Singleton getInstance() {
        if (instance == null) {
            synchronized (Singleton.class) {
                if (instance == null) {
                    instance = new Singleton();  // 这行可能被重排！
                }
            }
        }
        return instance;
    }
}
```

`instance = new Singleton()` 实际分三步：

```
① 分配对象内存
② 初始化对象（调用构造方法）
③ 将引用指向内存地址
```

重排后可能变成 ①→③→②，其他线程在 ③ 之后、② 之前读到 `instance != null`，拿到的却是一个**未初始化完毕的半成品对象**。加 `volatile` 可禁止这种重排（详见后面 DCL 案例）。

### 3.3 不保证原子性

```java
public class VolatileNotAtomic {
    private static volatile int count = 0;

    public static void main(String[] args) throws InterruptedException {
        for (int i = 0; i < 10; i++) {
            new Thread(() -> {
                for (int j = 0; j < 1000; j++) {
                    count++;  // ❌ volatile 不保证原子性，仍然丢更新
                }
            }).start();
        }
        Thread.sleep(2000);
        System.out.println(count);  // 期望 10000，实际 < 10000
    }
}
```

> ⚠️ `count++` 是读-改-写三步，`volatile` 只保证「读」和「写」各自可见，但中间的「改」仍可能被其他线程打断。要保证原子性，得用 `synchronized`、`Lock` 或 `AtomicInteger`。

### 3.4 volatile vs synchronized 对比

| 对比项 | volatile | synchronized |
| :--- | :--- | :--- |
| 原子性 | ❌ 不保证 | ✅ 保证 |
| 可见性 | ✅ 保证 | ✅ 保证 |
| 有序性 | ✅ 保证（禁止重排） | ✅ 保证 |
| 阻塞线程 | 否 | 是 |
| 性能 | 高（轻量） | 较低（重量级） |
| 适用场景 | 状态标志位、DCL 单例 | 复合操作、临界区保护 |

> 📌 **选择口诀**：状态标志用 `volatile`，复合操作用 `synchronized`。

## 四、Lock 接口

`Lock` 是 JDK 1.5 引入的锁 API，比 `synchronized` 更灵活。核心实现是 `ReentrantLock`（可重入锁）。

### 4.1 ReentrantLock 基本用法

```java
import java.util.concurrent.locks.ReentrantLock;

public class TicketLock implements Runnable {
    private int tickets = 100;
    private final ReentrantLock lock = new ReentrantLock();  // 创建锁

    @Override
    public void run() {
        while (true) {
            lock.lock();  // ✅ 加锁
            try {
                if (tickets > 0) {
                    System.out.println(Thread.currentThread().getName()
                            + " 危出第 " + tickets-- + " 张票");
                } else {
                    break;
                }
            } finally {
                lock.unlock();  // ✅ 必须在 finally 释放！
            }
        }
    }
}
```

> ⚠️ **铁律**：`unlock()` 必须放在 `finally` 块中。否则一旦临界区抛异常，锁永远释放不了，其他线程全部死等。这是 `Lock` 相比 `synchronized` 的代价——`synchronized` 出异常会自动释放锁。

### 4.2 可重入特性

「可重入」指**同一线程**获取同一把锁后，可以再次获取而不会死锁：

```java
public class ReentrantDemo {
    private final ReentrantLock lock = new ReentrantLock();

    public void methodA() {
        lock.lock();
        try {
            System.out.println("A 执行");
            methodB();  // ✅ 同一线程再次获取同一把锁，不会死锁
        } finally { lock.unlock(); }
    }

    public void methodB() {
        lock.lock();
        try {
            System.out.println("B 执行");
        } finally { lock.unlock(); }
    }
}
```

> 💡 `synchronized` 也是可重入的，原理是 monitor 的计数器：每重入一次 count+1，退出一次 count-1，归零才释放。

### 4.3 tryLock()：尝试获取

```java
import java.util.concurrent.TimeUnit;
import java.util.concurrent.locks.ReentrantLock;

public class TryLockDemo {
    private final ReentrantLock lock = new ReentrantLock();

    public void tryDo() {
        if (lock.tryLock()) {  // ✅ 尝试获取，成功返回 true
            try {
                System.out.println("获取成功，执行业务");
            } finally { lock.unlock(); }
        } else {
            System.out.println("获取失败，做别的");  // 不会阻塞
        }
    }

    public void tryDoTimeout() {
        try {
            if (lock.tryLock(3, TimeUnit.SECONDS)) {  // ✅ 最多等 3 秒
                try {
                    System.out.println("3 秒内获取成功");
                } finally { lock.unlock(); }
            } else {
                System.out.println("3 秒内没拿到，放弃");
            }
        } catch (InterruptedException e) {
            System.out.println("等待时被中断");
        }
    }
}
```

> 💡 `tryLock()` 是 `synchronized` 做不到的——它能让线程「拿不到锁就去做别的事」，而不是死等。适合**限时尝试**场景，如限时抢购。

### 4.4 lockInterruptibly()：可中断

```java
public class InterruptibleLockDemo {
    private final ReentrantLock lock = new ReentrantLock();

    public void doWork() {
        try {
            lock.lockInterruptibly();  // ✅ 等待锁期间可被中断
            try {
                System.out.println("拿到锁，干活");
            } finally { lock.unlock(); }
        } catch (InterruptedException e) {
            System.out.println("等锁时被中断，放弃获取");  // 死锁破解利器
        }
    }
}
```

> 💡 `synchronized` 一旦等待锁就无法被中断，这是它的硬伤。`lockInterruptibly()` 可以让死锁等待被 `interrupt()` 打破。

### 4.5 公平锁与非公平锁

```java
new ReentrantLock();         // 默认非公平锁
new ReentrantLock(true);     // ✅ 公平锁：按 FIFO 顺序获取
new ReentrantLock(false);    // 非公平锁：允许插队
```

| 类型 | 特点 | 优点 | 缺点 |
| :--- | :--- | :--- | :--- |
| 公平锁 | 严格按等待顺序 | 不会饿死 | 吞吐量低 |
| 非公平锁 | 允许插队（默认） | 吞吐量高 | 可能饿死 |

> 💡 非公平锁吞吐量更高，原因是：线程刚释放锁时，如果恰好有新线程来，直接给它省去了唤醒阻塞线程的开销。实际开发默认用非公平锁即可。

### 4.6 Condition：await/signal

`Condition` 配合 `Lock` 实现 `await`/`signal`，功能等价于 `synchronized` 的 `wait`/`notify`，但更灵活（可有多组等待队列）。

```java
import java.util.concurrent.locks.Condition;
import java.util.concurrent.locks.ReentrantLock;

public class ConditionDemo {
    private final ReentrantLock lock = new ReentrantLock();
    private final Condition cond = lock.newCondition();  // 创建 Condition
    private boolean ready = false;

    public void waitForReady() throws InterruptedException {
        lock.lock();
        try {
            while (!ready) {
                cond.await();  // ✅ 释放锁并等待（类似 wait）
            }
            System.out.println("条件满足，继续执行");
        } finally { lock.unlock(); }
    }

    public void setReady() {
        lock.lock();
        try {
            ready = true;
            cond.signal();  // ✅ 唤醒一个等待线程（类似 notify）
        } finally { lock.unlock(); }
    }
}
```

> ⚠️ `await`/`signal` 也必须在 `lock` 持有期间调用，否则抛 `IllegalMonitorStateException`。详见 [39-线程通信](39-线程通信.md)。

## 五、死锁

### 5.1 什么是死锁

两个或多个线程互相持有对方需要的锁，导致全部阻塞，谁也无法继续。

```java
public class DeadLockDemo {
    private static final Object lockA = new Object();
    private static final Object lockB = new Object();

    public static void main(String[] args) {
        new Thread(() -> {
            synchronized (lockA) {
                System.out.println("线程1 拿到 A，等 B");
                try { Thread.sleep(100); } catch (Exception e) {}
                synchronized (lockB) {  // ❌ 等 B，但 B 在线程2 手里
                    System.out.println("线程1 拿到 A+B");
                }
            }
        }, "线程1").start();

        new Thread(() -> {
            synchronized (lockB) {
                System.out.println("线程2 拿到 B，等 A");
                try { Thread.sleep(100); } catch (Exception e) {}
                synchronized (lockA) {  // ❌ 等 A，但 A 在线程1 手里 → 死锁！
                    System.out.println("线程2 拿到 A+B");
                }
            }
        }, "线程2").start();
    }
}
```

> ⚠️ 死锁一旦发生，程序不会报错也不会退出，会**永久卡住**。排查方法：用 `jps` 查进程号，`jstack <pid>` 打印线程栈，会看到 `Found 1 deadlock`。

### 5.2 死锁的四个必要条件

| 条件 | 含义 |
| :--- | :--- |
| ① 互斥 | 锁同一时刻只能被一个线程持有 |
| ② 请求与保持 | 持有锁的同时还去请求新锁，不释放已有的 |
| ③ 不剥夺 | 锁不能被强制剥夺，只能主动释放 |
| ④ 循环等待 | 多个线程形成首尾相接的等待链 |

### 5.3 避免死锁

```java
// ✅ 方法1：统一锁的获取顺序（破坏循环等待）
// 所有线程都先获取 lockA 再获取 lockB，就不会死锁
new Thread(() -> {
    synchronized (lockA) {
        synchronized (lockB) { /* ... */ }
    }
}).start();
new Thread(() -> {
    synchronized (lockA) {   // ✅ 顺序一致
        synchronized (lockB) { /* ... */ }
    }
}).start();

// ✅ 方法2：用 tryLock() 带超时（破坏请求与保持/不剥夺）
public void safeAcquire() {
    try {
        if (lockA.tryLock(1, TimeUnit.SECONDS)) {
            try {
                if (lockB.tryLock(1, TimeUnit.SECONDS)) {
                    try { /* 业务 */ }
                    finally { lockB.unlock(); }
                }
            } finally { lockA.unlock(); }
        }
    } catch (InterruptedException e) {}
}
```

> 📌 **开发规范**：多锁场景下，**固定锁的获取顺序**是最简单有效的防死锁手段。

## 六、原子性问题的解决

针对 `i++` 这类原子性问题，有三种解决方案：

```java
import java.util.concurrent.atomic.AtomicInteger;
import java.util.concurrent.locks.ReentrantLock;

public class AtomicSolution {
    // 方案1：synchronized
    private int count1 = 0;
    public synchronized void inc1() { count1++; }  // ✅

    // 方案2：Lock
    private int count2 = 0;
    private final ReentrantLock lock = new ReentrantLock();
    public void inc2() {
        lock.lock();
        try { count2++; } finally { lock.unlock(); }  // ✅
    }

    // 方案3：AtomicInteger（推荐，JUC 原子类）
    private AtomicInteger count3 = new AtomicInteger(0);
    public void inc3() { count3.incrementAndGet(); }  // ✅ 底层 CAS，无锁
}
```

> 💡 `AtomicInteger` 基于 **CAS（Compare-And-Swap）** 实现，无锁性能高。CAS 详解见 [40-JUC 原子类与 CAS](40-JUC原子类与CAS.md)。

## ⚠️ 重点

### 重点 1：synchronized 三种用法与锁对象 ⭐⭐⭐

| 用法 | 语法 | 锁对象 |
| :--- | :--- | :--- |
| 同步代码块 | `synchronized(obj) { }` | `obj`（自己指定） |
| 同步方法 | `public synchronized void m()` | `this` |
| 静态同步方法 | `public static synchronized void m()` | `XXClass.class` |

> ⚠️ **核心**：同步的前提是**多个线程用同一个锁对象**。锁对象不同，互不互斥。

### 重点 2：synchronized 与 Lock 的选择 ⭐⭐⭐

| 对比项 | synchronized | Lock |
| :--- | :--- | :--- |
| 释放锁 | 自动（出异常/代码结束） | 手动（必须 finally 中 unlock） |
| 可中断 | ❌ | ✅ `lockInterruptibly()` |
| 超时获取 | ❌ | ✅ `tryLock(time)` |
| 公平性 | 只能非公平 | 可选公平/非公平 |
| 多条件 | 单一等待队列 | 多个 Condition |
| 性能 | JDK 1.6 后优化明显 | 灵活但代码更繁琐 |

> 📌 **选择建议**：简单同步用 `synchronized`（代码简洁、不怕忘释放）；需要超时/中断/多条件时用 `Lock`。

### 重点 3：volatile 不保证原子性 ⭐⭐

```java
private volatile int count = 0;
// count++ 仍不安全 ❌，volatile 只管可见性不管原子性
```

> ⚠️ `volatile` 适合**纯赋值**场景（`flag = true`），不适合**复合操作**（`count++`、`a = a + 1`）。

### 重点 4：DCL 单例必须加 volatile ⭐⭐⭐

```java
public class Singleton {
    // ✅ 必须 volatile，防止「初始化未完成」的指令重排
    private static volatile Singleton instance;

    public static Singleton getInstance() {
        if (instance == null) {                  // 第一次检查，提升性能
            synchronized (Singleton.class) {
                if (instance == null) {          // 第二次检查，防并发重复创建
                    instance = new Singleton(); // ✅ volatile 防止重排
                }
            }
        }
        return instance;
    }
}
```

> ⚠️ 这是面试高频考点。不加 `volatile`，`new Singleton()` 的「分配-初始化-赋值」可能被重排为「分配-赋值-初始化」，其他线程拿到未初始化的对象。

### 重点 5：Lock 必须在 finally 释放 ⭐⭐⭐

```java
lock.lock();
try {
    // 业务代码
} finally {
    lock.unlock();  // ✅ 必须放 finally
}
```

> ⚠️ 忘记 `unlock` 或放错位置，是 `Lock` 最致命的坑——一旦异常，锁永久不释放。

### 重点 6：锁对象不要用字符串/缓存对象 ⭐⭐

```java
synchronized("lock") { }       // ❌ 字符串常量池，全局共享，可能意外互斥
synchronized(Integer.valueOf(1)) { }  // ❌ Integer 缓存 -128~127，同上
synchronized(new Object()) { }  // ❌ 每次新对象，锁不住
private final Object lock = new Object();  // ✅ 专用锁
```

## 💻 实战案例

### 案例 1：多窗口卖票——三种同步方式对比 ⭐⭐⭐

电商秒杀、影院选座、车票售卖都是「多线程抢共享资源」场景。

```java
// 方式1：同步代码块
class TicketByBlock implements Runnable {
    private int tickets = 100;
    private final Object lock = new Object();
    public void run() {
        while (true) {
            synchronized (lock) {
                if (tickets <= 0) break;
                System.out.println(Thread.currentThread().getName()
                        + " 卖出第 " + tickets-- + " 张");
            }
        }
    }
}

// 方式2：同步方法
class TicketByMethod implements Runnable {
    private int tickets = 100;
    public void run() { while (sell()) {} }
    private synchronized boolean sell() {
        if (tickets <= 0) return false;
        System.out.println(Thread.currentThread().getName()
                + " 危出第 " + tickets-- + " 张");
        return true;
    }
}

// 方式3：ReentrantLock
class TicketByLock implements Runnable {
    private int tickets = 100;
    private final ReentrantLock lock = new ReentrantLock();
    public void run() {
        while (true) {
            lock.lock();
            try {
                if (tickets <= 0) break;
                System.out.println(Thread.currentThread().getName()
                        + " 危出第 " + tickets-- + " 张");
            } finally { lock.unlock(); }
        }
    }
}
```

### 案例 2：银行取款线程安全 ⭐⭐⭐

金融场景：夫妻共用一个账户，同时取款必须保证余额正确。

```java
import java.util.concurrent.locks.ReentrantLock;

public class Account {
    private double balance;
    private final ReentrantLock lock = new ReentrantLock();  // 账户自带锁

    public Account(double balance) { this.balance = balance; }

    public void withdraw(String name, double amount) {
        lock.lock();
        try {
            if (balance >= amount) {
                try { Thread.sleep(10); } catch (InterruptedException e) {}
                balance -= amount;
                System.out.println(name + " 取款 " + amount + "，余额 " + balance);
            } else {
                System.out.println(name + " 余额不足，当前 " + balance);
            }
        } finally { lock.unlock(); }
    }

    public double getBalance() { return balance; }

    public static void main(String[] args) throws InterruptedException {
        Account acc = new Account(1000);
        Thread husband = new Thread(() -> acc.withdraw("丈夫", 800), "丈夫");
        Thread wife = new Thread(() -> acc.withdraw("妻子", 800), "妻子");
        husband.start(); wife.start();
        husband.join(); wife.join();
        System.out.println("最终余额：" + acc.getBalance());  // 200 或 1000，不会 -600
    }
}
```

### 案例 3：单例双重检查锁（DCL + volatile）⭐⭐⭐

后台系统配置管理器、数据库连接池等常用单例。

```java
public class ConfigManager {
    // ✅ volatile 防止指令重排，DCL 双重检查提升性能
    private static volatile ConfigManager instance;

    private ConfigManager() { /* 加载配置 */ }

    public static ConfigManager getInstance() {
        if (instance == null) {                    // 第一次检查：无锁快速判断
            synchronized (ConfigManager.class) {
                if (instance == null) {            // 第二次检查：防并发重复创建
                    instance = new ConfigManager();
                }
            }
        }
        return instance;
    }
}
```

> 📌 DCL 是单例模式的标准写法，面试必考。`volatile` 不是为了可见性（`synchronized` 已保证），而是为了**禁止 `new` 的指令重排**。

### 案例 4：死锁演示与避免 ⭐⭐

```java
import java.util.concurrent.TimeUnit;
import java.util.concurrent.locks.ReentrantLock;

public class DeadLockAvoid {
    private static final Object lockA = new Object();
    private static final Object lockB = new Object();

    // ❌ 危险写法：不同顺序获取多把锁，可能死锁
    public static void badMethod() {
        new Thread(() -> {
            synchronized (lockA) {
                sleep(100);
                synchronized (lockB) { System.out.println("T1 done"); }
            }
        }).start();
        new Thread(() -> {
            synchronized (lockB) {
                sleep(100);
                synchronized (lockA) { System.out.println("T2 done"); }
            }
        }).start();
    }

    // ✅ 安全写法：统一顺序获取
    public static void goodMethod() {
        new Thread(() -> acquireBoth()).start();
        new Thread(() -> acquireBoth()).start();
    }

    private static void acquireBoth() {
        synchronized (lockA) {      // ✅ 都先 A 后 B
            synchronized (lockB) {
                System.out.println(Thread.currentThread().getName() + " done");
            }
        }
    }

    // ✅ 用 tryLock 超时避免死锁
    private static void safeAcquire() {
        ReentrantLock la = new ReentrantLock();
        ReentrantLock lb = new ReentrantLock();
        try {
            if (la.tryLock(1, TimeUnit.SECONDS)) {
                try {
                    if (lb.tryLock(1, TimeUnit.SECONDS)) {
                        try { System.out.println("两把都拿到"); }
                        finally { lb.unlock(); }
                    }
                } finally { la.unlock(); }
            }
        } catch (InterruptedException e) {}
    }

    private static void sleep(long ms) {
        try { Thread.sleep(ms); } catch (InterruptedException e) {}
    }
}
```

### 案例 5：ReentrantLock 实现生产者消费者 ⭐⭐

```java
import java.util.LinkedList;
import java.util.Queue;
import java.util.concurrent.locks.Condition;
import java.util.concurrent.locks.ReentrantLock;

public class ProducerConsumerByLock {
    private final Queue<String> warehouse = new LinkedList<>();
    private final int capacity = 10;
    private final ReentrantLock lock = new ReentrantLock();
    private final Condition notFull = lock.newCondition();
    private final Condition notEmpty = lock.newCondition();

    public void produce(String item) throws InterruptedException {
        lock.lock();
        try {
            while (warehouse.size() == capacity) {
                notFull.await();  // 仓库满，等消费者取走
            }
            warehouse.add(item);
            System.out.println("生产 " + item + "，库存 " + warehouse.size());
            notEmpty.signal();  // 通知消费者有货了
        } finally { lock.unlock(); }
    }

    public String consume() throws InterruptedException {
        lock.lock();
        try {
            while (warehouse.isEmpty()) {
                notEmpty.await();  // 仓库空，等生产者生产
            }
            String item = warehouse.poll();
            System.out.println("消费 " + item + "，库存 " + warehouse.size());
            notFull.signal();  // 通知生产者有空位
            return item;
        } finally { lock.unlock(); }
    }
}
```

> 💡 这里用两个 `Condition`（`notFull`、`notEmpty`）分别唤醒「对方」，比 `synchronized` 的 `notifyAll` 精准——不会误唤醒同类线程。

## 🚀 新版本补充

### Java 5：ReentrantLock 与 Lock 接口

`Lock` 接口本身就是 Java 5 引入的，但已属于 Java 8 基准内容，放在正文讲解。

### Java 8：StampedLock（补充了解）

```java
import java.util.concurrent.locks.StampedLock;

public class StampedLockDemo {
    private final StampedLock sl = new StampedLock();
    private double x, y;

    // 写锁
    public void move(double dx, double dy) {
        long stamp = sl.writeLock();
        try { x += dx; y += dy; }
        finally { sl.unlockWrite(stamp); }
    }

    // 乐观读：不加锁，读多写少时性能极高
    public double distance() {
        long stamp = sl.tryOptimisticRead();
        double curX = x, curY = y;
        if (!sl.validate(stamp)) {       // 读期间有写操作？升级为悲观读
            stamp = sl.readLock();
            try { curX = x; curY = y; }
            finally { sl.unlockRead(stamp); }
        }
        return Math.sqrt(curX * curX + curY * curY);
    }
}
```

> 💡 `StampedLock` 提供乐观读，在读多写少场景性能优于 `ReentrantLock`。但它是**不可重入**的，同线程递归获取会死锁。

### Java 14：synchronized 的性能已大幅优化

JDK 14+ 对 `synchronized` 的偏向锁、轻量级锁做了持续优化，现代 JVM 下 `synchronized` 与 `ReentrantLock` 性能差距已很小。简单场景优先用 `synchronized`。

## 本章小结

| 知识点 | 要点 |
| :--- | :--- |
| 线程安全三性 | 原子性、可见性、有序性 |
| synchronized 代码块 | `synchronized(obj){}`，锁是 obj |
| synchronized 方法 | `public synchronized void m()`，锁是 this |
| synchronized 静态方法 | 锁是 XXClass.class |
| synchronized 底层 | Mark Word + monitor，锁升级：偏向→轻量→重量 |
| volatile | 保证可见性 + 禁止重排，不保证原子性 |
| ReentrantLock | `lock()/unlock()`，必须 finally 释放 |
| tryLock | 尝试获取，可带超时 |
| 公平锁 | `new ReentrantLock(true)`，按 FIFO |
| Condition | `await/signal`，替代 wait/notify，可多条件 |
| 死锁四条件 | 互斥、请求保持、不剥夺、循环等待 |
| 原子性方案 | synchronized / Lock / AtomicInteger |

## 学习建议

1. **先跑出 bug 再修复**：把卖票案例不加锁跑一遍，亲眼看到负数票，再依次用三种同步方式修复，理解会深刻十倍。
2. **死锁要会排查**：写一个死锁程序，用 `jps` + `jstack` 排查，看到 `Found 1 deadlock` 输出——这是生产环境处理死锁的核心技能。
3. **volatile 的边界要清晰**：记住「状态标志用 volatile，复合操作用锁」。自己写 `volatile int count` 的 `count++` 跑出错误结果，比背十遍定义都管用。
4. **DCL 单例背下来**：双重检查锁 + volatile 是面试高频，务必能默写，并说清楚 `volatile` 在这里防的是「new 对象的指令重排」。
5. **对比着学 synchronized 与 Lock**：两者是同质工具，列出「自动释放 vs 手动释放」「不可中断 vs 可中断」等对比表，理解它们的取舍，而不是死记语法。
