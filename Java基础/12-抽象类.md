# 抽象类

如果说**继承**解决的是「代码复用」，那么**抽象类**解决的是另一件更本质的事：**规范**。当父类知道「每个子类都必须会做某件事」，却无法替子类决定「具体怎么做」时，就把这个方法声明成**抽象方法**，把类声明成**抽象类**——父类只规定「必须有什么」，把「具体怎么写」强制交给子类。这一句话就是抽象类的全部价值：**用编译期检查，逼着子类把该实现的方法实现掉**。

`abstract` 是从「写能跑的代码」迈向「写有约束的设计」的第一步。它是模板方法模式的基础，也是 JDK 里 `AbstractList`、`AbstractMap`、`InputStream`、`HttpServlet` 等一大批基础设施的实现方式。真正读懂框架源码，绕不开它。

> 💡 本篇是 [11-继承与final](11-继承与final.md) 中「抽象类」一节的展开与深化。如果对 `extends`、`super`、方法重写、构造方法链还不熟，建议先回看那一篇，否则抽象类的「构造方法为什么存在」「为什么必须重写」会很难理解。学完本篇再进入 [13-多态](13-多态.md)，你会更容易体会到「父类引用调用抽象方法」背后的动态绑定。

## 一、为什么需要抽象类

### 1.1 一个「父类写不出来」的场景

电商系统要计算订单金额，商品有图书、电子产品、生鲜三类。它们都有名称、价格，都需要「算总价」，但算法各不相同：

- 图书：单价 × 数量，从不打折；
- 电子产品：满 3 件打 9 折；
- 生鲜：一律 95 折。

用继承来抽取共性，父类 `Product` 该怎么写 `calcTotal()`？

```java
class Product {
    protected String name;
    protected double price;

    public double calcTotal(int quantity) {
        return 0;    // ❓ 返回 0 显然不对，但父类根本不知道该怎么算
    }
}
```

### 1.2 用普通父类硬写的三个问题

**问题 1：父类的实现是「假的」，而且会传染。**

`Product` 给出了 `return 0`，可它没有任何业务含义。一旦某个子类忘了重写，程序不会报错，而是安静地算出 0 元——线上事故往往就是这么来的。

```java
class Toy extends Product {
    // 忘了重写 calcTotal —— 编译完全通过
}
System.out.println(new Toy("玩具", 50).calcTotal(2));   // 0.0，无人报警
```

**问题 2：父类自己可以被 `new`，语义荒谬。**

「一个不知道如何计价的商品」在业务上并不存在，但 `new Product()` 是合法的：

```java
Product p = new Product();     // 编译通过，业务上毫无意义
```

**问题 3：无法强制「子类必须实现」。**

父类没有办法表达「你必须实现我」。文档里写「请子类重写」是约束不了人的，只有编译器能。

### 1.3 抽象类的定位：一张「必须填完的表格」

抽象类就是那张表格：

- **父类填好的部分**（普通方法、成员变量、构造方法）——子类直接继承复用；
- **父类空着的部分**（抽象方法）——子类必须填写，不填就交不了卷（编译不过）。

```java
abstract class Product {
    protected String name;
    protected double price;

    public abstract double calcTotal(int quantity);   // 只给签名，不给实现
}
```

一句话对比：

| | 普通父类 | 抽象类 |
| :--- | :--- | :--- |
| 能不能 `new` | 能（可能没意义） | **不能** |
| 子类是否必须重写某方法 | 不能强制 | **能，编译期强制** |
| 父类方法能否「暂时不实现」 | 只能返回假值或抛异常 | **可以只声明** |
| 设计意图 | 「这是一个可用的类」 | 「这是一个**未完成的模板**」 |

> 💡 抽象类不是「不能用的类」，而是「**不能直接用、只能被继承后使用**的类」。它是为继承而生的。

## 二、抽象方法与抽象类的语法

### 2.1 abstract 修饰方法

抽象方法只有方法声明，**没有方法体**，用分号结尾：

```java
public abstract double calcTotal(int quantity);   // ✅ 抽象方法
```

只要类里出现一个抽象方法，这个类**必须**用 `abstract` 修饰，否则编译报错：

```java
class Product {
    public abstract double calcTotal(int quantity);   // ❌ 编译错误
}
// 报错：Product is not abstract and does not override abstract method calcTotal(int) in Product
```

### 2.2 abstract 修饰类

```java
abstract class Product {          // 抽象类
    private String name;

    public Product(String name) {  // ✅ 抽象类可以有构造方法
        this.name = name;
    }

    public String getName() {
        return name;
    }

    public abstract double calcTotal(int quantity);   // 抽象方法

    public void printBill(int quantity) {             // ✅ 普通方法
        System.out.println(name + " 应付：" + calcTotal(quantity));
    }
}
```

### 2.3 语法规则速查

| 位置 | 能否用 `abstract` | 说明 |
| :--- | :---: | :--- |
| 类（顶层/成员内部） | ✅ | 抽象类 |
| 方法（实例） | ✅ | 抽象方法，无方法体 |
| 方法（`static`） | ❌ | `abstract static` 非法——静态方法不参与多态 |
| 方法（`private`） | ❌ | 私有方法子类看不见，无法实现 |
| 方法（`final`） | ❌ | `final` 禁止重写，与「必须重写」矛盾 |
| 方法（`native`） | ❌ | 二者都「没有方法体」，选一个 |
| 成员变量 | ❌ | `abstract` 只能修饰类和方法 |
| 构造方法 | ❌ | 构造方法不能被重写，谈不上抽象 |
| 局部变量 / 代码块 | ❌ | 语法不支持 |

### 2.4 抽象类的内部构成：它什么都能有

抽象类**除了不能实例化，和普通类的成员构成完全一样**。这一点常被误解成「抽象类里只能有抽象方法」：

```java
abstract class AbstractTemplate {
    // 1. 成员变量（实例状态）
    protected int retryCount = 3;

    // 2. 静态常量
    public static final String VERSION = "1.0";

    // 3. 构造方法（供子类 super 调用）
    protected AbstractTemplate() {
        System.out.println("模板初始化");
    }

    // 4. 抽象方法
    public abstract void run();

    // 5. 普通实例方法（复用逻辑）
    public void log(String msg) {
        System.out.println("[" + VERSION + "] " + msg);
    }

    // 6. 静态方法
    public static AbstractTemplate of(AbstractTemplate t) {
        return t;
    }

    // 7. 静态代码块 / 实例代码块
    static { System.out.println("静态代码块"); }
    { System.out.println("实例代码块"); }

    // 8. 成员内部类
    class Helper { }
}
```

> 💡 **记忆锚点**：抽象类 = 普通类 − `new` + 抽象方法。别的都有。

## 三、抽象类的五条硬规则

### 3.1 规则一：不能实例化，但可以声明引用

```java
Product p = new Product("手机", 3999);   // ❌ 编译错误：Product is abstract; cannot be instantiated

Product p = new Phone("手机", 3999);     // ✅ 父类引用指向子类对象（多态）
Product[] cart = new Product[3];         // ✅ 数组可以，元素装子类对象
```

> 💡 「不能 `new`」限制的是**对象创建**，不是**类型使用**。抽象类作为类型（参数、返回值、数组元素、泛型实参）完全正常。

### 3.2 规则二：可以有构造方法，而且一定先执行 ⭐

很多人疑惑：既然不能 `new`，要构造方法干什么？

答案是：**构造方法是给子类用的**。子类对象创建时，必须先初始化继承自父类的那部分状态，而这段初始化代码就写在父类构造方法里。

```java
abstract class Animal {
    protected final String name;

    protected Animal(String name) {
        this.name = name;
        System.out.println("Animal 构造：" + name);
    }
}

class Dog extends Animal {
    private final String breed;

    Dog(String name, String breed) {
        super(name);                          // 必须显式调用：父类没有无参构造
        this.breed = breed;
        System.out.println("Dog 构造：" + breed);
    }
}

new Dog("旺财", "柴犬");
// Animal 构造：旺财
// Dog 构造：柴犬
```

如果抽象父类**只有**带参构造，子类不写 `super(...)` 就直接编译失败：

```java
class Cat extends Animal {
    Cat(String name) {
        // ❌ 编译错误：Animal 中没有无参构造
    }
}
```

> 💡 这与普通父类完全一致，规则来自 [11-继承与final](11-继承与final.md) 的「构造方法链」。

### 3.3 规则三：子类必须重写全部抽象方法，否则子类也要 abstract

```java
class Phone extends Product {
    Phone(String name, double price) { super(name, price); }

    @Override
    public double calcTotal(int quantity) {
        return price * quantity;
    }
}

class Tablet extends Product {
    // ❌ 编译错误：Tablet is not abstract and does not override abstract method calcTotal(int)
}
```

不想实现，就把「实现的责任」继续往下传：

```java
abstract class DigitalProduct extends Product {   // ✅ 自己不实现，声明成抽象类即可
    DigitalProduct(String name, double price) { super(name, price); }
}
```

这就是抽象类的**传递性**：抽象方法会沿着继承链一路「催债」，直到某个具体类把它实现为止。

### 3.4 规则四：abstract 不能与 private / static / final / native 共存

| 组合 | 是否合法 | 原因 |
| :--- | :---: | :--- |
| `abstract` + `private` | ❌ | 子类看不见，永远无法重写 |
| `abstract` + `static` | ❌ | 静态方法属于类本身，不参与动态绑定 |
| `abstract` + `final` | ❌ | `final` 禁止重写，与抽象方法要求重写冲突 |
| `abstract` + `native` | ❌ | 二者都表示「无方法体」，语义重复 |
| `abstract` + `synchronized` | ❌ | 无方法体，谈不上加锁 |
| `abstract` + `protected/public/包级` | ✅ | 抽象方法可以是这三种访问权限 |
| `abstract` 类 + `final` | ❌ | `final abstract class` 非法 |

### 3.5 规则五：抽象类可以一个抽象方法都没有

```java
abstract class Constants {
    public static final int MAX_SIZE = 100;

    private Constants() { }      // 私有构造 + abstract 有点矛盾，见下方说明
}
```

语法完全允许，但意义仅剩「禁止被实例化」。这种情况通常直接用 `final` 类 + 私有构造（工具类写法）更清晰：

```java
final class Constants {
    public static final int MAX_SIZE = 100;
    private Constants() { }
}
```

> 💡 一个没有抽象方法的抽象类，唯一站得住脚的理由是：**未来可能新增抽象方法**，或**要求子类才能被使用**（如框架的基类）。如果只是「不想让人 new」，用私有构造更准确。

## 四、抽象类与多态：真正的威力所在

### 4.1 父类引用调用抽象方法

抽象类的抽象方法，调用时遵循多态的「编译看左，运行看右」：

```java
abstract class Shape {
    public abstract double area();

    public void print() {
        // 这里调用抽象方法，运行时执行的是子类实现
        System.out.printf("%s 面积：%.2f%n", getClass().getSimpleName(), area());
    }
}

class Circle extends Shape {
    private final double r;
    Circle(double r) { this.r = r; }
    @Override public double area() { return Math.PI * r * r; }
}

class Square extends Shape {
    private final double side;
    Square(double side) { this.side = side; }
    @Override public double area() { return side * side; }
}

Shape s = new Circle(2);
s.print();     // Circle 面积：12.57  ← 执行的是 Circle.area()
```

**关键点**：`Shape.print()` 这份代码只写了一次，却能服务于未来任意多个子类。这就是抽象类带来的**扩展性**——新增 `Triangle` 不需要改 `print()` 一行代码。

### 4.2 抽象类做参数和返回值：统一的 API 边界

```java
// 参数用抽象类型，任何子类都能传进来
public static double totalArea(Shape[] shapes) {
    double sum = 0;
    for (Shape s : shapes) {
        sum += s.area();          // 不需要 instanceof，不需要强转
    }
    return sum;
}

// 返回值用抽象类型，内部决定返回哪个子类
public static Shape create(String type) {
    switch (type) {
        case "circle": return new Circle(1);
        case "square": return new Square(2);
        default: throw new IllegalArgumentException("未知类型：" + type);
    }
}
```

> 💡 **面向抽象编程**：方法签名里出现的是抽象类型而非具体类型，调用方就与具体实现解耦了。这是工厂模式、策略模式、依赖注入共同的思想基础。

### 4.3 抽象类 + 接口：既继承又实现

一个类只能继承一个父类，但可以实现多个接口。所以常见写法是：**抽象类继承一个父类、同时实现若干接口**，把两者能力叠加。

```java
interface Loggable {
    void log(String msg);
}

abstract class BaseService implements Loggable {   // 抽象类实现接口
    protected String serviceName() {
        return getClass().getSimpleName();
    }

    @Override
    public void log(String msg) {                  // 接口方法在这里实现，子类直接复用
        System.out.println("[" + serviceName() + "] " + msg);
    }

    public abstract void execute();
}

class OrderService extends BaseService {
    @Override
    public void execute() {
        log("创建订单完成");       // 直接复用父类对接口的实现
    }
}
```

### 4.4 适配器思路：抽象类「空实现」接口，子类只挑需要的

当一个接口方法很多、而实现类通常只关心其中一两个时，可以用一个抽象类把所有方法**空实现**，子类按需覆盖：

```java
interface MouseListener {
    void onClick();
    void onDoubleClick();
    void onRightClick();
    void onMove();
}

// 抽象适配器：把所有方法都做了空实现
abstract class MouseAdapter implements MouseListener {
    @Override public void onClick() { }
    @Override public void onDoubleClick() { }
    @Override public void onRightClick() { }
    @Override public void onMove() { }
}

// 子类只关心点击
class MyButton extends MouseAdapter {
    @Override public void onClick() { System.out.println("按钮被点击"); }
}
```

> 💡 JDK 里 `java.awt.event.MouseAdapter`、`KeyAdapter` 就是这个套路——用抽象类把接口「稀释」成可选覆盖。

## 五、抽象类 vs 接口：到底该用哪个

### 5.1 语法差异对照表

| 维度 | 抽象类 | 接口 |
| :--- | :--- | :--- |
| 关键字 | `abstract class` | `interface` |
| 继承/实现 | `extends`（单继承） | `implements`（多实现） |
| 构造方法 | ✅ 有 | ❌ 没有 |
| 实例成员变量 | ✅ 有（可读写） | ❌ 只能是 `public static final` 常量 |
| 普通方法 | ✅ 有方法体 | Java 7 前不能有；Java 8+ 可用 `default` / `static` |
| 抽象方法权限 | `public` / `protected` / 包级 | 隐式 `public` |
| 状态（字段）复用 | ✅ 核心优势 | ❌ 做不到 |
| 设计语义 | **is-a**：是什么 | **can-do**：能做什么 |
| 典型用途 | 模板方法、基类、复用代码 | 契约、能力标记、解耦 |

### 5.2 语义上的根本区别

```java
abstract class Bird {            // 鸟「是」动物 —— is-a
    protected String name;
    public abstract void move();
}

interface Flyable {              // 「能」飞 —— can-do，飞机、超人也能实现
    void fly();
}

class Sparrow extends Bird implements Flyable {
    @Override public void move() { System.out.println("跳跃前进"); }
    @Override public void fly() { System.out.println("振翅飞行"); }
}
```

「鸟」用抽象类，因为麻雀**是**鸟，且共享「有名字」这个状态；「会飞」用接口，因为飞机也会飞，但它不是鸟。

### 5.3 选型决策清单

按顺序问自己四个问题：

1. **子类之间需要共享状态（字段）或已实现的方法吗？** → 需要，倾向抽象类。
2. **希望约束「必须是什么」还是「必须能做什么」？** → 前者抽象类，后者接口。
3. **未来可能被完全无关的类复用这套能力吗？** → 可能，用接口（Java 单继承，抽象类会占掉唯一的继承名额）。
4. **需要定义一组固定的流程骨架，让子类填细节吗？** → 抽象类（模板方法模式）。

### 5.4 最佳实践：两者组合

JDK 集合框架是教科书级示范——**接口定义契约，抽象类提供骨架，具体类填空**：

```
Iterable → Collection（接口）
              ↓
        AbstractCollection（抽象类，实现了 size()/isEmpty()/contains() 等通用逻辑）
              ↓
        AbstractList（抽象类，实现 get() 相关的通用逻辑，留出 get(int)/size() 给子类）
              ↓
        ArrayList（具体类，只实现真正需要定制的部分）
```

| 抽象类 | 配套接口 | 留给子类的抽象方法 |
| :--- | :--- | :--- |
| `AbstractCollection` | `Collection` | `iterator()`、`size()` |
| `AbstractList` | `List` | `get(int)` |
| `AbstractMap` | `Map` | `entrySet()` |
| `InputStream` | — | `read()` |
| `HttpServlet` | — | `doGet()` / `doPost()` |

> 💡 这种「接口 + 抽象骨架类」的模式在 Spring 里随处可见（`AbstractApplicationContext`、`AbstractBeanFactory`）。自己写框架或中间件时，也建议对外暴露接口、对内提供抽象基类。

## ⚠️ 重点

### 重点 1：抽象类不能 new，但有构造方法、能声明引用、能进数组 ⭐⭐

```java
abstract class Animal { }

Animal a = new Animal();        // ❌ 编译错误
Animal a = new Dog();           // ✅ 多态
Animal[] arr = new Animal[3];   // ✅ 数组元素默认 null
arr[0] = new Dog();             // ✅
boolean b = a instanceof Animal;// ✅ 类型判断正常
```

**三句话记住**：
1. 不能创建**抽象类的实例**；
2. 可以作为**类型**使用；
3. 构造方法存在，只为**子类**服务。

### 重点 2：抽象方法不能是 private / static / final ⭐

```java
abstract class Bad {
    private abstract void a();    // ❌ illegal combination of modifiers: 'abstract' and 'private'
    static abstract void b();     // ❌ illegal combination of modifiers: 'abstract' and 'static'
    final abstract void c();      // ❌ illegal combination of modifiers: 'abstract' and 'final'
}
```

原因一句话：**抽象方法的唯一使命是「被子类重写」，任何阻止重写的修饰符都与之冲突**；而 `static` 方法不参与动态绑定，抽象毫无意义。

### 重点 3：抽象父类的构造方法里调用抽象方法，是个陷阱 ⭐⭐

```java
abstract class Base {
    Base() {
        init();                   // ⚠️ 此时子类字段还未初始化
    }
    abstract void init();
}

class Sub extends Base {
    private int value = 100;      // 初始化动作发生在 super() 返回之后

    @Override
    void init() {
        System.out.println("value = " + value);   // 打印 0，不是 100
    }
}

new Sub();     // value = 0
```

**执行顺序**：`Sub()` → `super()` → `Base()` 里调 `init()`（此时 `Sub.value` 仍是默认值 0）→ 回到 `Sub()` 执行 `value = 100`。

> 💡 结论：**构造方法里只做「自己类」的初始化，永远不要调用可被重写的方法**。Effective Java 第 19 条讲的就是这件事。

### 重点 4：别忘了给抽象方法加 public / protected ⭐

```java
// 包：com.shop.base
abstract class Product {
    abstract double calcTotal(int q);   // 包级（default）访问权限
}

// 包：com.shop.impl
class Book extends Product {
    @Override
    double calcTotal(int q) { return 0; }   // ❌ 编译错误：跨包无法重写包级抽象方法
}
```

抽象方法若不带修饰符就是**包级访问权限**，跨包继承时子类根本「看不见」它。**写抽象方法时务必显式加 `public` 或 `protected`**。

### 重点 5：重写抽象方法不能缩小访问权限 ⭐

```java
abstract class Product {
    protected abstract double calcTotal(int q);
}

class Book extends Product {
    @Override
    double calcTotal(int q) { return 0; }    // ❌ 试图将 protected 降为包级：编译错误
}
```

规则与普通重写一致：**子类方法访问权限 ≥ 父类**。

### 重点 6：匿名子类可以继承抽象类

抽象类不能 `new`，但可以「当场写一个子类再 new」：

```java
Shape s = new Shape() {              // ✅ 匿名子类，必须实现全部抽象方法
    @Override
    public double area() { return 1.0; }
};
```

这在回调、临时实现里非常常用（配合接口的匿名实现，见 [15-内部类](15-内部类.md)）。

### 重点 7：抽象类不能是 final，但可以是 sealed（Java 17）

```java
final abstract class A { }        // ❌ 自相矛盾：final 禁止继承，abstract 要求被继承
```

「要求被继承」和「禁止被继承」不能同时成立。

## 💻 实战案例

### 案例 1：电商商品抽象体系 ⭐⭐

用抽象类统一「计价」规范，同时复用展示逻辑。

```java
import java.util.Arrays;

abstract class Product {
    private final String name;
    private final double price;

    protected Product(String name, double price) {
        this.name = name;
        this.price = price;
    }

    public String getName() { return name; }
    public double getPrice() { return price; }

    /** 抽象方法：每个品类的计价规则不同，父类无法统一实现 */
    public abstract double calcTotal(int quantity);

    /** 普通方法：所有商品共用的账单打印，内部调用抽象方法（多态） */
    public void printBill(int quantity) {
        System.out.printf("%s x%d，单价 %.2f，应付 %.2f%n",
                name, quantity, price, calcTotal(quantity));
    }
}

class Book extends Product {
    Book(String name, double price) { super(name, price); }

    @Override
    public double calcTotal(int quantity) {
        return getPrice() * quantity;                 // 图书不打折
    }
}

class Electronics extends Product {
    Electronics(String name, double price) { super(name, price); }

    @Override
    public double calcTotal(int quantity) {
        double total = getPrice() * quantity;
        return quantity >= 3 ? total * 0.9 : total;   // 满 3 件 9 折
    }
}

class FreshFood extends Product {
    FreshFood(String name, double price) { super(name, price); }

    @Override
    public double calcTotal(int quantity) {
        return getPrice() * quantity * 0.95;          // 生鲜一律 95 折
    }
}

public class ProductDemo {
    public static void main(String[] args) {
        Product[] cart = {
                new Book("Java编程思想", 99.0),
                new Electronics("机械键盘", 399.0),
                new FreshFood("鲜牛奶", 12.5)
        };
        int[] quantities = {2, 3, 4};

        double total = 0;
        for (int i = 0; i < cart.length; i++) {
            cart[i].printBill(quantities[i]);
            total += cart[i].calcTotal(quantities[i]);
        }
        System.out.printf("订单合计：%.2f 元%n", total);
    }
}
```

输出：

```
Java编程思想 x2，单价 99.00，应付 198.00
机械键盘 x3，单价 399.00，应付 1077.30
鲜牛奶 x4，单价 12.50，应付 47.50
订单合计：1322.80 元
```

> 💡 注意 `printBill()` 只写了一次，却服务于三个品类。以后新增「图书满 5 本包邮」的 `Magazine` 子类，一行老代码都不用改。

### 案例 2：模板方法模式——数据导出 ⭐⭐

**模板方法模式**是抽象类最经典的应用：父类用 `final` 固定流程骨架，把可变步骤留给子类。

```java
import java.util.*;

abstract class DataExporter {

    /** 模板方法：流程骨架固定，final 防止子类篡改顺序 */
    public final void export(String fileName, List<Map<String, Object>> rows) {
        if (rows == null || rows.isEmpty()) {
            System.out.println("⚠️ 没有数据可导出");
            return;
        }
        List<String> columns = columns(rows);
        StringBuilder sb = new StringBuilder();

        writeHeader(sb, columns);                       // 可变步骤 1
        for (Map<String, Object> row : rows) {
            writeRow(sb, columns, row);                 // 可变步骤 2
        }
        if (needSummary()) {                            // 钩子：可选步骤
            writeSummary(sb, rows.size());
        }
        doWrite(fileName + "." + fileExtension(), sb.toString());   // 可变步骤 3
    }

    // ---- 子类必须实现 ----
    protected abstract String fileExtension();
    protected abstract void writeHeader(StringBuilder sb, List<String> columns);
    protected abstract void writeRow(StringBuilder sb, List<String> columns, Map<String, Object> row);
    protected abstract void doWrite(String fileName, String content);

    // ---- 父类提供的通用实现 ----
    protected List<String> columns(List<Map<String, Object>> rows) {
        return new ArrayList<>(rows.get(0).keySet());
    }

    protected void writeSummary(StringBuilder sb, int count) {
        sb.append("-- 共 ").append(count).append(" 条记录 --\n");
    }

    /** 钩子方法：默认返回 true，子类可覆盖以改变流程 */
    protected boolean needSummary() {
        return true;
    }
}

class CsvExporter extends DataExporter {
    @Override protected String fileExtension() { return "csv"; }

    @Override protected void writeHeader(StringBuilder sb, List<String> columns) {
        sb.append(String.join(",", columns)).append('\n');
    }

    @Override protected void writeRow(StringBuilder sb, List<String> columns, Map<String, Object> row) {
        for (int i = 0; i < columns.size(); i++) {
            if (i > 0) sb.append(',');
            sb.append(row.get(columns.get(i)));
        }
        sb.append('\n');
    }

    @Override protected void doWrite(String fileName, String content) {
        System.out.println("写入文件 " + fileName + "：");
        System.out.print(content);
    }
}

class HtmlExporter extends DataExporter {
    @Override protected String fileExtension() { return "html"; }

    @Override protected void writeHeader(StringBuilder sb, List<String> columns) {
        sb.append("<table>\n  <tr>");
        for (String c : columns) sb.append("<th>").append(c).append("</th>");
        sb.append("</tr>\n");
    }

    @Override protected void writeRow(StringBuilder sb, List<String> columns, Map<String, Object> row) {
        sb.append("  <tr>");
        for (String c : columns) sb.append("<td>").append(row.get(c)).append("</td>");
        sb.append("</tr>\n");
    }

    @Override protected void doWrite(String fileName, String content) {
        System.out.println("写入文件 " + fileName + "：");
        System.out.println(content + "</table>");
    }

    /** 覆盖钩子：HTML 报表不需要「共 N 条」的纯文本尾巴 */
    @Override protected boolean needSummary() {
        return false;
    }
}

public class ExportDemo {
    public static void main(String[] args) {
        List<Map<String, Object>> rows = new ArrayList<>();
        Map<String, Object> r1 = new LinkedHashMap<>();
        r1.put("姓名", "张三"); r1.put("城市", "北京"); r1.put("金额", 1200.0);
        Map<String, Object> r2 = new LinkedHashMap<>();
        r2.put("姓名", "李四"); r2.put("城市", "上海"); r2.put("金额", 980.5);
        rows.add(r1);
        rows.add(r2);

        new CsvExporter().export("report", rows);
        System.out.println();
        new HtmlExporter().export("report", rows);
    }
}
```

输出：

```
写入文件 report.csv：
姓名,城市,金额
张三,北京,1200.0
李四,上海,980.5
-- 共 2 条记录 --

写入文件 report.html：
<table>
  <tr><th>姓名</th><th>城市</th><th>金额</th></tr>
  <tr><td>张三</td><td>北京</td><td>1200.0</td></tr>
  <tr><td>李四</td><td>上海</td><td>980.5</td></tr>
</table>
```

> 💡 **模式三要素**：`final` 模板方法（锁流程）+ 抽象方法（必填步骤）+ 钩子方法（可选覆盖）。Spring 的 `JdbcTemplate`、`AbstractApplicationContext#refresh()` 都是这个结构。

### 案例 3：接口定契约 + 抽象类补实现——支付渠道 ⭐⭐

这是实际项目最常用的写法：**对外暴露接口，对内用抽象类复用公共逻辑**。

```java
interface PayChannel {
    void pay(String orderNo, double amount);
}

abstract class AbstractPayChannel implements PayChannel {
    private final String channelName;

    protected AbstractPayChannel(String channelName) {
        this.channelName = channelName;
    }

    /** 接口方法在这里被 final 固化：校验 → 支付 → 后置回调 */
    @Override
    public final void pay(String orderNo, double amount) {
        if (amount <= 0) {
            throw new IllegalArgumentException("金额必须大于 0");
        }
        System.out.printf("[%s] 订单 %s 发起支付 %.2f 元%n", channelName, orderNo, amount);
        doPay(orderNo, amount);          // 抽象步骤：各渠道不同
        afterPay(orderNo, amount);       // 钩子：默认空实现
    }

    protected abstract void doPay(String orderNo, double amount);

    protected void afterPay(String orderNo, double amount) { }
}

class AlipayChannel extends AbstractPayChannel {
    AlipayChannel() { super("支付宝"); }

    @Override
    protected void doPay(String orderNo, double amount) {
        System.out.println("  → 调用支付宝网关 alipay.trade.pay");
    }
}

class WechatChannel extends AbstractPayChannel {
    WechatChannel() { super("微信支付"); }

    @Override
    protected void doPay(String orderNo, double amount) {
        System.out.println("  → 调用微信统一下单 /v3/pay/transactions/jsapi");
    }

    @Override
    protected void afterPay(String orderNo, double amount) {
        System.out.println("  → 向用户推送支付成功模板消息");
    }
}

class BalanceChannel extends AbstractPayChannel {
    private double balance = 500.0;

    BalanceChannel() { super("余额支付"); }

    @Override
    protected void doPay(String orderNo, double amount) {
        if (balance < amount) {
            throw new IllegalStateException("余额不足，当前余额 " + balance);
        }
        balance -= amount;
        System.out.printf("  → 余额扣减成功，剩余 %.2f 元%n", balance);
    }
}

public class PayDemo {
    public static void main(String[] args) {
        PayChannel[] channels = { new AlipayChannel(), new WechatChannel(), new BalanceChannel() };
        for (PayChannel c : channels) {
            c.pay("NO20261103001", 199.0);
            System.out.println();
        }
    }
}
```

输出：

```
[支付宝] 订单 NO20261103001 发起支付 199.00 元
  → 调用支付宝网关 alipay.trade.pay

[微信支付] 订单 NO20261103001 发起支付 199.00 元
  → 调用微信统一下单 /v3/pay/transactions/jsapi
  → 向用户推送支付成功模板消息

[余额支付] 订单 NO20261103001 发起支付 199.00 元
  → 余额扣减成功，剩余 301.00 元
```

**设计收益**：

1. 调用方只依赖 `PayChannel` 接口，新增渠道不改调用代码；
2. 参数校验、日志等公共逻辑只写一次，子类无法绕过（`final`）；
3. 各渠道只关注自己的 `doPay()`。

### 案例 4：泛型抽象基类——DAO 复用 ⭐

抽象类 + 泛型，是「通用 CRUD 基类」的标准做法。

```java
import java.util.*;

abstract class BaseRepository<T> {
    private final Map<Long, T> store = new LinkedHashMap<>();
    private long sequence = 0;

    /** 子类告诉我：这张表叫什么 */
    protected abstract String tableName();

    /** 子类告诉我：怎么从实体里取主键 */
    protected abstract Long getId(T entity);

    /** 通用保存逻辑，所有子类复用 */
    public void save(T entity) {
        Long id = getId(entity);
        if (id == null) {
            id = ++sequence;
            setId(entity, id);
        }
        store.put(id, entity);
        System.out.printf("[%s] 保存成功，id=%d，当前共 %d 条%n", tableName(), id, store.size());
    }

    public T findById(Long id) {
        return store.get(id);
    }

    public List<T> findAll() {
        return new ArrayList<>(store.values());
    }

    public int count() {
        return store.size();
    }

    /** 主键回填：默认空实现，需要自增主键的子类自行覆盖 */
    protected void setId(T entity, Long id) { }
}

class User {
    private Long id;
    private String name;
    User(Long id, String name) { this.id = id; this.name = name; }
    public Long getId() { return id; }
    public void setId(Long id) { this.id = id; }
    @Override public String toString() { return "User{id=" + id + ", name='" + name + "'}"; }
}

class UserRepository extends BaseRepository<User> {
    @Override protected String tableName() { return "t_user"; }
    @Override protected Long getId(User entity) { return entity.getId(); }
    @Override protected void setId(User entity, Long id) { entity.setId(id); }
}

public class RepositoryDemo {
    public static void main(String[] args) {
        UserRepository repo = new UserRepository();
        repo.save(new User(null, "张三"));
        repo.save(new User(null, "李四"));
        repo.save(new User(100L, "王五"));

        System.out.println(repo.findById(1L));
        System.out.println("总数：" + repo.count());
    }
}
```

输出：

```
[t_user] 保存成功，id=1，当前共 1 条
[t_user] 保存成功，id=2，当前共 2 条
[t_user] 保存成功，id=100，当前共 3 条
User{id=1, name='张三'}
总数：3
```

> 💡 把 `UserRepository` 换成 `OrderRepository`，只需要实现两个方法，`save/findAll/count` 全部现成——这就是「抽象类复用状态与算法」的价值，接口做不到。

### 案例 5：抽象类 + 匿名子类——带重试的模板 ⭐

抽象类配合匿名子类，可以做出非常紧凑的「一次性流程」。

```java
abstract class RetryTask<T> {
    private final int maxAttempts;
    private final String taskName;

    protected RetryTask(String taskName, int maxAttempts) {
        this.taskName = taskName;
        this.maxAttempts = maxAttempts;
    }

    public final T execute() {
        RuntimeException last = null;
        for (int attempt = 1; attempt <= maxAttempts; attempt++) {
            try {
                return doExecute();
            } catch (RuntimeException e) {
                last = e;
                System.out.printf("  第 %d 次执行失败：%s%n", attempt, e.getMessage());
                if (!shouldRetry(e) || attempt == maxAttempts) {
                    break;
                }
                sleep(50L * attempt);
            }
        }
        throw new IllegalStateException("[" + taskName + "] 重试 " + maxAttempts + " 次仍失败", last);
    }

    /** 子类实现真正的业务动作 */
    protected abstract T doExecute();

    /** 钩子：决定某类异常是否值得重试 */
    protected boolean shouldRetry(RuntimeException e) {
        return true;
    }

    private void sleep(long millis) {
        try {
            Thread.sleep(millis);
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
        }
    }
}

public class RetryDemo {
    public static void main(String[] args) {
        final int[] callCount = {0};

        String rate = new RetryTask<String>("查询汇率", 3) {
            @Override
            protected String doExecute() {
                callCount[0]++;
                if (callCount[0] < 3) {
                    throw new RuntimeException("网关超时");
                }
                return "USD/CNY = 7.12";
            }
        }.execute();

        System.out.println("最终结果：" + rate);
    }
}
```

输出：

```
  第 1 次执行失败：网关超时
  第 2 次执行失败：网关超时
最终结果：USD/CNY = 7.12
```

> 💡 把「重试次数、退避、异常过滤」这些与业务无关的逻辑固定住，业务代码只写 `doExecute()` 一个方法——这正是模板方法模式在生产代码里的典型形态。

## 🚀 新版本补充

### Java 8：接口有了 default 方法，抽象类还有优势吗

Java 8 允许接口写 `default` 方法，看起来「接口也能提供实现了」。但两者仍有本质差距：

| 能力 | 抽象类 | 接口（Java 8+） |
| :--- | :---: | :---: |
| 实例字段（状态） | ✅ | ❌ 只能是常量 |
| 构造方法 | ✅ | ❌ |
| `protected` 方法 | ✅ | ❌ 接口方法隐式 public |
| 单继承限制 | 会占用唯一继承名额 | 可多实现 |
| `final` 固化流程 | ✅ | ❌ `default` 可被覆盖 |

**结论**：需要**复用状态**或**固化流程**时用抽象类；只是**定义能力契约并给点默认实现**时用接口。两者是互补关系，不是替代关系。

### Java 17：sealed 密封类 + 抽象类

`sealed` 允许抽象类**精确控制谁能继承它**，补齐了「抽象类太开放」的短板：

```java
// Java 17+
public sealed abstract class Shape permits Circle, Rectangle, Triangle { }

final class Circle extends Shape { }
final class Rectangle extends Shape { }
final class Triangle extends Shape { }
```

配合 Java 21 的 switch 模式匹配，编译器就能做到穷尽性检查（`switch` 少写一个分支直接编译报错）。这是「抽象类 + 有限子类集合」的现代写法。

### Java 16：record 不能继承抽象类

`record` 隐式继承 `java.lang.Record`，所以**不能 extends 任何类**，包括抽象类：

```java
abstract class Base { }
record Point(int x, int y) extends Base { }    // ❌ 编译错误：record 不能继承类
record Point(int x, int y) implements Serializable { }   // ✅ 可以实现接口
```

如果一套抽象设计未来可能被 `record` 实现，请**用接口而不是抽象类**。

### JDK 中的抽象类家族

| 抽象类 | 作用 | 留给子类的抽象方法 |
| :--- | :--- | :--- |
| `java.io.InputStream` | 字节输入流骨架 | `read()` |
| `java.io.OutputStream` | 字节输出流骨架 | `write(int)` |
| `java.util.AbstractCollection` | 集合通用逻辑 | `iterator()`、`size()` |
| `java.util.AbstractList` | 列表通用逻辑 | `get(int)` |
| `java.util.AbstractMap` | 映射通用逻辑 | `entrySet()` |
| `javax.servlet.http.HttpServlet` | HTTP 请求分发骨架 | `doGet()` / `doPost()`（钩子式） |
| `org.springframework.context.support.AbstractApplicationContext` | 容器刷新流程 | `refreshBeanFactory()` 等 |

> 💡 阅读这些类的源码时，留意同一个套路：**模板方法 `final` 锁流程 + 抽象方法留扩展点 + 钩子方法给默认行为**。

## 本章小结

| 知识点 | 核心要点 |
| :--- | :--- |
| 为什么需要抽象类 | 父类无法给出实现时，用抽象方法「强制子类实现」，把运行时错误提前到编译期 |
| 语法 | `abstract` 修饰类或方法；抽象方法无方法体，以 `;` 结尾 |
| 实例化 | 抽象类不能 `new`，但可以声明引用、进数组、做参数和返回值 |
| 构造方法 | 抽象类**有**构造方法，供子类 `super()` 调用，且先于子类构造执行 |
| 子类责任 | 必须重写**全部**抽象方法，否则子类也必须声明为 `abstract` |
| 成员构成 | 成员变量、常量、构造方法、普通方法、静态方法、代码块、内部类，一样不缺 |
| 修饰符互斥 | `abstract` 不能与 `private` / `static` / `final` / `native` / `synchronized` 共用；抽象类不能是 `final` |
| 与多态的关系 | 父类普通方法里调用抽象方法，运行时执行子类实现（动态绑定） |
| 与接口的区别 | 抽象类表达 is-a、可有状态与构造方法；接口表达 can-do、可多实现 |
| 经典应用 | 模板方法模式、DAO 泛型基类、接口适配器、JDK 的 `AbstractXxx` 家族 |
| 高频坑 | 构造方法里调抽象方法（子类字段未初始化）、抽象方法漏写 `public/protected` 导致跨包无法重写 |

**一句话总结**：抽象类 = 把「必须实现什么」写进类型系统，让编译器替你监督子类。

## 学习建议

1. **先改一遍老代码**：把之前写的「父类方法 `return 0`」或「`throw new UnsupportedOperationException()`」的地方，改成抽象方法，体会编译期约束带来的安全感。
2. **手写一次模板方法模式**：用「校验 → 处理 → 通知」三段式，写一个 `AbstractTask`，再用两个子类实现，重点感受 `final` 模板方法 + 钩子的配合。
3. **对比 `AbstractList` 源码**：打开 JDK 的 `java.util.AbstractList`，看它如何用 `get(int)` 一个抽象方法支撑起 `indexOf`、`iterator`、`equals` 等一堆通用方法。
4. **刻意练习选型**：拿项目里任意一个「接口 + 多个实现」的场景，问自己「这里该不该补一个抽象骨架类」，并写下理由。
5. **接着读 [13-多态](13-多态.md)**：抽象类是「规范的制定者」，多态是「规范的执行机制」；把两者连起来，方法调用的动态绑定过程就彻底通了。
