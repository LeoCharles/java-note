# 循环依赖与三级缓存

前面学了依赖注入，有一个绕不开的话题——**循环依赖**。A 依赖 B，B 依赖 A，怎么办？Spring 用三级缓存解决了 Setter/字段注入的循环依赖，但构造器注入的循环依赖无法解决。本篇从原理到源码，彻底讲透这个面试大热门。

> 💡 为什么要学这个？1）面试必问（"Spring 怎么解决循环依赖"能聊 15 分钟）；2）实际项目中重构时，循环依赖是最常见的启动报错；3）理解了三级缓存，你对 Spring IoC 容器的理解会上一个大台阶。

---

## 一、什么是循环依赖

### 1.1 三种场景

```java
// 场景一：构造器循环依赖 —— ❌ 无法解决
@Service
public class ServiceA {
    private final ServiceB serviceB;
    public ServiceA(ServiceB serviceB) { this.serviceB = serviceB; }
}

@Service
public class ServiceB {
    private final ServiceA serviceA;
    public ServiceB(ServiceA serviceA) { this.serviceA = serviceA; }
}

// 场景二：Setter 循环依赖 —— ✅ 可以解决
@Service
public class ServiceA {
    private ServiceB serviceB;
    @Autowired public void setServiceB(ServiceB serviceB) { this.serviceB = serviceB; }
}

@Service
public class ServiceB {
    private ServiceA serviceA;
    @Autowired public void setServiceA(ServiceA serviceA) { this.serviceA = serviceA; }
}

// 场景三：字段注入循环依赖 —— ✅ 可以解决
@Service
public class ServiceA {
    @Autowired private ServiceB serviceB;
}

@Service
public class ServiceB {
    @Autowired private ServiceA serviceA;
}
```

**结论**：Spring 只能解决 **singleton Bean** 的 Setter 注入 / 字段注入循环依赖。构造器注入 + prototype 作用域的循环依赖**无法解决**。

### 1.2 为什么构造器循环依赖无法解决

构造器注入需要"在创建对象时就把依赖传进去"，但两个对象都在创建中、都拿不到对方：

```
new ServiceA(serviceB)
    → 发现需要 serviceB，开始创建 ServiceB
    → new ServiceB(serviceA)
        → 发现需要 serviceA，但 ServiceA 还在创建中（构造没完成）
        → 死循环 → BeanCurrentlyInCreationException
```

> 💡 Bean 的创建是一个原子过程——构造方法必须先完成，对象才算"存在"。构造器注入要求"创建前准备好依赖"，两个 Bean 都等着对方先创建完，死锁。

## 二、三级缓存详解 ⭐⭐

### 2.1 三级缓存是什么

Spring 在 `DefaultSingletonBeanRegistry` 中定义了三个 Map，专门解决循环依赖：

```java
public class DefaultSingletonBeanRegistry {
    /**
     * 一级缓存（singletonObjects）：存放完全创建好的 Bean
     * key: beanName, value: 成品对象（可能被 AOP 代理过的最终对象）
     */
    private final Map<String, Object> singletonObjects = new ConcurrentHashMap<>(256);

    /**
     * 二级缓存（earlySingletonObjects）：存放提前暴露的半成品 Bean
     * key: beanName, value: 已经实例化但还没填充属性的早期对象
     * 从三级缓存升级上来的
     */
    private final Map<String, Object> earlySingletonObjects = new HashMap<>(16);

    /**
     * 三级缓存（singletonFactories）：存放能"创建代理对象"的工厂
     * key: beanName, value: 一个 ObjectFactory，调用 getObject() 可以生成早期引用
     * 调完后这个工厂就删了，产物升级到二级缓存
     */
    private final Map<String, ObjectFactory<?>> singletonFactories = new HashMap<>(16);
}
```

### 2.2 三级缓存的核心流程图

用 A ↔ B 循环依赖的例子：

```
时间线 →
Bean A 的创建过程：
  ① 实例化 A（new ServiceA()，构造方法执行完）
  ② 把自己（原始引用）放入三级缓存：singletonFactories.put("a", () → getEarlyBeanReference("a", ...))
  ③ 属性填充：发现需要 B → getBean("b")
     │
     └──→ Bean B 的创建过程：
           ④ 实例化 B（new ServiceB()）
           ⑤ 把自己放入三级缓存：singletonFactories.put("b", () → getEarlyBeanReference("b", ...))
           ⑥ 属性填充：发现需要 A → getBean("a")
              │
              └──→ 在三级缓存中找到 A 的 factory
                   ⑦ 调 factory.getObject() → 得到 A 的早期引用（如果有 AOP 需要，这里生成代理对象）
                   ⑧ 把早期引用从三级缓存移到二级缓存
                   ⑨ 把 A 的早期引用注入到 B
           ⑩ B 初始化完成，放入一级缓存
     ←───
  ⑪ 把 B 注入到 A（B 已经完整了）
  ⑫ 初始化 A，A 创建完成，放入一级缓存
```

**关键步骤 ⑦**：如果 A 需要 AOP 代理，三级缓存的 `getEarlyBeanReference()` 会在这时创建代理对象。**AOP 代理不是等 Bean 完全初始化后才创建，而是"发现需要提前暴露时"就创建了**——这保证了 B 注入的 A 引用和最终暴露的 A 是同一个代理对象。

### 2.3 为什么是三级而不是两级？

**核心原因：AOP 代理的延迟创建**。

如果只有两级缓存（成品 + 半成品），问题来了：一个需要 AOP 代理的 Bean A，在第一次提前暴露时，你放的是**原始对象**还是**代理对象**？

- 放原始对象？→ B 注入了原始 A，但最终暴露的应该是代理 A → 不一致！
- 放代理对象？→ 大部分 Bean 根本不需要代理，每次都创建代理太浪费。

**三级缓存的巧妙之处**：第三级存的是一个 `ObjectFactory`（工厂），而不是对象本身。这个工厂的 `getEarlyBeanReference()` 方法会判断"A 需不需要 AOP 代理"：

- 不需要 → 返回原始对象（大部分情况）
- 需要 → 调用 `SmartInstantiationAwareBeanPostProcessor.getEarlyBeanReference()` 生成代理对象，然后把代理对象升级到二级缓存

```java
// 三级缓存工厂的 getObject() 方法（简化逻辑）
() -> {
    Object earlyBeanReference = bean;  // 原始对象
    // 遍历所有 SmartInstantiationAwareBeanPostProcessor
    for (SmartInstantiationAwareBeanPostProcessor bp : processors) {
        earlyBeanReference = bp.getEarlyBeanReference(earlyBeanReference, beanName);
        // ↑ 如果需要代理，这里就把原始对象替换为代理对象
    }
    return earlyBeanReference;
}

// 调完后，删除三级缓存，升级到二级：
// singletonFactories.remove("a");
// earlySingletonObjects.put("a", earlyBeanReference);
```

> 💡 **一句话总结三级缓存**：一级存成品，二级存"提前暴露的半成品/代理"，三级存"能生成提前暴露对象的工厂"。三级的工厂让 AOP 代理能在需要时才创建（懒），而不是盲目给每个 Bean 都创建代理。

## 三、循环依赖的解决方案

### 3.1 方案一：重新设计（根本方案）⭐

循环依赖通常是**设计问题**的信号。审查一下：是不是两个 Service 职责没分清楚？

```java
// ❌ 循环依赖：OrderService ↔ UserService
@Service
public class OrderService {
    @Autowired private UserService userService;  // 需要查用户
}
@Service
public class UserService {
    @Autowired private OrderService orderService; // 需要查订单
}

// ✅ 提取公共逻辑：引入中间层
@Service
public class UserQueryService {
    // 用户相关查询
}

@Service
public class OrderQueryService {
    // 订单相关查询
}

@Service
public class OrderService {
    @Autowired private UserQueryService userQueryService;  // 不再依赖 UserService
}

@Service
public class UserService {
    @Autowired private OrderQueryService orderQueryService; // 不再依赖 OrderService
}
```

### 3.2 方案二：@Lazy 延迟注入

如果一个循环依赖确实无法避免，用 `@Lazy` 让 Spring 先注入一个代理，等真正用到时才去找真正的 Bean：

```java
@Service
public class ServiceA {
    @Autowired
    @Lazy  // ← 注入的是一个代理，不做真正初始化
    private ServiceB serviceB;
}

@Service
public class ServiceB {
    @Autowired
    @Lazy
    private ServiceA serviceA;
}
```

`@Lazy` 的原理：注入的不是真正的 `ServiceB`，而是一个 CGLIB 代理对象。当 `serviceB.xxx()` 第一次被调用时，代理才去容器中获取真正的 Bean。这样就打破了"创建时必须依赖"的锁。

> 💡 构造器注入的循环依赖也可以用 `@Lazy` 解决：

```java
@Service
public class ServiceA {
    private final ServiceB serviceB;
    public ServiceA(@Lazy ServiceB serviceB) {  // 注入代理
        this.serviceB = serviceB;
    }
}
```

### 3.3 方案三：改用 Setter/字段注入

把构造器注入改为字段注入或 Setter 注入，让 Spring 的三级缓存机制来兜底：

```java
// 从构造器注入改为字段注入
@Service
public class ServiceA {
    @Autowired private ServiceB serviceB;
}

@Service
public class ServiceB {
    @Autowired private ServiceA serviceA;
}
```

> ⚠️ 这不是"最佳实践"，只是应急方案。能重新设计消除循环依赖就不要走这条路。

## 💻 实战案例

### 案例：验证三级缓存全过程

```java
@Service
public class CircularA {
    private CircularB b;

    public CircularA() {
        System.out.println("A 构造方法执行");
    }

    @Autowired
    public void setCircularB(CircularB b) {
        System.out.println("A 注入了 B");
        this.b = b;
    }

    @PostConstruct
    public void init() {
        System.out.println("A @PostConstruct: B = " + (b != null ? "已注入" : "null"));
    }
}

@Service
public class CircularB {
    private CircularA a;

    public CircularB() {
        System.out.println("B 构造方法执行");
    }

    @Autowired
    public void setCircularA(CircularA a) {
        System.out.println("B 注入了 A");
        this.a = a;
    }

    @PostConstruct
    public void init() {
        System.out.println("B @PostConstruct: A = " + (a != null ? "已注入" : "null"));
    }
}
```

**输出顺序（Spring Boot 启动时）**：

```
A 构造方法执行          ← ① 实例化 A，放入三级缓存
B 构造方法执行          ← ② 填充 A 的属性时发现需要 B → 创建 B
B 注入了 A             ← ③ B 的属性需要 A → 从三级缓存获取 A 的早期引用，注入
B @PostConstruct: A = 已注入  ← ④ B 初始化完成，放入一级缓存
A 注入了 B             ← ⑤ 回到 A 的属性填充，B 已经就绪，注入
A @PostConstruct: B = 已注入  ← ⑥ A 初始化完成，放入一级缓存
```

> 💡 注意第③步：B 被注入的 A 还是"半成品"（属性还没填充完）。但因为注入的是引用，等 A 的属性后续填充完成后，B 持有的 A 引用自然就"完整"了——这是 Java 引用传递的特性。

## 🎯 面试高频

### Q1：Spring 如何解决循环依赖？

**答**：通过**三级缓存**解决 singleton Bean 的 Setter/字段注入的循环依赖：

1. **一级缓存（singletonObjects）**：存放完全创建好的成品 Bean
2. **二级缓存（earlySingletonObjects）**：存放提前暴露的半成品 Bean（或早期代理）
3. **三级缓存（singletonFactories）**：存放能生成早期引用的 ObjectFactory

**流程**：A 实例化 → 把 A 的工厂放入三级缓存 → 填充属性时发现需要 B → 创建 B → B 填充属性时发现需要 A → 从三级缓存获取 A 的早期引用 → 注入 B → B 创建完成 → 回到 A，注入 B → A 创建完成。

**构造器注入的循环依赖无法解决**，因为构造器需要在对象创建阶段就传入完整的依赖，而此时双方都还没创建完。

### Q2：为什么是三级缓存，不是两级？

**答**：因为 **AOP 代理的延迟创建**需求。如果只有两级缓存（成品 + 半成品），那"半成品"放原始对象还是代理对象就成了问题——放原始对象会导致最终的代理和注入的不一致（B 拿到的 A 和最终暴露的 A 不同），放代理对象又会给每个 Bean 都创建代理（浪费）。

三级缓存的第三级是一个 `ObjectFactory`，它的 `getEarlyBeanReference()` 方法能**在需要的时候**再决定要不要创建代理：
- 不需要代理 → 返回原始对象（大多数情况）
- 需要代理 → 调用 AOP 的 `getEarlyBeanReference()` 生成代理，升级到二级缓存

### Q3：prototype Bean 的循环依赖能解决吗？

**答**：不能。prototype Bean 每次获取都创建新实例，没有缓存机制。A → B → A 这种循环，到第二次要 A 时无法从缓存获取（prototype 不缓存），会陷入无限创建循环，最终抛 `BeanCurrentlyInCreationException`。

## 📌 在 Spring Boot 中

- Spring Boot 默认所有的 Bean 都是 singleton，所以 Setter/字段注入的循环依赖可以被三级缓存解决。但 Spring Boot 2.6+ **默认禁止了循环依赖**，如果检测到会打印警告甚至抛异常：

```yaml
# Spring Boot 2.6+
spring:
  main:
    allow-circular-references: true   # 显式允许循环依赖（不推荐）
```

- **不要依赖三级缓存**。虽然它能解决循环依赖，但循环依赖通常是设计问题。Spring Boot 2.6+ 默认禁止循环依赖就是官方态度——"我们能解决，但你不该这么写"。
- 推荐做法：用 `@Lazy` 打破循环，或者重新设计消除循环（提取公共依赖到第三个 Bean）。

## 本章小结

| 知识点 | 要点 |
| :--- | :--- |
| 循环依赖场景 | 构造器循环（❌ 无法解决）、Setter 循环（✅）、字段注入循环（✅） |
| 一级缓存 | singletonObjects：成品 Bean，`getBean()` 优先从这里找 |
| 二级缓存 | earlySingletonObjects：提前暴露的半成品 / 早期代理 |
| 三级缓存 | singletonFactories：ObjectFactory，能判断是否需要创建代理 |
| 三级缓存流程 | 实例化 → 三级缓存 → 属性填充（触发对方创建，对方从三级缓存拿早期引用）→ 初始化 → 一级缓存 |
| 为什么三级 | AOP 代理的延迟创建：三级工厂决定"要不要代理"，需要时才生成早期代理 |
| 解决方案 | 重新设计（最优）> @Lazy（次优）> 改字段注入（应急） |

## 学习建议

1. **画图理解三级缓存**。拿张纸画出 A ↔ B 的创建流程，标上每一步在一/二/三级缓存的"存取"操作。面试时能画这个流程图，比背八股文强十倍。
2. **验证构造器循环依赖的报错**：写两个 Bean 通过构造器互相依赖，启动项目看报错信息（`BeanCurrentlyInCreationException`），记住这个错误长什么样——以后项目启动报这个错就知道是循环依赖。
3. **验证 AOP + 循环依赖**：给循环依赖的 Bean 加上 `@Transactional`（会生成代理），观察三级缓存如何生成早期代理对象。可以下断点跟踪 `getEarlyBeanReference()` 方法。
4. **检查自己项目的循环依赖**：如果用的 Spring Boot 2.6+，去掉 `allow-circular-references: true`，看启动日志有没有循环依赖警告——有的话尽快重构。
