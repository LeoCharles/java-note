# 事务传播与隔离级别

上一篇学了 `@Transactional` 的基本用法和失效场景。本篇深入事务最核心、也是最容易出事故的两个概念：**传播行为**（一个事务方法调另一个事务方法时，事务怎么处理）和**隔离级别**（多个事务并发时，数据可见性怎么保证）。这两个概念是面试大热门，更是生产故障高发区。

> 💡 传播行为中 **REQUIRED vs REQUIRES_NEW** 的区别、隔离级别中**脏读/不可重复读/幻读**的定义——这五个词是后端面试的"固定曲目"，本篇让你从根上理解而不是死记硬背。

---

## 一、事务传播行为（Propagation）

### 1.1 什么是传播行为

**场景**：ServiceA.methodA() 有事务，它调用了 ServiceB.methodB()，methodB 也有事务注解。这时 methodB 是共用 A 的事务，还是新建一个自己的事务？

**这就是传播行为要回答的问题**。

### 1.2 七种传播行为

| 传播行为 | 含义 | 使用频率 |
| :--- | :--- | :--- |
| **REQUIRED** | 默认。有事务就用当前的，没有就新建 | ⭐⭐⭐⭐⭐ 99% 场景 |
| **REQUIRES_NEW** | 无论有没有事务，都新建一个独立的 | ⭐⭐⭐ 日志、审计 |
| **NESTED** | 嵌套事务：创建 savepoint，可独立回滚 | ⭐⭐ 部分回滚 |
| SUPPORTS | 有事务就用，没有就裸跑 | ⭐ 可选的只读操作 |
| NOT_SUPPORTED | 有事务就挂起，自己裸跑 | ⭐ 不需要事务的重操作 |
| MANDATORY | 必须有事务，没有就抛异常 | ⭐ 强制要求事务 |
| NEVER | 绝对不能有事务，有就抛异常 | ⭐ 强制非事务 |

### 1.3 REQUIRED：默认传播（主力）⭐⭐⭐

```java
@Service
public class OrderService {
    @Autowired private LogService logService;

    @Transactional(propagation = Propagation.REQUIRED)
    public void createOrder(Order order) {
        orderDao.save(order);           // 操作1
        logService.recordLog(order);    // 操作2：调另一个 @Transactional 方法
        // 两个操作在同一个事务中——操作1 失败 → 操作2 也不提交；操作2 失败 → 操作1 也回滚
    }
}

@Service
public class LogService {
    @Transactional(propagation = Propagation.REQUIRED)  // 默认就是 REQUIRED
    public void recordLog(Order order) {
        logDao.save(new Log(order.getId()));
    }
}
```

**流程**：

```
createOrder() 开始 → 没有事务 → REQUIRED 新建事务（TX-1）
    │
    ├── orderDao.save(order)        ← 在 TX-1 中
    ├── logService.recordLog()      ← 已有 TX-1 → REQUIRED 直接用 TX-1
    │       └── logDao.save(log)    ← 也在 TX-1 中
    │
    └── 方法结束 → TX-1 提交/回滚（两个操作一起）
```

> 💡 REQUIRED 是"一根绳上的蚂蚱"——调用的和被调用的在同一个事务中，要成功一起成功，要回滚一起回滚。

### 1.4 REQUIRES_NEW：独立事务 ⭐⭐⭐

```java
@Service
public class OrderService {
    @Autowired private AuditService auditService;

    @Transactional(propagation = Propagation.REQUIRED)
    public void createOrder(Order order) {
        orderDao.save(order);           // 操作1：在 TX-1 中

        try {
            auditService.audit(order);  // 操作2：新建独立事务 TX-2
        } catch (Exception e) {
            // 审计失败了，不耽误下单
            log.error("审计记录失败", e);
        }

        // 操作3：继续在 TX-1 中
    }
}

@Service
public class AuditService {
    @Transactional(propagation = Propagation.REQUIRES_NEW)
    public void audit(Order order) {
        auditDao.save(new AuditRecord(order.getId()));  // 如果这行抛异常，只回滚 TX-2
        // TX-1 不受影响！
    }
}
```

**流程**：

```
createOrder() 开始 → 没有事务 → REQUIRED 新建 TX-1
    │
    ├── save(order)                     ← 在 TX-1 中
    ├── auditService.audit(order)
    │       │
    │       ├── TX-1 被挂起（suspend）
    │       ├── REQUIRES_NEW 新建 TX-2（独立事务）
    │       ├── save(audit)             ← 在 TX-2 中
    │       ├── TX-2 提交/回滚（独立于 TX-1）
    │       └── TX-1 恢复
    │
    └── 方法结束 → TX-1 提交/回滚
```

> 💡 REQUIRES_NEW 是"各管各的"——被调用的方法独立开事务，和调用方的事务互不影响。典型场景：**操作日志/审计记录**——日志写失败了不能影响主业务。

**REQUIRED vs REQUIRES_NEW 对比**：

| | REQUIRED | REQUIRES_NEW |
| :--- | :--- | :--- |
| **事务数量** | 共用 1 个 | 各自独立 |
| **回滚影响** | 被调用方抛异常 → 调用方也回滚 | 被调用方抛异常 → 只回滚自己的 |
| **适用场景** | 业务操作（下单+扣库存要一起成功） | 非核心操作（日志/审计/通知） |

### 1.5 NESTED：嵌套事务

```java
@Service
public class OrderService {

    @Transactional(propagation = Propagation.REQUIRED)
    public void batchImport(List<Order> orders) {
        // TX-1 外部事务
        for (Order order : orders) {
            try {
                importSingle(order);   // 每个订单一个嵌套事务
            } catch (Exception e) {
                log.error("订单 {} 导入失败，跳过", order.getId(), e);
                // 失败的 rollback 到 savepoint，不影响其他订单
            }
        }
        // TX-1 正常提交 → 成功的订单全部入库
    }

    @Transactional(propagation = Propagation.NESTED)
    public void importSingle(Order order) {
        orderDao.save(order);
        // 如果这条抛异常 → 回滚到 importSingle 开头的 savepoint
        // 不影响 batchImport 中其他已成功的订单
    }
}
```

> ⚠️ `NESTED` 依赖 JDBC 的 `Savepoint` 机制。**只有 JdbcTemplate + DataSourceTransactionManager 支持**，JPA 的 JpaTransactionManager 不支持 NESTED。

## 二、事务隔离级别

### 2.1 并发事务的三大问题

| 问题 | 描述 | 示例 |
| :--- | :--- | :--- |
| **脏读** | 读到其他事务**未提交**的数据 | A 事务改了余额为 200，B 事务读到 200，A 事务回滚了 → B 读到的 200 是脏数据 |
| **不可重复读** | 同一事务内两次读同一条数据，**结果不同** | 事务内第一次读 age=20，中间被其他事务改成 age=21 并提交，第二次读 age=21 |
| **幻读** | 同一事务内两次查，**记录数不同** | 事务内第一次查 10 条记录，中间别的事务插入了一条并提交，第二次查 11 条 |

### 2.2 四种隔离级别

```
                   脏读    不可重复读    幻读
READ_UNCOMMITTED    ✅       ✅         ✅        ↓ 隔离性越来越强
READ_COMMITTED      ❌       ✅         ✅
REPEATABLE_READ     ❌       ❌         ✅  (MySQL InnoDB 也解决了幻读)
SERIALIZABLE        ❌       ❌         ❌
```

✅ = 问题存在（不安全）   ❌ = 问题解决（安全）

**各数据库默认隔离级别**：

| 数据库 | 默认隔离级别 | 常量值 |
| :--- | :--- | :--- |
| **MySQL（InnoDB）** | **REPEATABLE_READ** | 4 |
| **Oracle** | READ_COMMITTED | 2 |
| **PostgreSQL** | READ_COMMITTED | 2 |

### 2.3 在 Spring 中设置隔离级别

```java
@Transactional(isolation = Isolation.READ_COMMITTED)
public void updateBalance(Long userId, BigDecimal amount) {
    // 这个事务使用 READ_COMMITTED 隔离级别
    accountDao.update(userId, amount);
}

@Transactional(isolation = Isolation.REPEATABLE_READ)
public void transfer(Long from, Long to, BigDecimal amount) {
    // 转账用 REPEATABLE_READ，防止不可重复读
}
```

**隔离级别的选择原则**：

| 场景 | 推荐 | 原因 |
| :--- | :--- | :--- |
| 一般业务 | 跟随数据库默认 | MySQL 默认 RR，PostgreSQL 默认 RC |
| 高并发扣库存 | READ_COMMITTED | 避免间隙锁导致的死锁 |
| 转账/对账 | REPEATABLE_READ | 防止金额在事务内变化 |
| 严格一致性要求 | SERIALIZABLE | 极少使用，性能代价大 |

> 💡 **大多数业务场景**：不需要显式设置隔离级别，跟随数据库默认即可。MySQL InnoDB 的 REPEATABLE_READ 通过 **MVCC + 间隙锁（Next-Key Lock）** 实际上也解决了幻读问题。

## 三、传播 + 隔离的综合案例

### 下单操作的事务设计

```java
@Service
@RequiredArgsConstructor
public class OrderService {
    private final OrderDao orderDao;
    private final InventoryService inventoryService;
    private final AccountService accountService;
    private final AuditLogService auditLogService;

    @Transactional(
        propagation = Propagation.REQUIRED,        // 默认
        isolation = Isolation.READ_COMMITTED,       // MySQL 下用 RC 避免间隙锁
        rollbackFor = Exception.class,              // 所有异常回滚
        timeout = 30                                // 30 秒超时
    )
    public void createOrder(CreateOrderRequest request) {
        // 1. 扣库存（REQUIRED，同一事务——扣库存失败了订单也不能生成）
        inventoryService.deduct(request.getItems());

        // 2. 扣款（REQUIRED，同一事务）
        accountService.deduct(request.getUserId(), request.getTotalAmount());

        // 3. 保存订单（同一事务）
        Order order = orderDao.save(toOrder(request));

        // 4. 记录审计日志（REQUIRES_NEW，独立事务——日志失败了不影响下单）
        try {
            auditLogService.record("CREATE_ORDER", order.getId());
        } catch (Exception e) {
            log.error("审计日志记录失败（不影响下单）", e);
        }

        // 5. 发通知（非事务方法——通知失败了不影响下单）
        try {
            notificationService.sendOrderNotification(order);
        } catch (Exception e) {
            log.error("通知发送失败", e);
        }
    }
}

@Service
public class AuditLogService {
    @Transactional(propagation = Propagation.REQUIRES_NEW)
    public void record(String action, Long orderId) {
        auditLogDao.save(new AuditLog(action, orderId));
    }
}
```

**事务架构图**：

```
createOrder() TX-1（REQUIRED, READ_COMMITTED）
    │
    ├── inventoryService.deduct()         ← TX-1
    ├── accountService.deduct()           ← TX-1
    ├── orderDao.save()                   ← TX-1
    │
    ├── auditLogService.record()          ← TX-2（REQUIRES_NEW，独立）
    │       ├── TX-1 挂起
    │       ├── TX-2 执行
    │       └── TX-1 恢复
    │
    ├── notificationService.send()        ← 无事务
    │
    └── TX-1 提交
```

> 💡 **设计原则**：**核心业务操作共用一个事务（REQUIRED），非关键操作独立事务（REQUIRES_NEW），纯通知/外部调用不用事务。** 这样保证：库存 + 金额 + 订单要么全成功、要么全回滚；审计日志的成功与否不影响主流程。

## 💻 实战案例

### 验证 REQUIRED vs REQUIRES_NEW

```java
@Service
@RequiredArgsConstructor
public class PropagationDemo {
    private final UserDao userDao;
    private final PropagationDemo self; // 注入自己，通过代理调方法避免内部调用失效

    @Transactional(propagation = Propagation.REQUIRED, rollbackFor = Exception.class)
    public void testRequired() {
        userDao.save(new User("A", 20));            // ← 在 TX-1 中
        try {
            self.saveWithException();               // ← 也在 TX-1 中，抛异常会导致 TX-1 回滚
        } catch (Exception e) {
            log.error("内部异常", e);
        }
        // TX-1 已经是 rollback-only 状态，即使 catch 了异常，提交时也会抛 UnexpectedRollbackException
    }

    @Transactional(propagation = Propagation.REQUIRES_NEW, rollbackFor = Exception.class)
    public void saveWithException() {
        userDao.save(new User("B", 25));
        throw new RuntimeException("B 保存后抛出异常"); // 只回滚 TX-2（B），不影响 TX-1（A）
    }
}
```

**验证结果**：
- `REQUIRES_NEW` 方法抛异常 → 只回滚 B，A 正常保存
- 如果换成 `REQUIRED` → A 和 B 一起回滚

## 🎯 面试高频

### Q1：REQUIRED 和 REQUIRES_NEW 的区别？举例说明使用场景。

**答**：
- **REQUIRED**：共用一个事务。被调方抛异常 → 双方都回滚。场景：下单 + 扣库存，两者必须一起成功或一起失败。
- **REQUIRES_NEW**：新建独立事务。调用方的事务被挂起，被调方独立提交或回滚。场景：操作审计日志——日志写失败了不应该影响主业务。

### Q2：MySQL 默认隔离级别是什么？为什么能防幻读？

**答**：MySQL InnoDB 默认 **REPEATABLE_READ**。通过**间隙锁（Next-Key Lock）** 防止幻读：索引记录之间的"间隙"也被锁定，其他事务无法在这些间隙中插入新数据，因此同一事务内两次范围查询的结果一致。

### Q3：事务并发可能产生哪些问题？

**答**：脏读（读到未提交数据）、不可重复读（同一条数据两次读结果不同）、幻读（两次查的记录数不同）。

## 📌 在 Spring Boot 中

- Spring Boot 默认传播行为就是 REQUIRED，99% 的场景不需要改
- 需要独立事务的场景（如审计日志）用 `@Transactional(propagation = Propagation.REQUIRES_NEW)`
- 查询方法建议加 `@Transactional(readOnly = true)`，让数据库做只读优化
- `spring.jpa.open-in-view` 默认 true 会延长事务到视图层，建议设为 false 避免不必要的长事务

## 本章小结

| 知识点 | 要点 |
| :--- | :--- |
| REQUIRED（默认） | 共用事务——一条绳上的蚂蚱，要回退一起回退 |
| REQUIRES_NEW | 独立事务——挂起原事务，新建独立事务，适合日志/审计 |
| NESTED | 嵌套事务——Savepoint 机制，部分回滚 |
| READ_UNCOMMITTED | 最低隔离——脏读/不可重复读/幻读都存在 |
| READ_COMMITTED | 防脏读——Oracle/PostgreSQL 默认 |
| REPEATABLE_READ | 防脏读+不可重复读——MySQL (InnoDB) 默认，通过间隙锁也防幻读 |
| SERIALIZABLE | 串行执行——最安全但性能最差 |

## 学习建议

1. **用代码验证传播行为**：写两个 Service，methodA 用 REQUIRED，methodB 分别用 REQUIRED 和 REQUIRES_NEW。在 methodB 中抛异常，对比 methodA 的数据是否回滚。
2. **用两个数据库连接窗口验证隔离级别**：窗口1 `BEGIN; UPDATE ... SET balance = 200;`（不提交），窗口2 不同隔离级别下 `SELECT balance`——亲身验证脏读和不可重复读。
3. **记住一句话**：核心业务 REQUIRED + 一起提交，非核心日志 REQUIRES_NEW + 独立提交，查询用 readOnly。
