# 依赖注入方式详解

前三篇讲的是"容器怎么管理 Bean"——注册、作用域、生命周期、条件装配。从本篇开始进入 IoC 的第二层含义：**依赖获取权反转**——容器不是只存对象，还要把对象之间的依赖关系自动"注入"好。本篇详细讲解三种注入方式，以及在实际项目中的选型原则。

> 💡 DI（Dependency Injection）是 IoC 的具体实现。如果说 IoC 是"交给容器管"，DI 就是"容器帮你把依赖准备好"。本篇是三篇 DI 系列的开篇，06 讲自动装配规则，07 讲循环依赖。

---

## 一、什么是依赖注入

### 1.1 直觉理解

```java
// ❌ 没有 DI：自己管依赖
public class OrderService {
    private UserService userService = new UserService();   // 自己 new
    private OrderDao orderDao = new OrderDao();             // 自己 new
}

// ✅ 有 DI：容器管依赖
public class OrderService {
    private UserService userService;
    private OrderDao orderDao;

    public OrderService(UserService userService, OrderDao orderDao) {
        // 依赖从外部"注入"，OrderService 只管用
        this.userService = userService;
        this.orderDao = orderDao;
    }
}
```

DI 的本质：**使用方只声明"我需要什么"，由容器负责提供**。使用方不关心依赖从哪来、怎么创建、是单例还是多例。

### 1.2 DI 的三种方式总览

| 方式 | 注入位置 | Spring 版本 | 推荐度 |
| :--- | :--- | :--- | :--- |
| **构造器注入** | 构造方法参数 | 最早就支持 | ⭐⭐⭐ 官方推荐 |
| **Setter 注入** | setter 方法 | 最早就支持 | ⭐⭐ 可选依赖 |
| **字段注入** | 字段（反射设值） | 2.5+（`@Autowired`） | ⭐ 便捷但不推荐 |

## 二、构造器注入（Constructor Injection）⭐⭐⭐

### 2.1 基本写法

```java
@Service
public class OrderService {
    private final UserService userService;   // final：一旦注入不可变
    private final OrderDao orderDao;

    // 构造器注入：Spring 自动从容器中找到 UserService 和 OrderDao，传入构造方法
    public OrderService(UserService userService, OrderDao orderDao) {
        this.userService = userService;
        this.orderDao = orderDao;
    }
}
```

**Spring 4.3+ 简化**：如果类**只有一个构造方法**，`@Autowired` 可以省略：

```java
@Service
public class OrderService {
    private final UserService userService;
    private final OrderDao orderDao;

    // 只有一个构造方法 → Spring 自动用它注入，不需要 @Autowired
    public OrderService(UserService userService, OrderDao orderDao) {
        this.userService = userService;
        this.orderDao = orderDao;
    }
}
```

### 2.2 Lombok 简化：@RequiredArgsConstructor

```java
@Service
@RequiredArgsConstructor  // ← 为所有 final 字段生成构造方法
public class OrderService {
    private final UserService userService;
    private final OrderDao orderDao;
    // 不需要写构造方法了！Lombok 编译期生成
}
```

编译后等价于：
```java
@Service
public class OrderService {
    private final UserService userService;
    private final OrderDao orderDao;

    public OrderService(UserService userService, OrderDao orderDao) {
        this.userService = userService;
        this.orderDao = orderDao;
    }
}
```

> 💡 这是 Spring Boot 项目中最常见的写法：**`@RequiredArgsConstructor` + `private final` 字段**，兼顾简洁性和不可变性。

### 2.3 构造器注入的优点

| 优点 | 说明 |
| :--- | :--- |
| **不可变性** | 依赖用 `final` 修饰，注入后不能被修改 |
| **依赖明确** | 构造参数列出来就是所有依赖，不会藏着隐式依赖 |
| **保证就绪** | 对象创建完依赖就齐全，不存在"NPE 风险" |
| **方便测试** | 单测时直接 `new Service(mockDao, mockService)`，不用 Spring 容器 |
| **防止循环依赖** | 构造器注入的循环依赖无法解决，启动即报错（比运行时才发现好） |

## 三、Setter 注入（Setter Injection）⭐⭐

### 3.1 基本写法

```java
@Service
public class OrderService {
    private UserService userService;
    private OrderDao orderDao;

    @Autowired
    public void setUserService(UserService userService) {
        this.userService = userService;
    }

    @Autowired
    public void setOrderDao(OrderDao orderDao) {
        this.orderDao = orderDao;
    }
}
```

### 3.2 适用场景

Setter 注入适用于**可选依赖**——这个依赖不是必须的，没有也能正常工作：

```java
@Service
public class OrderService {
    private SmsService smsService;  // 可选：有些环境不发短信

    @Autowired(required = false)   // ← 没有这个 Bean 也不报错
    public void setSmsService(SmsService smsService) {
        this.smsService = smsService;
    }

    public void createOrder(Order order) {
        // ...
        if (smsService != null) {  // 用之前要判空
            smsService.send(order.getUserPhone(), "下单成功");
        }
    }
}
```

> ⚠️ **注意事项**：Setter 注入的依赖不是 final 的，可能在运行时被修改。如果有其他代码调了 setter 把依赖换掉了，极难排查。除非确实需要可选注入，否则优先用构造器注入。

## 四、字段注入（Field Injection）⭐

### 4.1 基本写法

```java
@Service
public class OrderService {
    @Autowired
    private UserService userService;  // 连 setter 都不需要，反射直接设值

    @Autowired
    private OrderDao orderDao;
}
```

### 4.2 为什么不推荐

字段注入是代码最少的写法，也是网上教程最常见的写法，但 **Spring 官方不推荐**，原因：

| 问题 | 说明 |
| :--- | :--- |
| **无法使用 final** | 字段不能是 final，可被修改 |
| **依赖隐藏** | 看字段列表不知道哪些是注入的，哪些是普通变量 |
| **难以测试** | 单测无法 `new Service()` 后手动设值（字段 private），必须用反射或启动 Spring 容器 |
| **强依赖 Spring** | 脱离 Spring 容器就无法工作，Pojo 不纯 |
| **容易注入过多** | 加一个依赖只需一行 `@Autowired`，没有"痛感"，不知不觉一个类注入了十几个依赖（违反单一职责） |

### 4.3 一句话总结选型

> 💡 **日常开发：构造器注入（`@RequiredArgsConstructor` + `final`）是唯一真理。特殊场景：Setter 注入用于可选依赖。字段注入：能不用就不用。**

## 五、三种注入方式的对比示例

```java
// ===== 方式一：构造器注入（推荐）=====
@Service
@RequiredArgsConstructor
public class OrderServiceV1 {
    private final UserService userService;
    private final OrderDao orderDao;

    public void createOrder(Order order) {
        userService.validate(order.getUserId());
        orderDao.save(order);
    }
}

// ===== 方式二：Setter 注入（可选依赖场景）=====
@Service
public class OrderServiceV2 {
    private final UserService userService;
    private final OrderDao orderDao;
    private SmsService smsService;

    public OrderServiceV2(UserService userService, OrderDao orderDao) {
        this.userService = userService;
        this.orderDao = orderDao;
    }

    @Autowired(required = false)
    public void setSmsService(SmsService smsService) {
        this.smsService = smsService;
    }
}

// ===== 方式三：字段注入（不推荐）=====
@Service
public class OrderServiceV3 {
    @Autowired
    private UserService userService;
    @Autowired
    private OrderDao orderDao;
}
```

**单测友好度对比**：

```java
// 构造器注入 → 纯 new 就能测，不需要 Spring
@Test
void testConstructorInjection() {
    UserService mockUser = mock(UserService.class);
    OrderDao mockDao = mock(OrderDao.class);
    OrderServiceV1 service = new OrderServiceV1(mockUser, mockDao);  // 一行搞定
    // 测试...
}

// 字段注入 → 必须启动 Spring 容器或用反射
@Test
void testFieldInjection() {
    OrderServiceV3 service = new OrderServiceV3();
    // userService 是 private 的，怎么设值？
    // 只能用反射或 @SpringBootTest 启动整个容器——重且慢
}
```

## 💻 实战案例

### 案例 1：构造器注入的全家桶

```java
@RestController
@RequestMapping("/orders")
@RequiredArgsConstructor
public class OrderController {
    private final OrderService orderService;
    private final OrderConverter orderConverter;

    @PostMapping
    public Result<OrderVO> create(@Valid @RequestBody CreateOrderRequest request) {
        Order order = orderConverter.toEntity(request);
        orderService.createOrder(order);
        return Result.success(orderConverter.toVO(order));
    }

    @GetMapping("/{id}")
    public Result<OrderVO> getById(@PathVariable Long id) {
        Order order = orderService.findById(id);
        return Result.success(orderConverter.toVO(order));
    }
}

@Service
@RequiredArgsConstructor
public class OrderService {
    private final OrderDao orderDao;
    private final UserService userService;
    private final InventoryService inventoryService;

    @Transactional
    public void createOrder(Order order) {
        userService.validate(order.getUserId());
        inventoryService.deduct(order.getItems());
        orderDao.save(order);
    }
}
```

### 案例 2：循环依赖触发构造器注入失败

```java
@Service
public class ServiceA {
    private final ServiceB serviceB;

    public ServiceA(ServiceB serviceB) {  // 需要 ServiceB
        this.serviceB = serviceB;
    }
}

@Service
public class ServiceB {
    private final ServiceA serviceA;

    public ServiceB(ServiceA serviceA) {  // 需要 ServiceA
        this.serviceA = serviceA;
    }
}

// Spring 启动报错：
// UnsatisfiedDependencyException → BeanCurrentlyInCreationException
// → Is there an unresolvable circular reference?
```

> 💡 构造器注入的循环依赖**无法解决**，Spring 会在启动时就报错——这是好事！比运行时才发现循环依赖强多了。如果必须循环依赖，参考 [07-循环依赖与三级缓存](07-循环依赖与三级缓存.md)。

## 🎯 面试高频

### Q1：构造器注入、Setter 注入、字段注入的区别和选择？

**答**：
- **构造器注入**：依赖通过构造参数传入，可用 `final`，保证不可变和依赖齐全。Spring 官方推荐。Lombok `@RequiredArgsConstructor` 简化写法。
- **Setter 注入**：通过 setter 方法注入，适合**可选依赖**（`@Autowired(required = false)`）。
- **字段注入**：`@Autowired` 在字段上，代码最少但隐藏了依赖、不能用 `final`、难测试。Spring 官方不推荐。

选型原则：构造器注入为主、Setter 注入用于可选依赖、字段注入尽量不用。

### Q2：为什么 Spring 官方推荐构造器注入？

**答**：三个核心原因——
1. **不可变性**：依赖可以声明为 `final`
2. **依赖明确**：构造参数直接暴露所有依赖，不会悄悄加十几个
3. **方便测试**：不需要 Spring 容器就能 `new` 对象并传入 Mock 依赖

## 📌 在 Spring Boot 中

- Spring Boot 项目中，**`@RequiredArgsConstructor` + `private final` 字段**是最主流写法——Lombok 编译期生成构造器，Spring 自动注入，简洁且安全。
- 构造器是唯一的依赖入口，当你给一个 Service 加了第 5 个 `final` 依赖时，构造函数参数变成 5 个——这种"痛感"是好事，提醒你可能要拆分职责了。如果用的是字段注入，加第 10 个 `@Autowired` 也毫无痛感。
- Spring Boot 官方文档和 [Spring Initializr](https://start.spring.io) 生成的代码都是构造器注入风格。

## 本章小结

| 知识点 | 要点 |
| :--- | :--- |
| 构造器注入 | 依赖通过构造参数传入，可用 final，官方推荐，`@RequiredArgsConstructor` 简化 |
| Setter 注入 | `@Autowired` 在 setter 上，适合可选依赖 `required = false` |
| 字段注入 | `@Autowired` 在字段上，反射设值，代码最少但隐藏依赖、难测试，官方不推荐 |
| 选型原则 | 构造器注入为主 + Setter 可选 + 字段不用 |
| 单构造器规则 | 类只有一个构造方法时，`@Autowired` 可省略（Spring 4.3+） |

## 学习建议

1. **把现有项目的 `@Autowired` 字段注入改成构造器注入**。特别是看到 Service 里有超过 3 个 `@Autowired` 字段时，改造成构造器注入后你会直观感受到"依赖太多"——这是重构的信号。
2. **熟悉 `@RequiredArgsConstructor`**：这几乎是 Spring Boot 开发的标配。配置 IDEA 的 Live Template，输入 `srv` 自动生成 `@Service @RequiredArgsConstructor public class XxxService { }`。
3. **尝试写一个可选依赖的场景**：比如 Service 中的"审计日志记录器"——开发环境不记录、生产环境记录。用 Setter 注入 + `@Autowired(required = false)` 实现这个需求。
